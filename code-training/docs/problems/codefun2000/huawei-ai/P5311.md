# P5311. 双资源约束下的运维任务收益最大化

> 场次：2026年8月26日 · 来源：[CodeFun2000 P5311](https://codefun2000.com/p/P5311)

## 题目描述

运维团队在批量处理服务器运维任务时，需要合理分配有限的内存资源和算力资源。每个任务执行后会占用一定量的资源，同时能够带来对应的运维收益，例如增强系统稳定性、降低变更风险等。

现有$n$个待执行任务，系统最多可以提供$A$单位内存和$B$单位算力。对于第$i$个任务，执行它需要消耗$x_i$单位内存、$y_i$单位算力，并可以获得收益$w_i$。

请从所有任务中选择若干个执行，使所选任务的内存消耗总量不超过$A$，算力消耗总量不超过$B$，并使获得的总运维收益最大。

在得到最大收益的情况下，还需要确定对应方案的内存总消耗和算力总消耗。若存在多个方案获得的收益相同，则优先选择内存消耗更小的方案；若内存消耗也相同，则选择算力消耗更小的方案。

## 输入格式

第一行输入三个整数$n$、$A$、$B$（$1 \le n \le 100$，$1 \le A \le 500$，$1 \le B \le 500$），分别表示任务数量、可使用的最大内存和可使用的最大算力。

第二行到$(n+1)$行，每行输入三个正整数$x_i$、$y_i$、$w_i$（$1 \le x_i \le 100$，$1 \le y_i \le 100$，$1 \le w_i \le 100$），分别表示第$i$个任务的内存消耗、算力消耗和运维收益。

## 输出格式

输出三个整数，用空格分隔：

1. 最大运维收益
2. 达到最大收益时的总内存消耗
3. 达到最大收益时的总算力消耗

若有多组方案都能达到最大收益，输出内存消耗最小的方案；若内存消耗也相同，则输出算力消耗最小的方案。

## 示例

### 示例 1

**输入：**

```text
4 12 10
5 4 8
6 3 10
4 6 9
3 2 5
```

**输出：**

```text
19 10 9
```

### 示例 2

**输入：**

```text
3 9 8
4 3 7
5 4 9
3 4 6
```

**输出：**

```text
16 9 7
```

**说明：**

选择第1、2个任务，总内存$(4+5=9)$，总算力$(3+4=7)$，总收益$(7+9=16)$

## 解题思路

### 输出比「最大收益」多了两个数

题面要求的输出是三个整数：最大收益、达到该收益时的内存消耗与算力消耗。后两个数不是「随便挑哪个收益最大的方案」——判定标准写得很具体：收益先做到最大；在所有收益最大的方案里，内存消耗小的优先；内存也相同时，算力消耗小的优先。三个目标排成一条字典序。

这条判定标准决定了状态必须长什么样。若 `dp[...]` 只记「最多能拿多少收益」，多个方案打平时都被折叠成同一个数，输出里两个消耗值无从取起——次级目标必须在平局发生时仍能区分方案。

### 数据范围把解法指向背包

每个任务只有「选/不选」两种命运，内存、算力、收益都沿选择逐项叠加；并且在剩余资源限制下继续决策时，「已选任务 $i$」的方案恰好由「更小子问题的结果」加上任务 $i$ 的固定贡献构成。问题按子问题定义——这就是背包的形状。

数据范围进一步坐实：$n\le100$ 但 $A,B\le500$。枚举全部选择方案是 $2^{100}$，根本不可行；而以「两种资源的上限」为状态做 DP，转移约 $n\times A\times B=2.5\times10^7$ 次，用 Python 也能限时内跑完。大到枚不动的决策数、小到可能开二维表的容量，正是二维背包留在数据范围里的暗号。

### 把三级排序压成一个整数的状态

最自然的起步状态是「容量 $(a,b)$ 下能拿到的最大收益」，如上所述不够用。把状态升级为三元组（收益、−内存、−算力）按字典序比较，判定标准就完整了——这条路线正确可行，但每次转移都要构造并逐项比较三个分量。既然判定标准只是字典序，而三个分量取值范围有限，就能把整条字典序编码成单个整数再做比较：

$$
\text{score} = \text{收益}\times\text{PU} - \text{内存}\times\text{MU} - \text{算力}
$$

两个常数（初始化 `memory_unit` 与 `profit_unit` 的那两行）取：

$$
\text{MU} = B + 1,\qquad \text{PU} = A\times\text{MU} + B + 1
$$

为什么恰好是它们？逐条检查「抵消」会不会发生：

- 内存与算力之间：算力最多是 $B$。内存多 1 扣 $\text{MU}=B+1$，而算力省下的分数最多回补 $B$，任何方案只要内存多 1，即使算力省到 0 也仍净多扣至少 1——内存差的判定不可能被算力翻转。$\text{MU}=B$ 则恰好抵平：内存差 1 与算力差 $B$ 追平。
- 收益与资源之间：一个方案的资源总扣分最多 $A\times\text{MU}+B$。$\text{PU}$ 比这个上界刚好大 1，所以两方案只要收益差 1，score 至少差 $\text{PU}-(A\times\text{MU}+B)=1>0$——收益差的判定不可能被资源差翻转。

于是 `dp[a][b]` 存一个整数，「哪个方案更好」退化为一次整数比较。转移里选物品的增量是 `gain = profit*profit_unit - memory*memory_unit - compute`，与编码逐项对上。

### 转移：与二维 0/1 背包同构

$$
dp[a][b] = \max\bigl(dp[a][b],\ dp[a-x_i][b-y_i] + \text{gain}_i\bigr)
$$

两个容量维都要**倒序**枚举：正序时 `dp[a-x][b-y]` 可能已在本轮把当前任务计入，同一任务就会被选两次。这是从一维 0/1 背包升级到二维时最容易漏的一处：外层 `for a in range(max_memory, memory-1, -1)` 与内层 `for b in range(..., -1, -1)` 各管一个维度。二维表压成一维数组（`a*width + b`，`width=B+1`）只是省 Python 嵌套列表寻址的常数，不改变转移逻辑；单件就超容量的任务在处理时直接 `continue`。

### 从 score 反解输出

DP 收尾取一维表最后一格 `dp[A][B]`。它满足

$$
\text{score}=P\times\text{PU}-\text{penalty},\quad \text{penalty}=\text{内存}\times\text{MU}+\text{算力},\ 0\le\text{penalty}<\text{PU}
$$

收益用**向上取整**还原：score 被 penalty 拉低过，普通整除会少 1，代码里写的是 `(best + profit_unit - 1) // profit_unit`。随后 `penalty // memory_unit` 得内存、`% memory_unit` 得算力，算力恒小于 MU 保证拆分不串位。DP 表初值全 0 即「空方案」，全部任务都超容量时自然输出 `0 0 0`。

## 完整代码实现

```python
"""
P5311. 双资源约束下的运维任务收益最大化 - 二维 0/1 背包

输入格式：
- 第 1 行：三个整数 n、A、B；
- 接下来 n 行：每行三个正整数 x_i、y_i、w_i。

输出格式：
- 一行三个整数：最大收益、总内存消耗、总算力消耗。

时间复杂度：O(n * A * B)
空间复杂度：O(A * B)
"""

import sys


def solve():
    # 一次性读入全部整数。ACM 模式下用 buffer.read() 比逐行 input() 更快，
    # 也不会因为行末空格或空行影响解析。
    data = sys.stdin.buffer.read().split()
    if not data:
        return

    it = iter(data)
    n = int(next(it))
    max_memory = int(next(it))
    max_compute = int(next(it))

    # dp 本来是二维表：dp[a][b] 表示“内存上限为 a、算力上限为 b”时的最优分数。
    # 为了减少 Python 嵌套列表的寻址开销，这里把它压成一维数组：
    #   二维下标 (a, b)  ->  一维下标 a * width + b
    # 其中 width 是一行里有多少个算力状态（b 从 0 到 max_compute）。
    width = max_compute + 1
    dp = [0] * ((max_memory + 1) * width)

    # 下面两个“单位”用来把三个目标编码成一个整数：
    #
    #   score = 收益 * profit_unit - 内存 * memory_unit - 算力
    #
    # memory_unit 必须严格大于算力上限，这样“内存多 1”造成的扣分
    # 一定大于“算力减少最多 B”带来的补偿，保证同收益时内存优先。
    #
    # profit_unit 必须严格大于所有方案可能产生的最大惩罚值
    # memory * memory_unit + compute（最多 A * memory_unit + B），
    # 这样“收益多 1”一定大于任何资源扣分差，保证收益优先。
    memory_unit = max_compute + 1
    profit_unit = max_memory * memory_unit + max_compute + 1

    for _ in range(n):
        # 读入当前任务：内存消耗、算力消耗、收益。
        memory = int(next(it))
        compute = int(next(it))
        profit = int(next(it))

        # 如果单个任务的内存或算力已经超过上限，它不可能出现在任何合法方案里。
        if memory > max_memory or compute > max_compute:
            continue

        # 选择当前任务，相当于在分数上加上：
        #   收益 * profit_unit        （收益越多越好）
        #   - 内存 * memory_unit      （内存越少越好）
        #   - 算力                    （算力越少越好）
        gain = profit * profit_unit - memory * memory_unit - compute

        # 0/1 背包的容量必须倒序枚举。
        # 以内存 a 为例：如果从小到大枚举，dp[a - memory] 可能已经在本轮
        # 选过当前任务，再转移就会把同一个任务选两次。
        for a in range(max_memory, memory - 1, -1):
            # 一维数组中，容量 a 这一行的起点
            base = a * width
            # 选当前任务之前，内存上限是 a - memory，对应上一行的起点
            prev_base = (a - memory) * width

            # 算力 b 同样要倒序枚举，原因和上面的内存完全一样。
            for b in range(max_compute, compute - 1, -1):
                # 不选当前任务时，dp[base + b] 保持原值；
                # 选当前任务时，从“扣掉当前任务消耗”的旧状态转移过来。
                candidate = dp[prev_base + b - compute] + gain
                index = base + b
                if candidate > dp[index]:
                    dp[index] = candidate

    # 容量上限为 (max_memory, max_compute) 的状态，在扁平数组的最后一个位置。
    best = dp[max_memory * width + max_compute]

    # score = profit * profit_unit - penalty，其中 0 <= penalty < profit_unit。
    # 因为 score 可能被 penalty 拉低，直接整除会少算 1，所以这里用向上取整。
    profit = (best + profit_unit - 1) // profit_unit
    penalty = profit * profit_unit - best

    # penalty = 内存 * memory_unit + 算力。
    # 因为算力 < memory_unit，所以整除得到内存，取余得到算力。
    memory_used = penalty // memory_unit
    compute_used = penalty % memory_unit

    print(profit, memory_used, compute_used)


if __name__ == "__main__":
    solve()
```

## 示例推演

以样例 1 为例：任务 $(5,4,8),(6,3,10),(4,6,9),(3,2,5)$，上限 $(12,10)$；编码常数 $\text{MU}=11$，$\text{PU}=12\times11+10+1=143$。

| 组合 | 内存 | 算力 | 收益 | score |
| ---- | ---- | ---- | ---- | ----- |
| 2+3 | 10 | 9 | 19 | $19\times143-10\times11-9=2598$ |
| 1+2 | 11 | 7 | 18 | $18\times143-11\times11-7=2446$ |
| 1+3 | 9 | 10 | 17 | $17\times143-9\times11-10=2322$ |
| 2+4 | 9 | 5 | 15 | $15\times143-9\times11-5=2041$ |
| 1+2+4 | 14 | — | — | 内存超限 |
| 1+3+4 | 12 | 12 | 22 | 算力超限 |

收益最靠前的是 2+3，输出 `19 10 9`。再走一遍反解：$P=\lceil2598/143\rceil=19$，$\text{penalty}=19\times143-2598=119$，内存 $=119\div11=10$，算力 $=119\bmod11=9$。

最值得看的是同收益平局怎么被打破，补两组演示：

- 收益相同、内存有差：上限 $(10,10)$ 下 $(6,6,10)$ 与 $(5,5,10)$ 二选一收益都是 10，两个 score 相差 $(6-5)\times11+(6-5)=12$，内存 5 的方案胜出，输出 `10 5 5`——这个差值正是「$\text{MU}$ 必须大于算力上限」在起作用。
- 内存也相同、差在算力：$(4,6,10)$ 与 $(4,2,10)$ 的 score 相差 $6-2=4$，选算力 2，输出 `10 4 2`。

样例 2：任务 $(4,3,7),(5,4,9),(3,4,6)$，上限 $(9,8)$。三个任务全选要内存 12、算力 11，双双超限；可行组合里 1+2 收益 16 最靠前（内存 9、算力 7），输出 `16 9 7`。

## 复杂度分析

| 解法 | 时间复杂度 | 空间复杂度 | 说明 |
| ---- | ---------- | ---------- | ---- |
| 枚举任务子集 | $O(2^n \cdot n)$ | $O(n)$ | $n=100$ 时方案数 $2^{100}$，不可行 |
| 二维 DP，状态存「收益-内存-算力」三元组 | $O(nAB)$ | $O(AB)$ | 可行且正确，但每次转移都比较三个分量 |
| 二维 DP + 整数编码（最优） | $O(nAB)$ | $O(AB)$ | 平局比较退化为一次整数比较；本题采用 |

$n=100$、$A=B=500$ 时转移约 $2.5\times10^7$ 次，Python 中可以接受。

## 易错点总结

### 1. 编码常数取错时，样例常常照过

`memory_unit` 必须是 `B+1`：写成 `B` 后「内存多 1」与「算力多 B」恰成平手，同收益下内存优先会被算力差翻转；而且反解时算力与内存的进位纠缠，像「内存 9、算力 10」这样的方案会被拆成 `10 0`。`profit_unit` 必须大于最大资源扣分 `A*memory_unit + B`，太小时收益差 1 会被资源差吞掉，输出会落在一个收益不是最大的方案上。这两个常数取错时，「胜者独大」的数据（如样例 1）照样通过，只有同收益多方案的数据才照出问题——示例推演里那两组平局数据就是一个现成的检验。

### 2. 反解收益要向上取整

score $=$ 收益 $\times$ PU $-$ penalty，只要方案消耗过资源，penalty 就大于 0，直接整除比真实收益少 1。代码里写的是 `(best + profit_unit - 1) // profit_unit` 这一行；改成普通 `//` 后输出的第一列普遍偏小，反解出的内存、算力也随后跟着错。

### 3. 两种容量都要倒序枚举

外层 `range(max_memory, memory-1, -1)` 与内层 `range(max_compute, compute-1, -1)` 都是从大到小。只要有一维正序，`dp[a-x][b-y]` 可能已经在本轮更新过，同一个任务被算进两次——现象是输出收益比真实答案大、却没有任何报错。二维时尤其容易只倒序了内存一维。

## 扩展思考

- 本题把「收益最大、内存最小、算力最小」叠进一个比较键，靠的是每个分量取值范围有限。若输出还要方案本身（选了哪些任务），整数编码外再配一个决策来源数组即可，DP 骨架不变。
- 资源再多一维就是三维背包，做法相同，但每多一维就多乘一个容量上限：当资源上限大到 $O(nAB)$ 装不下时，可以反过来以收益为状态维、记录最省资源，或者对状态做 Pareto 剪枝。
- 若题面不要求输出方案的资源消耗，普通二维 0/1 背包即可，不需要任何编码。
