你要为这个项目写文档。先不要动笔，先出方案。

## 先读

- 代码库结构、README、入口、配置、数据模型、核心链路、测试。
- 现有的项目文档（如果有）：知道哪些要重写、哪些要新增、哪些不动。
- `.agents/skills/doc-writing/SKILL.md` 和 `references/project-model.md`。

## 方案要回答

1. **写几篇**：总数，以及为什么是这个数。不要默认「全部重写」，也不要默认「只写一篇」。
2. **写哪几篇**：每篇的文件名、标题、一句话目的、读者、和现有文档的关系（新增 / 重写 / 合并 / 删除）。**篇目和标题不要沿用旧文档的目录**；旧文档只提供事实。
3. **每篇的框架**：二级标题清单（3–8 个），每个标题一句话说明这一节讲什么。每个标题先想清楚“读者读完这一节能回答什么问题”。
4. **图**：哪几篇需要图、每张图要表达什么、用哪种图型（C4 Container / UML sequence / UML state machine / activity + swimlane / ER / decision tree）、画布宽与最小字号（默认 700px / 14px）、导出 PNG 2x 还是 SVG、每张图的预估体积。讲流程或结构的篇目至少一张；全套通常 8–14 张。**表格能说清的内容不画。**
5. **术语与前置知识**：列出项目内的类名、表名、变量名、实例 id、配置键，标出每个词第一次定义的位置；哪些通用知识可以假设（HTTP、JSON），哪些不能（项目里的 `kb_dense`、`preset`、`ScopedTaskStore`）。导读先术语表，再讲链路。
6. **顺序与依赖**：先写哪篇、后写哪篇、哪篇定调。
7. **不写什么**：明确排除的内容，避免用户以为你会覆盖全部。
8. **风险**：哪些事实需要用户确认、哪些旧文档可能和代码冲突。
9. **试写**：附一段 300 字左右的样稿，让用户先确认声音和密度，再开始整篇。

## 规则

- 方案控制在 1 页左右，不要写成文档。
- 标题可以带编号；正文不写点不动的编号引用（`§7`、`第 7 节`）。要指某一节，写篇名加小节标题（`《检索与问答》的「降级清单」`），或给可点击的跳转链接。
- 表格只放可对照的数据与取值；机制、因果、代价放正文，不要塞进单元格。
- 图的标准见 `references/diagrams.md`；画布 >700px、最小字号 <14px、或把表格画成盒子的方案不通过。
- 术语表放在导读的链路之前；后面的页面第一次用到项目内名词时链接回导读。方案里没列术语表的，不通过。
- 用户明确同意之前，不要写正文、不要改 `docs/`。
- 用户改动方案后，更新方案再确认，不要直接按自己的理解开写。
