## 逐段过五个问题

1. **这一段最后一句是不是在替读者下结论？**
   「这条约束比……重要」「这不是 bug」「这是明说的取舍」「这才是真正的坑」——整句删。
   删完读者仍能得出同样的结论，就证明它本来就多余。

2. **有没有「等于 / 就是 / 相当于」把实现换算成比喻？**
   换成函数名、字段名、分支条件、哪个测试。写不出具体实现，说明这个比喻在替一个没查清的事实打掩护。

3. **后果是不是写成了画面？**
   「别人看到不属于自己的照片」「承诺没人能兑现」「全盘皆输」——换成可查的证据：哪个接口返回了什么、`skipped` 里写了什么字符串、哪条日志、哪个 issue 编号。
   参考 `exemplars/reference/01-logging.md` 里那句 `Loguru #548`、`WinError 32`。

4. **这一段有没有一条只有作者知道的事实？**
   实测数字、报错原文、某次线上事故的形状、试错最后定下的那条约束。
   有就留着并突出它；没有就补——补事实要回到代码或旧文档，标 `file:line`。
   补不出来，把这一段压成一张表或三行命令。**宁可短，不要用形容词撑。**
   注意：要的是**约束**，不是**时间线**。"早期是 A，后来改成 B"属于下一节。

5. **该有立场的地方，写的是决定还是评价？**
   「我们没把过滤下推到 8020」是决定；「这条约束比省一次往返重要」是评价。
   一律改成决定，并写明当时的条件。不同意某个方案就直说不同意，不要把反对写成「值得权衡」。

## 删时间线

「早期实现是 A，后来改成 B，改完的表现是 C」这类沿革，只在这三种情况下留：

1. 它解释了**当前数据为什么长这样**（同名 current 可能不止一个，所以版本号要取 max）；
2. 它是**可复现的证据**：报错原文、实测数字、某次事故的形状（不是"当时报错了"）；
3. 它是**待办欠账**（旧文档要 `reparse`、旧点没有新字段）。

其余一律删，只留「现在必须怎么做 + 为什么不能那样做」。

反例（真实改写前，多租户文档讲 Key 哈希）：

> 早期实现只存 sha256 的前 12 个 hex（48 bit），理由写的是"Key 本身是 256 位随机数，没有低熵可爆破"——那句话只对离线成立。在线要猜的是哈希前缀，成本从 2^256 降到 2^48，一块 GPU 大约 8 小时。改成 64 位之后，旧 Key 全部失效，表现是被登出一次。

改后：

> Key 只存完整 64 位 hex。截短没有意义：Key 本身是 256 位随机数，离线确实没有低熵可爆破，但**在线要猜的是哈希前缀**。只存 12 个 hex（48 bit）时，猜中成本从 2^256 降到 2^48，一块 GPU 大约 8 小时。

删掉的是「改成 64 位之后旧 Key 全部失效、表现是被登出一次」。那是迁移记录：读者既不需要知道，也不该以为这是一条要遵守的规则。保留下来的「必须完整长度」与「2^48」才是约束。

机械扫描可以在 `scripts/check_voice.py` 里看「历史沿革候选」，命中不等于要删，回原文按上面三条判。

- 判断句式、口号式、比喻式的标题，改成名词短语：`降级是一等公民` → `检索腿的降级`；`两个过滤入口，不是四个` → `过滤入口`。
