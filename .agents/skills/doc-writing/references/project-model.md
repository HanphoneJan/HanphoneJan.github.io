# 项目模型模板

写文档前，先把这个表填完。填不出来的，说明代码还没读够。

输出位置：`/tmp/doc-writer/<project>/brief.md`，或项目根下 `.doc-drafts/brief.md`（gitignore）。不要提交进仓库。

## 必答问题

1. 这个项目一句话是什么？边界在哪（不做什么）？
2. 有哪几个进程/服务？各自监听什么端口？谁常驻、谁轮询？
3. 数据以哪一份为准？哪些是可重建的派生数据？
4. 一次写入/上传，从入口到落库经过哪些步骤？
5. 一次读取/检索/查询，经过哪些步骤？失败时怎么降级？
6. 模块怎么分？每个目录的职责和入口文件是什么？
7. 权限/租户从哪里来？过滤条件在几处构造？为什么不能多一处？
8. 任务/队列的状态机是什么？怎么领取、重试、结算？
9. 对外有哪几种入口（HTTP / RPC / CLI / MCP / A2A）？共用哪套内核？
10. 测试分几层？哪些是结构守卫？哪些需要真实依赖？
11. 怎么部署、怎么巡检、怎么备份恢复？
12. 术语表：中英对照，一篇一个叫法的在这里定死。
13. 关键数字清单：数字、含义、出处（`file:line` 或源文档）。
14. 旧文档与代码的冲突：旧说法、代码证据、以哪个为准。

## 写法

每节先写事实，再写出处；不要写「本文」「总之」。

```markdown
## 进程与端口

| 进程 | 端口 | 职责 | 常驻 |
|---|---|---|---|
| api | 8010 | HTTP、SSE、静态站点 | 是 |
| worker | 无 | 轮询任务、摄取、清理 | 是 |
| visual | 8020 | 只做编码 | 是 |

出处：`services/api/main.py:132-154`、`services/common/config.py:29-65`
```

## 关键数字清单

| 数字 | 含义 | 出处 |
|---|---|---|
| 82 / 81 / 1 | 契约声明 / 实现 / 明确不做 | `eval/contract_check.py` 实跑 |
| 1335 | pytest 收集数 | `pytest --collect-only -q` |
| 15 分钟 | 任务租约 | `services/common/jobs.py:51-55` |

数字必须能复算。不能复算的标 `measured`，不要伪装成代码事实。

## 冲突记录

| 旧说法 | 代码证据 | 结论 |
|---|---|---|
| 租约 5 分钟 | `jobs.py:51-55` 是 15 分钟 | 写 15 分钟 + 心跳 |

## 每篇的必写事实

给每篇文档列 5–10 条必须出现的事实（数字、路径、结论），写作时逐条对照。这是防止改写丢信息最有效的一步。
