# 核对

改写稿必须过两关：机械核对、代码核对。两关都过，才允许写回 `docs/`。

## 1. 机械核对

```bash
python3 .agents/skills/doc-writing/scripts/check_rewrite.py <原文> <改写稿>
python3 .agents/skills/doc-writing/scripts/check_rewrite.py --dir <原文目录> <改写目录>
# 旧文复用红线（可选）：连续 12 字以上的重合超过 10% 就失败
python3 .agents/skills/doc-writing/scripts/check_rewrite.py --max-overlap 0.10 <原文> <改写稿>
```

检查项：

- 数字：原文出现、改写稿没有 → 失败（标题编号除外）。
- 行内代码：代码路径、表名、函数名、错误码丢失 → 失败。
- 链接：站内/站外链接目标丢失 → 失败。
- 标题数、代码块数、表格行数：只报告。改写允许把叙述性表格改成句子，表格行减少是正常的；数据要在正文里找得到。
- **旧文重合**：报告连续 12 字以上的正文片段占比。它不是越低越好（事实、术语、数字必须保留），但超过 20% 通常说明还在改旧句子；**超过 30% 直接按新提纲重写**，不要逐句替换。

机械通过不代表事实对，只代表没丢东西。

## 1.1 图的核对

```bash
python3 .agents/skills/doc-writing/scripts/check_diagrams.py static/img/<project>/src
# 或整站
python3 .agents/skills/doc-writing/scripts/check_diagrams.py static/img
```

检查项：

- `.drawio` 的 `pageWidth > 700`：画布超宽，正文栏里会缩到一半以下。
- 有文字的节点/边标签 `fontSize < 14`，或没有显式字号（draw.io 默认 12）：字太小。
- 对应 PNG 缺失、体积 >150KB、宽度不是约 2 倍画布：没导出、太大或不是 2x。
- PNG 比 `.drawio` 旧：导出后忘了重新生成（只警告，git checkout 的 mtime 不可靠）。

机械检查只量尺寸，不量语义。再人工看：

1. 在正文宽度（约 673px）下不点开也能读；100% 与 150% 都不裁切。
2. 箭头方向对，连线没有穿过文字；跨泳道的边从边界进出。
3. 图例只解释这张图用到的颜色；没有与图无关的图例。
4. 暗色主题下能读。
5. 表结构、状态机、时序图的语义对：不把表格画成盒子，不画不可达状态，不让返回路径经过不相关的组件。
6. 正文里的“下图”和图对得上，每张图有 alt 文本。
7. 单张 ≤150KB；整篇的图加起来不超过约 500KB。

## 2. 代码核对

逐条核对事实性断言，代码是唯一裁判：

- 数字、默认值、端口、模型名、维度、阈值。
- 行为：谁调用谁、失败怎么处理、状态怎么变。
- 边界：哪些事不做、哪些开关默认关闭。
- 测试名与它守的约束。

方法：`rg` 找证据，记录 `file:line`。不要凭印象，也不要拿旧文档当证据。

没有旧稿时没有可比对象，就把全文的数字与 `file:line` 回查一遍：文件在、行号在范围内、那一行确实是这个值。指到同名常量或注释里的旧数字，是这类核对最常抓到的错。

判定三类：

| 判定 | 处理 |
|---|---|
| 代码能确认 | 按代码写 |
| 代码与草稿冲突 | 改草稿，并在文末自查注释里标 `file:line` |
| 代码无法确认（实测性能、部署规格、历史事故） | 保留原说法，标 `measured` |

## 2.5 读者模型检查

把稿子当成第一次接触这个项目的人来读。逐项过：

1. **项目内名词有没有裸用。** 列出所有反引号里的类名、表名、变量名、实例 id、配置键，确认第一次出现有解释或链接。没有就补。读者不知道 `kb_dense`、`ScopedTaskStore`、`preset` 是什么，除非前文刚解释过。
2. **通用词只解释一次。** A2A、JSON-RPC、SSE、AgentCard 第一次出现展开一次；HTTP、JSON 这类不解释。
3. **术语表在链路之前。** 导读先给术语表，再讲“一次任务经过哪些部件”；后面的页面第一次用到术语时链接回导读，不要在后面才定义前面已经用过的词。
4. **每节接得上。** 每一节的第一句能接上一节的问题，不是孤立的条目。页面开头写“读这页之前要知道什么”，结尾写“接下来读哪篇”。
5. **同一概念一个叫法。** 换叫法要在术语表里写“也叫……”，正文不要混用。

先跑一遍列出首次出现：

```bash
python3 .agents/skills/doc-writing/scripts/list_terms.py docs/项目/<name>
```

它只列每个反引号术语在每篇里的第一次出现与上下文，**不判断对错**。拿它当清单逐条看。

## 3. 统计口径的坑

有些数字不是「代码里写死的」，而是随统计方式变化：

- **巡检项数**：注册了几个检查函数、每个函数 add 几条、报告里实际几项，可能不是同一个数。写「十二个检查函数，报告通常十四项」比写死一个数字稳。
- **测试用例数**：`pytest --collect-only` 会随测试增删变化。写「约 450 项」或「四百多项」，不要写死。
- **端点数量**：以契约检查脚本的实跑输出为准，不要数装饰器。

凡是「数出来」的数字，注明统计方式和日期。

## 4. 人工复核

机械和代码都过不了「读起来像不像」这一关。最后至少抽三段朗读：

- 开头有没有把读者带进问题。
- 中间有没有具体例子/数字/图。
- 结尾有没有拔高或总结腔。

## 5. 应用

1. 去掉文末那段自查注释（它是工作记录，不进正文）。
2. 写回 `docs/`。
3. 跑项目自己的构建/检查（如 `pnpm build`、`pnpm check:docs`）。
4. 构建失败就回滚，不要带着坏链接提交。
