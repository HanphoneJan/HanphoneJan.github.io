# 核对

改写稿必须过两关：机械核对、代码核对。两关都过，才允许写回 `docs/`。

## 1. 机械核对

```bash
python3 .agents/skills/doc-writing/scripts/check_rewrite.py <原文> <改写稿>
python3 .agents/skills/doc-writing/scripts/check_rewrite.py --dir <原文目录> <改写目录>
# 旧文复用红线（可选）：连续 12 字以上的重合超过 10% 就失败
python3 .agents/skills/doc-writing/scripts/check_rewrite.py --max-overlap 0.10 <原文> <改写稿>
```

检查项：

- 数字：原文出现、改写稿没有 → 失败（标题编号除外）。
- 行内代码：代码路径、表名、函数名、错误码丢失 → 失败。
- 链接：站内/站外链接目标丢失 → 失败。
- 标题数、代码块数、表格行数：只报告。改写允许把叙述性表格改成句子，表格行减少是正常的；数据要在正文里找得到。
- **旧文重合**：报告连续 12 字以上的正文片段占比。它不是越低越好（事实、术语、数字必须保留），但超过 20% 通常说明还在改旧句子；**超过 30% 直接按新提纲重写**，不要逐句替换。

机械通过不代表事实对，只代表没丢东西。

## 1.1 图的核对

```bash
grep -o '<image' static/diagrams/<slug>.svg | wc -l   # 中文标签被栅格化的信号（按次数，grep -c 会少报）
ls -lh static/diagrams/<slug>.svg
```

单张图超过 150 KB、或 SVG 里含大量 `<image>`，就改导 PNG 2x 或拆图。页面加载慢通常不是“图多”，而是每张“SVG”里塞了十几张位图。

## 2. 代码核对

逐条核对事实性断言，代码是唯一裁判：

- 数字、默认值、端口、模型名、维度、阈值。
- 行为：谁调用谁、失败怎么处理、状态怎么变。
- 边界：哪些事不做、哪些开关默认关闭。
- 测试名与它守的约束。

方法：`rg` 找证据，记录 `file:line`。不要凭印象，也不要拿旧文档当证据。

没有旧稿时没有可比对象，就把全文的数字与 `file:line` 回查一遍：文件在、行号在范围内、那一行确实是这个值。指到同名常量或注释里的旧数字，是这类核对最常抓到的错。

判定三类：

| 判定 | 处理 |
|---|---|
| 代码能确认 | 按代码写 |
| 代码与草稿冲突 | 改草稿，并在文末自查注释里标 `file:line` |
| 代码无法确认（实测性能、部署规格、历史事故） | 保留原说法，标 `measured` |

## 3. 统计口径的坑

有些数字不是「代码里写死的」，而是随统计方式变化：

- **巡检项数**：注册了几个检查函数、每个函数 add 几条、报告里实际几项，可能不是同一个数。写「十二个检查函数，报告通常十四项」比写死一个数字稳。
- **测试用例数**：`pytest --collect-only` 会随测试增删变化。写「约 450 项」或「四百多项」，不要写死。
- **端点数量**：以契约检查脚本的实跑输出为准，不要数装饰器。

凡是「数出来」的数字，注明统计方式和日期。

## 4. 人工复核

机械和代码都过不了「读起来像不像」这一关。最后至少抽三段朗读：

- 开头有没有把读者带进问题。
- 中间有没有具体例子/数字/图。
- 结尾有没有拔高或总结腔。

## 5. 应用

1. 去掉文末那段自查注释（它是工作记录，不进正文）。
2. 写回 `docs/`。
3. 跑项目自己的构建/检查（如 `pnpm build`、`pnpm check:docs`）。
4. 构建失败就回滚，不要带着坏链接提交。
