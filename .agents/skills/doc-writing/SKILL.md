# 项目文档写作：单 writer，先懂项目，再动笔

## 适用

- 给一个已有代码库写项目文档，或重写旧文档。
- 文档可以是一篇，也可以是一组；**写多少篇、写哪几篇由 writer 根据项目决定**，不预设数量，但必须先给用户方案并得到同意。
- 需要术语、架构、声音跨文档一致时，这套方法比逐篇派 agent 更稳。

## 三条原则

1. **一个项目一个 writer。** 同一个 agent 通读代码、建立项目模型，再决定写哪几篇。术语和判断由同一个上下文保证，不靠事后统一。
2. **事实以代码为准。** 旧文档只是线索。代码与旧文档冲突时按代码写，并在文末自查注释里标 `file:line`。测量值、部署规格这类代码里没有的，保留原说法并标 `measured`。
   **旧文档只做事实清单，不做行文模板。** 开始写之前，先从旧文档抄出数字、路径、结论，然后关掉它；初稿写完再拿它查漏。不要沿用它的章节顺序、标题层级、段落节奏和句子。连续 12 个汉字与旧文相同，就当作复用，重写。
3. **风格靠范文，不靠规则。** 提示词只留两类约束：只用事实、不写元话语。其余交给 `exemplars/` 里的范文。规则写多了，模型会逐条应试，文字反而变平。
   **范文按文体分组，先选文体再动笔**（`reference/` 参考手册、`reasoning/` 机制与取舍、`tutorial/` 教程）。写项目文档时只读 `reference/` 与 `reasoning/`；`tutorial/` 的问答体一旦被当成通用范文，写出来的设计文档会通篇是判断句和短句断言。换文体就换范文组，提示词不动。

## 流程

### 1. 建项目模型（最重要的一步）

先读，不要写：

- 代码库根目录的 README、`docs/`、`pyproject.toml` / `package.json`。
- 入口与进程：`main.py`、路由注册、worker、独立服务。
- 配置：`config.py`、`.env.example`、端口、开关。
- 数据模型：ORM 表、迁移、向量集合。
- 核心链路：一次读取/写入/检索/任务，从入口追到落库。
- 测试：`tests/`、`eval/`、CI 脚本；测试名往往就是约束。
- 旧文档：只提取**事实清单**（数字、路径、结论、失败模式），不要记它的章节顺序、标题层级和句式。写作时把它关掉。

产出 **项目模型**，写到临时目录，不要写进仓库：

- 默认 `/tmp/doc-writer/<project>/brief.md`。
- 或项目根下 `.doc-drafts/`（记得 gitignore）。
- 模板与必答问题见 `references/project-model.md`。

**如果用户要求“完全删除旧文档”：** 先删工作区里的旧稿、staging 和 `/tmp` 备份，再从代码重建事实。不要用 `git log` / `git show` 把旧文找回来；契约文件（如 `DESIGN-API.md`）可以保留，但它只提供端点形状，不提供行文。删完直接告诉用户“旧稿已从工作区移除，事实只从代码重建”。

模型至少要能回答：几个进程/端口、三条主链路、模块职责、数据以哪份为准、权限怎么过滤、任务状态机、测试分层、部署与巡检、术语表、关键数字及其出处。

### 2. 出方案，等用户确认

不要直接开写。writer 先决定这四件事，写成 1 页方案：

1. 写几篇、写哪几篇、每篇的目的是什么；
2. 每篇的二级标题框架（3–8 个）；
3. 哪几篇需要图、每张图表达什么、用 draw.io 的哪种形态（流程/时序/状态/泳道/结构）、导出 PNG 2x 还是 SVG、每张图的预估体积；
4. 写作顺序，以及哪些旧文档不动。再附一段 300 字试写，让用户先听声音。

把方案汇报给用户，**用户明确同意后再动笔**。用户改方案就更新方案再确认，不要按自己的理解开写。

方案模板：`prompts/plan.md`。

每篇的章节结构由内容和项目决定，不套统一模板。

### 3. 写

- 先按文体读范文：写架构说明、设计文档、运维/踩坑记录，读 `exemplars/reference/` 与 `exemplars/reasoning/`；只有写教程/面试向内容才读 `exemplars/tutorial/`。`reference/` 不够时，读本仓库 `docs/项目/数据分析平台/` 与 `docs/项目/图像检索系统/` 的文档看完整形态（只学行文，不搬事实）。再读 `prompts/new-section.md` 或 `prompts/rewrite-section.md`。
- **整篇重写，不在旧句子上打补丁。** 保留事实、数字、代码路径，**章节顺序和标题层级可以完全重来**。先按自己的提纲写，初稿完成后再拿旧文档查漏。
- 一次一篇，写到临时 staging 目录（默认 `/tmp/doc-writer/<project>/stage/`），**不要直接改 `docs/`**。
- 每篇写完，在文末留一段注释：关键数字与它们的出处（`file:line`），自查用；交付前删掉。

没有旧稿时，第 1 条不适用：事实全从代码来，写完把数字与路径回查一遍（见 `references/verification.md`）。

### 3.4 连贯性

连贯性不靠逐条规则。写之前读范文，写完对照范文朗读：如果读起来像条目说明、像在填表、每段都能单独抽出来贴到别处，就重写。不要用“首先/其次/最后”把段落缝起来，回到具体问题、因果和代价上。判断标准是读者能不能顺着上一句读下一句，而不是命中了几条清单。

五篇教程体范文覆盖讲解、排障、选型三种文体。它们的标题形态各不相同——问句、对象名、症状句都有——学的是怎么切进去、怎么摆数字和代价，不是照抄结构。**但教程体只是 `exemplars/` 里的一个分组**：写项目文档时读 `reference/` 和 `reasoning/`，它们的标题是名词短语、信息靠表格与目录树承载。都不像这次的文体时，另拿用户认可的一篇成品当范文，并指出它属于哪一组。

### 3.5 图

写完后统一处理图，不要边写边画：

- **每个主链路、状态机、数据模型、部署形态、权限判定至少一张图。** 一篇讲流程的文章只有一张“方框+箭头”通常不够；把“入口与进程边界”“状态迁移”“删除/失败路径”拆成不同的图。
- 用 draw.io 的完整能力，不要只摆矩形：泳道分进程/角色，container 分组，实线画主路径、虚线画可选/降级/异步，编号标步骤，图例说明颜色与线型，note 写边界条件。
- 一张图只表达一件事。表达两件事就拆两张；宁可多一张小图，不要一张信息过载的大图。
- 源文件放 `static/diagrams/src/<slug>.drawio`，导出到 `static/diagrams/<slug>.svg` 或 `.png`，正文用 `![图注](/diagrams/<slug>.svg)`。没有 `static/` 的项目放 `docs/diagrams/`，在方案里写明。
- **中文标签默认 PNG 2x。** draw.io 导中文常把字栅格化成 `<image>`，一个“SVG”可能 200–400 KB。拿 3 个节点的小图导一次探针，`grep -o '<image' | wc -l` 非 0 就整批用 PNG 2x（`--scale 2`）；含 `<image>` 或超过 150 KB 就拆图。目标是每张图 ≤150 KB。
- 导出：`bash .agents/skills/doc-writing/scripts/export_drawio.sh --format svg`（或 `png`）。
- 每个「下图」必须有图；没有就删句子。不用 Mermaid。
- 完整约定（命名、暗色模式、diagram brief、最小模板、体积检查）见 `references/diagrams.md`。

### 3.6 去 AI 味（独立一遍，只做减法）

初稿写完、图处理完，再单独过一遍 `prompts/de-ai-pass.md`。这一遍**不加风格，只删、只换、只缩**：删替读者下结论的句子，把「等于」换成实现事实，把画面化后果换成可查证据，补一条只有作者知道的事实，把评价改成决定。

- **必须由同一个 writer 做**，不要外包给评审 agent。判断「这句话背后有没有事实」需要写它的人知道代码里有什么。
- **这一遍不新增事实**。要补的事实回到代码或旧文档，标 `file:line`；补不出来就把那段压成表格或命令。
- **不要试图把文档写成「像人写的」**。目标是「像一份参考手册，外加一处当时的决定」。追「像人」会让模型去伪造口语、感叹和跳跃，那是另一种假。

指标只做对照，不做验收：

```bash
python3 .agents/skills/doc-writing/scripts/check_voice.py <稿子或目录>
```

它打印分号密度、引号口语、破折号、加粗，和 `exemplars/reference/` 的基线并列，再列出判决句候选的行号与原文。**没有通过线，退出码恒为 0。** 分号密度最可信：一个分号串两个论点、第二个论点是升华，是演讲腔最稳的指纹。引号口语会误伤（引用术语也算），命中要回原文看。

### 4. 核对

```bash
python3 .agents/skills/doc-writing/scripts/check_rewrite.py <原文> <改写稿>
# 或整批
python3 .agents/skills/doc-writing/scripts/check_rewrite.py --dir <原文目录> <改写目录>
```

机械检查只看数字、行内代码、链接是否丢；标题/表格/代码块数量只报告。机械通过后再做代码核对，见 `references/verification.md`。

### 5. 应用

通过后，去掉文末那段自查注释，再把文件写回**本仓库**的 `docs/`；跑一次项目自己的构建/检查命令。失败就回滚，不要带着坏链接上线。

文档写在本仓库，不要写进被写文档的那个项目仓库；要同步过去，等用户明确同意后单独做。

## 硬规则

**必须保留**

- 数字、代码路径、表名、错误码、环境变量、命令、实测数据、链接。
- 表格里的数据；能改成句子的改写，数据进正文。
- ASCII 图在写作阶段原样保留；成稿前统一转成 draw.io，见 `references/diagrams.md`。
- 结论强度：可能、通常、大约、默认、在……情况下。

**可以改**

- 标题文字，去编号。
- 拆段、并段、改句式、用「你/我」、关键结论和数字加粗。
- 删「本文」「本节」「这里不重复」「详见」。
- **删判决句**：替读者下的结论（「这条约束比……重要」「这不是 bug」「这是明说的取舍」）。删完读者仍能得出同样的结论，就说明它本来就多余。
- **把评价改成决定**：「我们没把过滤下推到 8020」是决定，「这条约束比省一次往返重要」是评价。决定要留，评价不要。

**不可以**

- 删节、删事实、新增事实、改数字、改代码路径、改结论强度。
- **升级结论强度**（改写时最常见的走形）：把「可能/通常/大约」改成「必然/迟早/唯一/永远/极难」，或把一个失败案例写成普遍规律。降级同样要有依据，不能为了让句子显得克制就抽掉原文的断言。
- 加原文没有的例子、类比、场景细节。
- 用「等于 / 相当于 / 就是」把实现换算成比喻。写不出具体函数、字段或分支，说明那个比喻在替一个没查清的事实打掩护。
- 改写时扩写或压缩超过 ±20%。
- 用 Mermaid 代替原有的 ASCII 图。
- **复用旧文档的句子或段落结构。** 连续 12 个汉字相同即视为复用；旧文档只能提供事实，不能提供行文。

## 不要做

- 不要按篇拆给多个 agent 再统一。那样每篇都要重新建立上下文，术语和判断必然漂。
- 别把核对全押到最后，也别每篇都停下来等确认：一篇一核对最省返工；被要求一次写完时，最后统一过一遍引用与构建。
- 不要用检查器分数当验收标准。它量的是机械丢失，不是声音。
- 不要把去 AI 味做成风格规则清单。规则清单会让模型逐条应试，写出第二种僵硬；减法 pass 只做删、换、缩。
- 不要拿教程体范文写设计文档。`tutorial/` 学来的是判断句和短句断言，正好是演讲腔的来源。
- 不要把项目模型提交进仓库；它是工作底稿。
