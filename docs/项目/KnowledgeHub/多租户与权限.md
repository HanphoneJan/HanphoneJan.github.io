# 多租户与权限

一次请求的权限范围由 API Key 在服务端推导出，落在一个 `UserContext` 上下文对象里。所有过滤函数只消费 `readable_kb_ids`，不再各自计算可见性——这一章讲推导、三档可见性、四个过滤函数，以及判定拿不到范围时的 fail-closed。

![Key、上下文与四个过滤函数的判定路径](/img/knowledge-hub/tenancy-decision.png)

## 1. API Key 与 UserContext

每个请求带 `Authorization: Bearer sk-pkh_...`。`common/deps.py::get_current_user` 解析后交给 `load_user_context`，路由代码不接触授权头。

```python
plaintext = f"sk-pkh_{secrets.token_urlsafe(32)}"
hash_key(plaintext)     # sha256 完整 64 位 hex，存 api_keys.key_hash
```

两点存储设计需要区分开：

- Key 本身是 256 位随机数，用 sha256 哈希存储即可（argon2 只给用户密码用，那才是低熵可爆破的场景）。
- 哈希存完整 64 位 hex，截短没有意义。Key 是高熵随机数，离线爆破 2^256 没有意义，但在线要猜的是哈希前缀——D134 曾发现截短到 48 bit（12 hex）时，猜中成本从 2^256 降到 2^48，一块 GPU 约 8 小时。

服务端按顺序做五件事：

1. 用完整 SHA-256 查 `api_keys.key_hash`，要求 `revoked_at IS NULL` 且用户 `is_active`。
2. 判 Key 自己的 `expires_at`。
3. 从用户行读全局角色（`superadmin` 与否）。
4. 查 `workspace_members` 拿我加入的工作区。
5. 用读侧可见性条件查出所有可读 KB，折叠成 `readable_kb_ids`。

结果装进 frozen dataclass `UserContext`：

| 字段 | 来源 |
|---|---|
| `user_id` / `email` / `display_name` | `users` 行 |
| `api_key_id` / `scopes` | `api_keys` 行 |
| `workspace_ids` | `workspace_members` |
| `readable_kb_ids` | 可见性条件算出的 KB id 集合 |
| `is_superadmin` / `nickname` | `users.role` / `users.nickname` |

任一步失败一律 `INVALID_TOKEN`，不区分「不存在 / 已吊销 / 已过期 / 用户停用」——错误码不做存在性探测信号。

`api_key.last_used_at` 由请求成功时的会话 `commit()` 落库。失败请求走 rollback，不会留下时间。它的语义是「最后一次成功使用」。

## 2. 三档可见性

| visibility | 谁能读 | 谁能写 |
|---|---|---|
| `private` | 创建者 | 创建者 |
| `workspace` | 该工作区成员 **或** 创建者 | 只有该工作区成员 |
| `global` | 所有用户 | 所有用户 |

读写判定差一格：一个 `workspace` 库的创建者若已退出工作区，他读得到（读判定里 `created_by == 我` 是一条独立的 or 分支），但改不了（写判定按 visibility 分派，不看 `created_by`）。

这一格的边界要写实：回收站列表如果错按读判据筛，会出现「列表里能看到、点恢复 403」。

`global` 可读可写是小团队部署的取舍。若对外开放，这是最先被攻击的点。所有判定收在 `services/common/auth.py` 一个文件里，将来接 RBAC 只改那几处。

## 3. 四个过滤函数

| 函数 | 服务对象 | 用在哪 |
|---|---|---|
| `build_qdrant_filter` | Qdrant | dense / sparse / visual 三腿 |
| `build_kb_scope_sql` | Postgres | trgm 子串腿 |
| `visible_kb_clause` | Postgres | KB 列表、`load_user_context` |
| `writable_kb_clause` | Postgres | KB 回收站列表 |

四个函数都只读 `ctx.readable_kb_ids`（或同一组 `(user_id, workspace_ids)` 零件），不各自重算三档。Qdrant 与 SQL 的过滤入口分开，是因为 trgm 腿跑在 Postgres 里，拿不到 Qdrant 的过滤字典。如果 `trgm.py` 自己 join 复刻可见性，就是第二个判定入口。

读与写的列表条件也分开，因为 §2 那一格差异。`can_write_kb` 的行版本与 `writable_kb_clause` 的 SQL 版本必须逐档等价，`tests/test_container_trash.py` 在真实 PG 上逐格比对。

三档写错只有两种典型写法：

```python
# 错误一：workspace 与 global 合并成 IN，所有工作区的库任何用户可见
visibility.in_(("workspace", "global"))

# 错误二：成员资格作为独立 or 分支，可见性限定完全失效
or_(visibility == "workspace", workspace_id.in_(my_ws))
```

正确写法是 workspace 分支的两个条件放进同一个 `and_`。

## 4. fail-closed 与同码

拿不到授权范围时，过滤条件必须退化成恒假，而不是不过滤：

```python
{"must": [{"key": "kb_id", "match": {"value": -1}}]}   # Qdrant 侧
col == NO_SUCH_KB                                       # SQL 侧，NO_SUCH_KB = -1
```

-1 是一个从 KB id 序列中不可能出现的值（id 从 1 开始递增）。

跨库请求里的 `kb_ids` 只是**意图**，实际范围是交集：

```python
want = allowed if kb_ids is None else (allowed & set(kb_ids))
```

交集只会更小，所以带一个无权限的 `kb_id` 进来不会越权，只会少结果。传空数组返回 400（明确指向「传 null 表示全部有权限的库」）。交集为空返回空结果、不报错——报错会泄漏「这些 id 里至少有一个存在」。

资源级失败统一走到 `ResourceNotFound`：

| 情况 | 表现 |
|---|---|
| HTTP：KB 或文档不存在、无读权限、无写权限 | 403 + `KB_NOT_FOUND` |
| MCP：库不存在或无权限 | `result.isError=true` + `{"error":"KB_NOT_FOUND"}` |
| MCP：文档不在这个库 | `result.isError=true` + `{"error":"DOC_NOT_FOUND"}` |
| 操作级拒绝（非超管调管理端点） | 403 + `FORBIDDEN` |

前三行是 fail-closed 的核心：调用方不能通过错误码差异推断资源是否存在。`FORBIDDEN` 只给「这个操作被禁止」这一操作级语义，没有资源存在性可言。（`errors.py` 里另有 `DocNotFound` 类，HTTP 路由不使用它，文档级失败同样走 `KB_NOT_FOUND`。）

MCP 与 A2A 同样遵守：一个库都没有时，MCP 不暴露 `search_kb` / `ask_kb` / `get_document`，A2A Agent Card 的 `readableKbCount` 为 0。先返回全部工具、调用时再拒绝，等于给调用方一条探测路径。

## 5. 工作区软删的连锁

`DELETE /workspaces/{id}` 只标记工作区一行，不级联软删其下的库与文档。恢复因此只有一行操作。代价是「删掉的工作区下的库」在所有判定里必须真的不可见——做法是可见性判定上加一条：

```python
and_(or_(三档条件), _workspace_alive(model))
```

这个 `EXISTS` 子查询有两个写错形态，都真实发生过：

1. **写成第四条 or 分支**：`or_(三档, EXISTS)` 会让只要存在任意一个未软删的工作区，所有行的 `EXISTS` 都为真，三档判定里的 `workspace` 分支照样命中。
2. **子查询未 `correlate(model)`**：直接 `exists().where(ws.id == model.workspace_id, ...)` 渲染出的是 `EXISTS (SELECT * FROM workspaces, knowledge_bases WHERE ...)`——子查询自己带了一张 `knowledge_bases`，与外层行无关。

两次错误的表现相同：判据看起来在运行、实际什么都没挡住，pytest 全绿，只能靠真库探测发现。连带约束：工作区还软删着时，它的库既搜不到也恢复不了，`GET /kb/trash` 与 `POST /kb/{id}/restore` 都要求先恢复工作区。

## 6. 邀请码、超管与操作级拒绝

邀请码把「邀请一个还没注册的人」变成自服务：owner 生成一段码，对方注册后自己输码加入工作区。

| 项 | 值 |
|---|---|
| 字符集 | 31 个；去掉 `0 O 1 l I` 这类手抄会混的字符 |
| 长度 | 8 |
| 默认有效期 | 7 天 |
| 默认可用次数 | 1，上限 50 |
| 存库 | HMAC-SHA256 + 每码盐，另存 4 位前缀供识别 |
| 授予角色 | 仅 `member` |

兑换失败时，过期、用完、已撤销、码不存在四种情况回同一句：

```
邀请码无效（可能已过期、已被使用，或已被撤销）
```

区分开这四种，就给了攻击者一个「这个码存在但已失效」的探测信号，所以共用一句。

超管 `users.role='superadmin'` 越过三档可见性的实现是**展开上下文**，不是在过滤器里加分支：

```python
workspace_ids = 所有工作区
readable_kb_ids = 所有未软删的库
```

它仍然从用户行经 API Key 推导，请求体里的任何字段都不能抢先赋予这个角色。

## 7. 守卫与边界

| 守卫 | 守什么 |
|---|---|
| `tests/test_permissions.py` | 三档分别判定的真值表；workspace 分支必须带成员资格；private 不能被同工作区成员读到 |
| `tests/test_container_trash.py` | `can_write_kb` 行版本与 `writable_kb_clause` SQL 版逐格等价；`visibility == 'global'` 字面量只允许出现在 `auth.py` |
| `tests/test_qdrant_filter_scope.py` | Qdrant 过滤字典只允许 `kb_id` 一个 key；`services/` 下没有用 `visibility` / `workspace_id` / `source_kind` / `owner_id` 做 key 的过滤 |
| `tests/test_retrieval_filters.py` | AST 扫描：检索层不出现可见性判定；每条查 Qdrant 的腿传的都是 `build_qdrant_filter` 的产物 |

第三条守的具体形状：Qdrant payload 里的 `visibility` 是摄取时写死的字段值，改库可见性不会回写。有人按它过滤，陈旧值立刻造成越权。

 明确不做的四条：不做细粒度 RBAC（scope 目前只有 `kb:read` / `chat:read` 这类粗粒度门禁）。不把租户字段放进请求体（`kb_ids` 是检索范围意图，不是身份）。不靠前端隐藏按钮（前端不显示的，后端仍然要判）。不在日志里打完整 API Key 或审计原文。
