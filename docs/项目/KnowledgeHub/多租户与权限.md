# 多租户与权限

> **阅读目标**: 一次请求的权限范围从哪来、三档可见性差在哪一格、拿不到范围时为什么必须判成恒假。

---

## 1. API Key 推出上下文

每个请求带 `Authorization: Bearer sk-pkh_...`。`common/deps.py::get_current_user` 解析后交给 `load_user_context`，路由里不碰授权头。

```python
plaintext = f"sk-pkh_{secrets.token_urlsafe(32)}"
hash_key(plaintext)     # sha256 完整 64 位 hex，存 api_keys.key_hash
```

服务端按顺序做五件事：

1. 用完整 SHA-256 查 `api_keys.key_hash`，要求 `revoked_at IS NULL`、用户 `is_active`。
2. 过期的 Key 再判一次 `expires_at`。
3. 从用户行读全局角色，`superadmin` 与否。
4. 查 `workspace_members` 拿我加入的工作区。
5. 用读侧可见性条件查出所有可读 KB，折叠成 `readable_kb_ids`。

结果装进 frozen dataclass `UserContext`：

| 字段 | 来源 |
|---|---|
| `user_id` / `email` / `display_name` | `users` 行 |
| `api_key_id` / `scopes` | `api_keys` 行 |
| `workspace_ids` | `workspace_members` |
| `readable_kb_ids` | 可见性条件算出的 KB id 集合 |
| `is_superadmin` / `nickname` | `users.role` / `users.nickname` |

失败一律 `INVALID_TOKEN`，不区分"不存在 / 已吊销 / 已过期 / 用户停用"。

Key 只存哈希，且必须是完整 64 位 hex。截短没有意义：Key 本身是 256 位随机数，离线确实没有低熵可爆破，但**在线要猜的是哈希前缀**。只存 12 个 hex（48 bit）时，猜中成本从 2^256 降到 2^48，一块 GPU 大约 8 小时。

`api_key.last_used_at` 在请求成功时由会话的 `commit()` 落库。失败请求走 `rollback`，不会留下使用时间，所以它的语义是"最后一次成功使用"。

## 2. 三档可见性

![Key、上下文与四个过滤函数的判定路径](/img/knowledge-hub/tenancy-decision.png)

| visibility | 谁能读 | 谁能写 |
|---|---|---|
| `private` | 创建者 | 创建者 |
| `workspace` | 该工作区成员 **或** 创建者 | **只有该工作区成员** |
| `global` | 所有用户 | 所有用户 |

读写差一格。一个 `workspace` 库的创建者如果已经退出工作区，他读得到（读判定里 `created_by == 我` 是一条独立的 `or` 分支），但改不了（写判定按 visibility 分派，不看 `created_by`）。

这一格不能混用。回收站列表如果按读判据筛，会出现"列表里有、点恢复 403"。

`global` 可读可写是小团队部署的取舍。如果对外开放，这是最先被攻击的点，所以判定全部收在 `auth.py`，将来接 RBAC 只改那几处。

## 3. 四个过滤函数

| 函数 | 服务对象 | 用在哪 |
|---|---|---|
| `build_qdrant_filter` | Qdrant | dense / sparse / visual 三腿 |
| `build_kb_scope_sql` | Postgres | trgm 子串腿 |
| `visible_kb_clause` | Postgres | KB 列表、`load_user_context` |
| `writable_kb_clause` | Postgres | KB 回收站列表 |

前两个是检索过滤入口，后两个是列表条件。四个都只读 `ctx.readable_kb_ids` 或同一组 `(user_id, workspace_ids)` 零件，不各自重算三档可见性。

两个检索入口分开，是因为 trgm 腿跑在 Postgres 里，拿不到也不该拿 Qdrant 的 filter 字典。让 `trgm.py` 自己 join 复刻可见性，就等于开第二个判定入口。

两个列表条件分开，是因为读与写差那一格。`can_write_kb` 的行版本与 `writable_kb_clause` 的 SQL 版本必须逐档等价，`tests/test_container_trash.py` 在真实 PG 上逐格比对。

写错三档的形状只有两种，但都很短：

```python
# ❌ workspace 与 global 合成一个 IN：所有工作区的库对任何用户可见
visibility.in_(("workspace", "global"))

# ❌ 把成员资格追加成另一条 or：限定条件完全失效
or_(visibility == "workspace", workspace_id.in_(my_ws))
```

正确写法是 `workspace` 分支的两个条件放在同一个 `and_` 里。

## 4. fail-closed 与同码

拿不到授权范围时，过滤条件必须变成恒假，不能退化成不过滤：

```python
{"must": [{"key": "kb_id", "match": {"value": -1}}]}   # Qdrant
col == NO_SUCH_KB                                      # SQL
```

`NO_SUCH_KB = -1`。KB id 从 1 开始，这个值永远不存在。

跨库请求里的 `kb_ids` 只是意图，实际范围是交集：

```python
want = allowed if kb_ids is None else (allowed & set(kb_ids))
```

交集只会更小，所以带一个无权限的 `kb_id` 进来不会越权，只会少结果。传空数组返回 400（"传 null 表示全部有权限的库"）；交集为空返回空结果，不报错。报错会泄漏"这些 id 里至少有一个存在"。

资源级失败统一 `ResourceNotFound`：

| 情况 | 表现 |
|---|---|
| HTTP：KB 或文档不存在、无读权限、无写权限 | `KB_NOT_FOUND` / 403 |
| MCP：库不存在或无权限 | `result.isError=true` + `{"error":"KB_NOT_FOUND"}` |
| MCP：文档不在这个库 | `result.isError=true` + `{"error":"DOC_NOT_FOUND"}` |
| 操作级拒绝（非超管调管理端点） | `FORBIDDEN` / 403 |

前三行是 fail-closed：调用方不能通过错误码差异推断资源是否存在。`FORBIDDEN` 只用于"这个操作你就不能做"，没有资源存在性可探测（`errors.py` 里另有 `DocNotFound` 类，但 HTTP 路由不用它，文档级失败同样走 `KB_NOT_FOUND`）。

MCP 与 A2A 也遵守这条。一个库都没有时，MCP 不暴露 `search_kb` / `ask_kb` / `get_document`，A2A 的 `readableKbCount` 为 0。先返回全部工具、调用时再拒绝，等于让调用方探测到不该存在的 KB。

## 5. 工作区软删的连锁

`DELETE /workspaces/{id}` 只标记工作区一行，不级联软删其下的库与文档。这样恢复只有一行。

代价是"删掉工作区"必须真的生效。做法是在可见性判定里加一个条件：

```python
and_(or_(三档条件), _workspace_alive(model))
```

这个 `EXISTS` 有两个容易写错的地方，都实际发生过：

1. **不能写成第四条 `or` 分支。** 写成 `or_(三档, EXISTS)` 时，只要库里存在任意一个未软删的工作区，每一行都会通过，三档里 workspace 那一支照样命中。
2. **子查询必须 `correlate(model)`。** 直接 `exists().where(ws.id == model.workspace_id, ...)` 会被渲染成 `EXISTS (SELECT * FROM workspaces, knowledge_bases WHERE ...)`，子查询自己带了一张 `knowledge_bases`，与外层那一行没有关联。

两次错误的表现都是"判据看起来在工作、实际什么都没挡住"，而且 pytest 全绿，靠真库探测才发现。

连带结果是顺序：工作区还软删着的时候，它的库既搜不到、也恢复不了。`GET /kb/trash` 与 `POST /kb/{id}/restore` 都要求先恢复工作区。

## 6. 邀请码、超管与操作级拒绝

邀请码把"邀请一个还没注册的人"变成自服务：owner 生成一段码，对方注册后自己输码加入。

| 项 | 值 |
|---|---|
| 字符集 | 31 个，去掉 `0 O 1 l I` 这些手抄会认错的字符 |
| 长度 | 8 |
| 默认有效期 | 7 天 |
| 默认可用次数 | 1，上限 50 |
| 存库 | HMAC-SHA256 + 每码盐，另存 4 位前缀供人识别 |
| 角色 | 只能授予 `member` |

兑换失败时，过期、用完、被撤销、码不存在四种情况回同一句话：

```
邀请码无效（可能已过期、已被使用，或已被撤销）
```

区分开等于给攻击者一个"这个码存在但失效了"的探测信号。

超管 `users.role='superadmin'` 越过三档可见性。实现方式是展开 `UserContext` 的范围，不是在过滤器里加分支：

```python
workspace_ids = 所有工作区
readable_kb_ids = 所有未软删的库
```

它仍然从用户行经 API Key 推导，请求体里不接受这个字段。

## 7. 守卫

| 守卫 | 守什么 |
|---|---|
| `tests/test_permissions.py` | 三档分别判定；workspace 分支必须带成员资格；private 不能被同工作区成员读到 |
| `tests/test_container_trash.py` | `can_write_kb` 的行版本与 `writable_kb_clause` 的 SQL 版本逐格等价；`visibility == 'global'` 只允许出现在 `auth.py` |
| `tests/test_qdrant_filter_scope.py` | Qdrant 过滤只允许 `kb_id`；`services/` 下没有用 `visibility` / `workspace_id` / `source_kind` / `owner_id` 做 key 的过滤字典 |
| `tests/test_retrieval_filters.py` | AST 扫描：检索层不出现可见性判定，每条查 Qdrant 的腿都传 `build_qdrant_filter` 的产物 |

第三条守的是一个具体形状：payload 里的 `visibility` 是摄取时写死的，改库可见性不回写。一旦有人按它过滤，陈旧值立刻造成越权。

不做的部分：

- 不做细粒度 RBAC。scope 目前只有 `kb:read` / `chat:read` 这类粗粒度门禁，写操作靠资源归属判定。
- 不把租户字段放进请求体。`kb_ids` 是检索范围意图，不是身份。
- 不靠前端隐藏。前端不显示的按钮，后端仍然要判。
- 不在日志里打完整 API Key 或审计 detail 的原文。
