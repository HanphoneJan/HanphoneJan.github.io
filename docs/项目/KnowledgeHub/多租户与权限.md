# 多租户与权限

本文描述当前已经实现并生效的权限体系。结论以 `services/common/auth.py`、各路由和前端守卫为准。

## 1. 权限体系总览

平台没有做完整的 RBAC，只用了四层足够满足当前需求的机制：

1. 身份：用户，以及每个用户的一把或多把 API Key；
2. 组织：工作区（Workspace）和成员（owner 或 member）；
3. 资源可见性：知识库的三档可见性（`private`、`workspace`、`global`）；
4. 全局角色：`user` 或 `superadmin`，用于运维和用户管理。

权限判定的入口只有一个，就是 `services/common/auth.py`。

## 2. API Key：唯一的租户来源

### 2.1 格式与存储

```python
KEY_PREFIX = "sk-pkh"
plaintext = f"{KEY_PREFIX}_{secrets.token_urlsafe(32)}"
key_hash  = sha256(plaintext)                 # 完整 64 位十六进制，不截断
key_prefix = plaintext[:KEY_PREFIX_LEN + 6]   # 仅用于界面展示
```

明文只在创建时返回一次，数据库里只保存哈希。

这里用 SHA-256 而不是 bcrypt 或 argon2，是因为 key 本身就是 256 位随机数，没有低熵空间可以被爆破，而且每次请求都要计算，必须足够快。用户密码才使用 argon2。

哈希必须保存完整长度。早期版本只保存 sha256 的前 12 个十六进制字符（48 位），在线爆破平均需要 2 的 48 次方次哈希，一块 GPU 大约 8 小时就能完成。改成完整长度后，旧 Key 会全部失效一次，前端在收到 401 时会重新登录并换取新 Key。

### 2.2 请求体不接受租户字段

```python
# ❌ 攻击者可以传别人的 user_id
{"user_id": 42, "query": "..."}

# ✅ 租户范围从 API Key 推导
ctx = await load_user_context(session, api_key)
```

所有范围都来自 `UserContext`：

| 字段 | 含义 |
|---|---|
| `user_id` | 当前用户 |
| `workspace_ids` | 我加入的工作区 |
| `readable_kb_ids` | 我可读的知识库全集，是三档可见性折叠后的结果 |
| `is_superadmin` | 是否是全局超管，同样从 API Key 推导 |
| `scopes` | 粗粒度门禁，当前只做 `kb:read` 和 `chat:read`，为将来的 RBAC 留位置 |

`workspace_id` 可以作为请求参数，但必须校验成员资格。`kb_ids` 只用于求交，不能扩大可访问范围。

## 3. 三档可见性

### 3.1 三个独立分支，不能写进一个 `IN`

```python
# ❌ 这样写有两个独立漏洞
or_(visibility.in_(("workspace", "global")), created_by == me)
#   1. 所有 workspace 库对任何用户可见，缺少“我是该工作区成员”这一条件
#   2. 同工作区成员能看到别人的 private 库，因为 private 被混在同一个 IN 里

# ✅ 三个档位各有各的限定条件
global    → 所有用户可见
workspace → visibility == 'workspace' AND workspace_id IN (我的工作区)
private   → created_by == 我
```

`IN` 表达的是“任一条件成立即可”，而可见性要表达“不同档位有各自不同的限定条件”，两者语义不匹配。

### 3.2 修复时最容易犯的二次错误

保留裸的 `workspace` 分支，把带成员资格限定的分支追加成另一条 `or`：

```python
# ❌ 限定条件完全无效，等于没改
conds = [vis == "global", vis == "workspace", created_by == 我]
conds.append((vis == "workspace") & ws_id.in_(ws))    # 白加
```

两个条件必须写在同一个 `and_` 里：

```python
# ✅
and_(visibility == "workspace", workspace_id.in_(ws_ids))
```

由此得到一条推论：任何附加的限定条件，都要先问它是 `or` 的一项还是 `and` 的一项。拿不准就写成 `and_(or_(可见性条件), 额外限定)`，让结构本身表达意图。

### 3.3 工作区软删除之后

早期删除工作区时只标记 `workspaces.deleted_at`，没有级联处理知识库和文档。结果是“删掉工作区”对保密毫无作用：`GET /kb` 仍然会列出它的库，搜索仍然能命中正文。

修法不是级联删除，因为那会把“恢复一行”变成“恢复一串”。正确做法是在可见性判定里要求工作区仍然存活：

```python
exists(select(1).where(Workspace.id == KB.workspace_id,
                       Workspace.deleted_at.is_(None)))
```

一个条件就同时覆盖了四条路径。但要注意，这个 `EXISTS` 必须关联到当前知识库行（correlate），否则会退化成“只要库里存在任意一个存活的工作区，每一行都通过”。

## 4. 过滤入口只有一个

| 函数 | 服务的存储 | 用在哪里 |
|---|---|---|
| `build_qdrant_filter(ctx, kb_id, kb_ids=)` | Qdrant | dense、sparse、visual 三条通道 |
| `build_kb_scope_sql(ctx, kb_id, column, kb_ids=)` | PostgreSQL | trgm 子串通道 |
| `visible_kb_clause(ctx)` | PostgreSQL | 知识库列表（读） |
| `writable_kb_clause(ctx)` | PostgreSQL | 知识库回收站和恢复（写） |

前两个函数同源，都只读取 `ctx.readable_kb_ids`，不各自重新计算三档可见性。历史上唯一一次真实越权，正是因为两处各自复刻了可见性逻辑。

之所以不合并成一个函数，是因为有一条通道运行在 PostgreSQL 里，拿不到 Qdrant 的过滤字典。将来增加任何检索存储时，往这张表里加一行，不要在调用方临时拼条件。

### 4.1 自动化守卫

`tests/test_retrieval_filters.py` 用 AST 扫描全仓库，断言以下几条：

- 除白名单外，任何文件不得出现过滤字面量；
- 每条查询 Qdrant 的通道都必须传入来自统一入口的 `filter`；
- 检索层不得出现可见性判定代码；
- 运行时只有一棵依赖树；
- 检索实现只存在于 `services/retrieval/`。

`tests/test_permissions.py` 还会用 `literal_binds` 编译 SQL，用正则查找裸的 `workspace` 分支，并断言不出现 `visibility IN`。

### 4.2 三个存储分别靠什么隔离

系统用了三个存储，但授权只判定一次：`load_user_context` 从 API Key 推导出 `ctx.readable_kb_ids`，三个存储各自只做“按这个范围过滤或校验”，都不重新计算可见性。

| 存储 | 里面有什么 | 隔离手段 | 失败时 |
|---|---|---|---|
| PostgreSQL（真相源） | 知识库、文档、chunk、任务、用户 | `build_kb_scope_sql`、`visible_kb_clause`、`writable_kb_clause`；读取资源前调用 `assert_kb_access` | 恒假条件，或返回 `KB_NOT_FOUND` |
| Qdrant（派生索引） | dense、sparse、visual 三个集合 | 每条查询都带 `build_qdrant_filter(...)`；payload 里也有 `kb_id`、`workspace_id`、`visibility` | 使用 `{"kb_id": -1}` 这类恒空过滤 |
| Blob（内容寻址） | 原件、预览、缩略图，按 sha256 去重 | 鉴权在元数据层：先 `load_document`，再 `assert_kb_access`，最后才读 `doc.blob_sha` | 返回 404 或 403，不按路径放行 |

两条容易被忽略的边界：

- blob 去重不等于权限共享。同一份文件被两个租户上传时只存一份，但 sha256 不是访问凭证。知道哈希也读不到文件，因为读端点会先校验文档所属的知识库。文件路径从来不是权限。
- Qdrant 允许短暂落后。检索在融合之后还要做一次 `_drop_deleted`，也就是批量查询 PostgreSQL。绝不允许“PostgreSQL 已删、Qdrant 还能搜到”，那才是真正的数据泄漏。

另外有一处有意的统计量泄漏。BM25 的 `terms` 和 `corpus_stats` 是全局的，因为三个知识库共用一个 sparse 集合，下标空间必须一致。一个罕见词如果在别的租户语料里出现过，会拉低这边的 idf。它只泄漏统计量，不泄漏内容。这是明确记录下来的取舍，不是遗漏。

## 5. fail-closed：无权限等于不存在

```python
# ❌ 攻击者能通过错误码差异探测资源是否存在
if kb.visibility == "global": raise Forbidden()
raise NotFound()

# ✅ 内部日志可以记录原因，对外一律返回同一个错误码
raise ResourceNotFound()   # KB_NOT_FOUND，HTTP 403
```

同样的规则适用于：

- 文档：统一返回 `DOC_NOT_FOUND`；
- 工作区：无权限和不存在返回同一个错误码；
- MCP 工具：知识库不存在或无权限，都返回 `result.isError = true` 加 `KB_NOT_FOUND`，不暴露存在性。

跨库搜索还有两条边界：

- `kb_ids=[]` 返回 400，空数组属于请求错误；
- `kb_ids` 求交后为空时返回空结果而不是报错，因为报错会泄漏“这些 kb_id 里至少有一个存在”。

## 6. 工作区、成员与邀请码

工作区有 owner 和 member 两档。`POST /workspaces/{id}/members` 只能添加已经注册的邮箱，没注册会返回 400。由于设计上不接邮件服务，邀请必须做成自服务形式，也就是邀请码。

| 端点 | 谁能调用 | 说明 |
|---|---|---|
| `POST /workspaces/{id}/invites` | owner 或 admin | 生成邀请码，明文只返回这一次 |
| `GET /workspaces/{id}/invites` | owner 或 admin | 列表里只有前缀 |
| `DELETE /workspaces/{id}/invites/{invite_id}` | owner 或 admin | 撤销，重复撤销也返回成功 |
| `POST /invites/redeem` | 已登录用户 | 兑换后成为该工作区的 member |

邀请码有四条设计约束：

1. 数据库只保存 HMAC-SHA256 哈希和前 4 位，每个码使用随机盐，与 API Key 遵循同一纪律。
2. 口令是 8 位，去掉了容易混淆的 `0O1IL`。规范化时接受空格、连字符和小写，但不会把 `0` 猜成 `O`。
3. 默认有效期 7 天、可用 1 次，`max_uses` 上限为 50。
4. 兑换失败统一返回一句话。不存在、过期、用完和撤销都是同一句，区分开等于给攻击者一个探测信号。

兑换的校验顺序是先验证哈希，再看“是不是已经是成员”，最后验证状态。顺序反了，重复兑换会得到“邀请码无效”。已经是成员不算失败，返回 200 和 `already_member: true`。`POST` 的请求体没有 `role` 字段，只能给 member 角色。`used <= max_uses` 由数据库 CHECK 约束保证，撞上时返回 400。

## 7. 超级管理员

- `users.role` 有 `user` 和 `superadmin` 两个值，是全局角色，与工作区的 owner/member 不是一回事；
- 超管身份同样是从用户行经 API Key 推导出来的，请求体不接受角色字段；
- 超管越过三档可见性的方式，是把 `UserContext.readable_kb_ids` 展开成全集，而不是在过滤器里增加分支；
- `GET/POST/PATCH /admin/users` 仅超管可用；
- 防自锁：不能降级或停用最后一个超管，也不能停用自己；
- 任何用户都可以用 `PATCH /auth/me` 修改自己的显示名、昵称、邮箱和密码；修改邮箱或密码必须带上 `current_password`。

普通用户的三档可见性 SQL 一字未改，且有守卫固定。超管只是把范围展开，并没有绕开过滤逻辑。

## 8. 审计

审计表记录三元组：API Key、用户、知识库，另外还有 query 摘要、结果数和耗时。

| `action` | 端点 |
|---|---|
| `search` | `POST /kb/{id}/search`、`POST /search`、`POST /kb/{id}/search/debug`、`GET /kb/{id}/ask/preview` |
| `ask` | `POST /kb/{id}/ask`（SSE） |
| `upload` | `POST /kb/{id}/documents`、`import/chat`、`import/dir` |
| `mcp_call` | `POST /mcp`，每次 `tools/call` |
| `a2a_call` | `POST /a2a/tasks` |

几个要点：

- `ask_preview` 记为 `search` 而不是 `ask`，因为它没有生成任何内容；
- `ask` 的 `detail` 里另外记录 `retrieval_query`（真正送去检索的 query，可能被指代消解改写）、`query_expanded` 和 `history_turns`；
- 有几类读端点刻意不记审计：`/documents/{id}/chunks`、`/pages/{n}`、`/preview`、`/thumbs/{n}`、`/pii`；
- 新增检索端点时必须接上审计，`tests/test_audit_coverage.py` 是接线守卫；
- `GET /audit` 只能查询自己有权管理的工作区，因为审计里包含 query 摘要，那也是用户数据。`workspace_id` 必填，`action` 要先校验再查询，拼错的值如果静默返回空列表，就是在骗人。

## 9. 权限之外的隐私边界

权限解决“谁能看”，隐私解决“数据去哪里”，两者不要混为一谈。

| 机制 | 解决什么 | 默认 |
|---|---|---|
| 三档可见性 | 用户之间的隔离 | `private` |
| `KB_NOT_FOUND` | 不泄露资源是否存在 | 始终开启 |
| PII 掩码 | 索引文本里的敏感信息 | 按库关闭 |
| 抽取式生成 | 原文不出本机 | 始终开启 |
| 外部 LLM 开关 | 是否允许原文外传 | 关闭 |
| 视觉服务无鉴权但只绑 127.0.0.1 | 重模型不暴露到网络 | 仅本机 |

视觉服务没有鉴权，它只绑定 `127.0.0.1`。不要把它指到 `0.0.0.0`，用 `deploy/visual.sh` 单独起停。

## 10. 常见错误与排查

| 现象 | 原因 | 处理方式 |
|---|---|---|
| 列表里有，点恢复 403 | 回收站用了读判据而不是写判据 | 改用 `writable_kb_clause`；`tests/test_container_trash.py` 会用真值表逐格比对 |
| 删了工作区还能搜到 | 可见性没有要求工作区仍然存活 | 增加 `EXISTS`，并确认它关联到当前知识库行 |
| 同工作区能看到别人的 private 库 | 三档可见性写进了一个 `IN` | 改成三个独立分支 |
| 搜索返回了别的库 | `kb_ids` 被当成全集，或过滤条件没有传 | 子集只做求交；检查通道是否传了统一 filter |
| 升级后前端被登出 | API Key 哈希改成完整长度，旧 Key 失效 | 前端在 401 时重新登录并换取新 Key |
| 邀请码重复兑换提示无效 | 校验顺序错了 | 先验哈希，再看是否已是成员，最后验状态 |
