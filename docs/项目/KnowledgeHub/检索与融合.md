# 检索与融合

本文讲一次检索是怎么完成的：四条召回通道各自做什么，结果如何融合，查询路由和精排如何介入，某条通道不可用时会怎样，以及引用坐标从哪里来。进程模型、存储分工和租户隔离在[架构总览](./架构总览.md)里，这里不重复。

## 1. 四条召回通道

一次 `hybrid` 检索会同时执行四条召回通道，然后把结果融合成一个排序。

| 通道 | 实现位置 | 检索方式 | 分数量纲 | 擅长 |
|---|---|---|---|---|
| `dense` | `services/retrieval/dense.py` | 用 `bge-small-zh-v1.5` 编码成 512 维，在 Qdrant 里做余弦检索 | 0.2 到 0.9（有界） | 语义泛化、同义改写 |
| `sparse` | `sparse.py` 和 `bm25.py` | 自实现 BM25（jieba 分词），写入 Qdrant 稀疏向量 | 0 到 40 以上（无界） | 关键词、人名、术语 |
| `trgm` | `trgm.py` | PostgreSQL 的 `word_similarity()`，字符级三元组 | 0.25 到 0.40（窄带） | 非词字符串：编号、错误码、文件名片段 |
| `visual` | `visual.py` | `colSmol-500M` 的 late-interaction 多向量 MaxSim | 0 到 1 | 扫描页、照片等没有文本层的内容 |

在同一个评测集上，单条通道的实测结果如下：

| 通道 | R@10 | MRR@10 | 单通道耗时 |
|---|---|---|---|
| `dense` | 0.585 | — | 56 毫秒 |
| `sparse` | 0.756（四路最强） | 0.681 | 153 毫秒 |
| `trgm` | — | — | 约 45 毫秒 |
| `visual` | 照片 1.00，扫描页 1.00，文本类 0.00 | — | 编码每条 119 到 128 毫秒 |

`visual` 的 overall 数字没有意义。它只索引扫描页和照片，总共几十个点，天然无法召回文本类提问，混在一起算总平均只会得到无法解释的数字。只有分类别的数字可以比较，这条纪律适用于本文所有表格。

### 1.1 `mode` 与通道的对应关系

| mode | 走哪条路 | 能搜什么 |
|---|---|---|
| `semantic` | 只走 `dense` | 意思相近的内容 |
| `exact` | 只走 `trgm` | 子串和模糊匹配，例如编号、文件名 |
| `hybrid`（默认） | `dense`、`sparse`、`trgm` 三路 RRF | 语义、关键词和字面匹配 |

`visual` 不在 `mode` 里。它是否执行，由“本进程能不能做视觉查询”决定，例如本地允许，或者远端编码服务可达。这样纯字符查询不会莫名其妙多花一次视觉编码。

### 1.2 三个值得单说的实现细节

**BM25 的日期归一化。** `2025-02-14` 会被 ASCII 规则切成 `2025/02/14`，而提问里的“2025年2月14日”会被切成 `2025/年/2/月/14/日`。两边没有任何共同 token 能表达“这一天”，而 BM25 又无法表达“多个词共现”。增加一个归一化 token `d20250214` 之后，这类查询的 R@10 从 0.20 提升到 1.00。这是一个典型的“检索质量问题其实出在分词”的例子。

**BM25 的 idf 是全局统计量。** 稀疏向量的下标空间必须全局一致，所以所有知识库共用一个词表和一份语料统计。副作用是：一个罕见词如果在别的知识库里出现过，这边的 idf 会被拉低。它只泄漏统计量，不泄漏内容。修法是定期跑重建任务重算，而不是让每个库各算一套。

**trgm 的召回条件只能使用 `word_similarity` 阈值。** 曾经试过两种“更快”的写法，结果都静默漏召回：

- 用 `ILIKE '%<整句提问>%'` 或对整段调用 `similarity()`，各返回 0 条；
- 只有 `word_similarity(query, chunk) >= 0.25` 返回了 3 条，其中包含正确答案（0.400）。

两个失败版本的共同原因是它们都要求 query 和整段文本可比：`ILIKE` 要求 query 是原文的连续子串，而自然语言提问从来不是；`similarity()` 按整段长度归一化，500 字的块对 8 个字的 query，分数恒在 0.05 到 0.11。把两者用 `OR` 连起来也会漏，因为放宽的是同一个错误判据，而不是换了一个判据。

代价是这条通道要全表扫描（`word_similarity` 用不上 GIN 索引），以目前的规模可以接受：慢能被发现，漏召回不能。

### 1.3 四条通道真并发，但每条数据库通道用自己的会话

- `dense`、`sparse`、`trgm` 都要访问数据库，不能共用一个 `AsyncSession`；
- SQLAlchemy 的 `AsyncSession` 不允许并发 `execute`，共用会抛出 `This session is provisioning a new connection; concurrent operations are not permitted`；
- 后果很隐蔽：sparse 和 trgm 被记成 `skipped`，`hybrid` 静默退化成 dense 单通道，接口仍然返回 200；
- 现在每条数据库通道从会话工厂各拿一个会话，也就是各自占一条 PostgreSQL 连接，四条通道真正并发；视觉通道不访问数据库，同样并发；
- 代价是连接数。一次 `hybrid` 最多占用请求会话加三条通道，共 4 条连接，连接池要按“并发检索数 × 4”估算。池不够时请求会排队，结果仍然正确。

这里的“连接”指 API 进程到 PostgreSQL 的连接池连接（asyncpg 的 TCP 连接），不是浏览器到 API 的 HTTP 连接。连接池是进程级的，每个 uvicorn worker 各有一份，详见[部署与运维](./部署与运维.md)的连接池一节。

这是“检索质量悄悄变差但不报错”的典型案例。在调试面板里看到 `sparse.skipped` 有值，第一反应应该是检查会话或连接，而不是怀疑“库里没有数据”。

## 2. RRF 融合

### 2.1 为什么不加权求和

四条通道的分数量纲互不相同：BM25 无界且随语料增长，trgm 只在 0.25 到 0.40 的窄带里，dense 有界。要加权求和，就必须先归一化，而常见的两种归一化都不好用：

- min/max 归一化对单次查询的候选集敏感，同一段文本在两个 query 下的分数会不同；
- z-score 会被那条通道的离群值带偏。

RRF 只看排名，天然避开了这些问题：

```
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))        k = 60
```

`k = 60` 是 RRF 原论文的取值。它的作用可以从数值上看出来：排名第 1 和第 2 的贡献分别是 `1/61` 和 `1/62`，相差约 0.26%。也就是说，头部名次的微小优势不会压倒第二条通道的共识。dense 和 sparse 都排第一的 chunk，应该赢过“只有一条通道排第一、另一条排第 30”的 chunk。

实现上有两个工程细节：

- **融合 key 必须带命名空间**，例如 `text:<id>` 和 `visual:<id>`。文本集合和视觉集合的点 ID 空间是独立的，直接拿点 ID 做 key 会让两者互相抵消。
- **排序要有确定的 tiebreaker**。RRF 分数是浮点数，理论上会有并列，如果没有兜底排序，同一个 query 两次请求的顺序会抖动，前端的引用角标会在刷新后对调。

### 2.2 为什么默认权重都是 1.0

这是实测结论，不是懒得调。等权 RRF 在每个语料类别上都没有赢过该类的最佳单通道：chat 从 1.00 降到 0.90，photo 从 1.00 降到 0.60，blog 从 1.00 降到 0.88。

原因很直接：一套固定权重不可能同时是 chat 的最优和 photo 的最优。所以问题不是“`k` 值不对”或“权重没调好”，而是“应该按查询类型换一套权重”。这就是下一节的路由。

`k = 60` 也被刻意保护起来。它定义的是排名尺度，不是分类器可以调的旋钮。

### 2.3 候选池与软删除过滤

```
per_leg = min(100, max(top_k × 3, 30))     # 每条通道的候选数，设绝对上限防止负载过大
fused   = rrf(四条通道, limit = top_k × 2)  # 融合池取最终返回量的两倍
  → 软删除过滤 → 路由偏好 → 截到 top_k → 可选精排
```

池子取 `top_k × 2` 而不是 `top_k`，是因为路由的偏好过滤只能重排池内的结果。

软删除二次过滤放在融合之后、路由偏好之前，顺序不能换：

- 索引和数据库允许短暂不一致，删除是异步清理的，所以向量通道可能召回已经进回收站的文档；
- 这里用一次批量查询把它们挡掉。绝不允许“数据库已删但索引还能搜到”，那才是真正的数据泄漏；
- 放在路由偏好之前，否则“被路由滤掉的命中”会被算进“被软删滤掉”的计数里，那个数字的含义就变了。

成本上，它只查询命中里出现的文档 ID，一次 `IN` 查询，开销与 `top_k` 成正比，与语料规模无关。

## 3. 查询路由与精排

### 3.1 路由做什么

路由用正则匹配六类意图（`photo`、`scan`、`table`、`chat`、`date`、`general`），命中后调整通道权重并增加软偏好：

| 意图 | 通道权重 | 偏好 | 依据 |
|---|---|---|---|
| `photo` | `visual 3.0` | 照片库 | visual 在照片类 R@10 为 1.00 |
| `scan` | `visual 2.0` 加 `sparse 1.2` | 整页或表格类块 | 扫描页靠视觉，表单文字靠字面 |
| `table` | `sparse 1.3` 加 `trgm 1.2` | 表格类块 | 问“哪一栏怎么填”属于字面匹配题 |
| `chat` | `sparse 1.6` | 聊天类块与聊天库 | 实测 chat 类 sparse 为 1.00，dense 为 0.10 |
| `date` | `sparse 2.5` | 无 | dense 召不回“哪天”，BM25 的日期归一化实测 Hit@1 为 0.875 |
| `general`（兜底） | 全部 1.0 | 无 | 与引入路由前完全一致 |

表格 chunk 的文本以一句描述开头（“表格描述：N 行 × M 列；表头：…”），由摄取期纯规则生成。`table` 意图偏好表格类块，而描述让“XX 一览表”这类查询在 dense 通道也能召回表格，表头是编号或 `值1` 时尤其明显。

`photo` 对应的 `visual 3.0` 是实测出来的。在一组 60 个照片点、60 个文本点、`top_k=10`（融合池上限 20）的对照实验里：

| `visual` 权重 | 融合池里的照片点数 | top10 里的照片数 |
|---|---|---|
| 0.0 或 1.0 | 0/20 | 0/10 |
| 2.0 | 10/20 | 5/10 |
| 3.0 | 20/20 | 10/10 |
| 4.0 或 6.0 | 20/20 | 10/10（与 3.0 等价） |

所以 3.0 是能让照片点把融合池装满的最小值，再往上没有收益。

2026 年 10 月 15 日重测的结果也支持这张表：8 张照片上 dense、sparse、trgm 的命中都是 0，visual 的 Hit@1 为 0.750，Hit@5 为 1.000；8 条真实聊天按天查询，sparse 的 Hit@1 为 0.875，dense 为 0.250，trgm 为 0.000；从真实 PDF 派生的 4 页扫描件，visual 的 Hit@1 为 1.000，其它三条通道都是 0.000。

### 3.2 三条设计原则

**拿不准就不路由。** 置信度低于 0.35 时返回等权结果且不做偏好过滤，行为与引入路由前完全一致。宁可少优化一点，也不要用一个猜错的意图把结果过滤空，那对用户来说等于“搜索坏了”。置信度的赋值方式是：命中多个意图时为 0.5，取更具体的那一个，不加权求和；只命中日期字面量时为 0.6；单一意图命中时为 0.9。

**过滤是软偏好，不是硬排除。** 过滤后如果为空，就退回未过滤的结果，并在返回说明里如实写上原因。例如“识别到在找照片，但库里没有照片类型的库，不做过滤”。硬排除加空结果，用户看到的就是 0 条。

**路由只调整通道权重和偏好，不调整 `k`。** `k = 60` 是排名尺度的定义。

路由不做的事情也要明确：它不做学习出来的路由（需要标注数据和训练管线），不改变 `mode` 的语义（`semantic` 和 `exact` 由用户选择，不由路由器猜），也不做 LLM 意图识别（会在编码开销之外再加一次调用）。

### 3.3 一个必须知道的机制：偏好管不到池外

执行顺序是先 `rrf(..., limit = top_k × 2, weights = 路由权重)`，再 `prefer(fused, route)`。

所以权重决定“哪些结果能进入池子”，偏好只能重排池内已有的结果。推论是：`photo` 路由在知识库大于 `top_k × 2` 时才有意义；库很小的时候，它与任何权重的结果完全一样。这也解释了早期几次对照实验为什么量不出差异。

### 3.4 精排

精排开关按知识库设置：`kb.rerank_model` 非空时才执行，为空表示不启用，这是默认状态。默认模型是 `BAAI/bge-reranker-v2-m3`，CPU 上处理一对约 114 毫秒，输入是 RRF 融合后的 top_k 候选，每段截断到 1200 字符。跨库检索一律不启用精排。`rerank_model` 只从知识库读取，不接受请求参数，因为排序是知识库的属性，同一个问题在不同库里答案可能不同。

默认关闭有两个原因：

1. 它只能重排候选，不能扩大召回。真值不在候选里就救不回来，所以它是提升，不是解决方案。
2. 延迟上，20 个候选需要 0.6 到 1.2 秒，而 `hybrid` 检索本身已经是 1 秒量级。

模型选型也是实测的。更小的 `base` 版本在成对判别上只对了 2/4，`v2-m3` 对了 4/4，而 `base` 失败的正是中文公文类语料，它把标题行排在了答案段之上。代价是单对耗时从 53 毫秒涨到 114 毫秒，这是“默认关闭、按库开启”的另一个理由。

精排不可用时要如实标记 `skipped`，不能静默降级，否则用户会以为自己在用精排，实际并没有。

### 3.5 三个默认关闭的增强功能

| 能力 | 做什么 | 默认 | 代价或边界 |
|---|---|---|---|
| 查询改写 | 规则层（规范化、抽取实体词）不外传；可选 LLM Multi-Query 生成变体 | 关闭 | 原始 query 永远排在第 0 位一起参与召回，作为改错时的兜底；LLM 层只在显式配置外部 LLM 且开关打开时生效 |
| 证据质量与拒答 | 用 RRF 的跨通道共识判断 `ok`、`weak` 或 `none`；`none` 且生成器不是抽取式时直接拒答，不调用 LLM | 自动 | 只看已有信号，不额外调用；抽取式本来就会在摘不出句子时拒答 |
| 时间过滤 | `updated_after` 和 `updated_before` 同时收紧三条 Qdrant 通道与 trgm 的 PostgreSQL 条件 | 不传即关闭 | 旧点没有 `updated_at`，带时间过滤时会被排除，属于重摄取欠账 |

这三项都不改变默认路径的排序，这也是它们能默认关闭的前提。

## 4. 降级行为

核心纪律是：检索通道属于增强项，不可用时只降级，绝不返回 500。检索照常返回其它通道的结果。

| 通道 | 什么情况下标记 `skipped` | 原因文案的要求 |
|---|---|---|
| `visual` | 远端编码服务不可达、超时或返回 503 | 必须可操作，说清怎么修，不能只写“失败” |
| `dense` | 索引和查询使用的嵌入模型不一致（`index_models` 记录的值与当前配置不同） | 说清“索引用哪个模型建的、现在配的是哪个、怎么修（改回或重建）” |
| `rerank` | 知识库未配置精排模型，或模型不可用 | 说明是“未配置”还是“不可用” |
| 任意通道 | 该通道抛出异常 | `ok=false` 加原因，其它通道不受影响 |

嵌入模型一致性为什么要拦住并标记 `skipped`：不同模型的向量空间不通用，混用等于在两个空间里计算相似度，结果不是“随机”，而是整个排序基础都坏了，而且不会报错。所以宁可降级并说清原因，也不静默返回错误排序。判据是保守的：`index_models` 为空表表示“未知”，此时放行，因为还没记录不等于不一致。

调试端点里的 `legs[].skipped` 是字符串或 `null`，不是布尔值，因为前端要显示原因。一条没有内容的 `skipped: false` 会让人查错方向。视觉通道的远端调用有硬性限制：超时 2 秒、并发上限 4，使用单例 HTTP 客户端，所有失败统一从一个出口构造 `skipped` 结果。

### 4.1 两件容易混淆的事

“查询侧没跑”和“写入侧没数据”在数据面上看起来一模一样，都是“这条通道返回 0 条”。所以判断能力是否可用，不能看集合里有没有点：能力检测只回答“本进程能不能跑”，即本地允许，或者远端可达且模型就绪；集合为空只能说明没有数据。

`GET /health` 的 `available_legs` 如实汇报这个部署实际能跑哪几条通道。三条文本通道始终存在，`visual` 视情况而定。这与“库里有没有照片”是两件事。

被跳过的通道直接不参与融合。不能把它的空结果当成“排在第 0 名”塞进分母，那会稀释所有结果。RRF 天然支持这一点：一条通道没有命中时对总分的贡献是 0，不会拉低别的通道，这正是它相对加权求和的好处。

## 5. 证据组装与生成

问答的流程是：检索、组装证据、生成、校验引用、落库。

- 证据去重：同一条通道可能命中同一个 chunk，重复会让 `[1]` 和 `[2]` 指向同一段文字。
- 同文档的相邻片段保持原文顺序：RRF 和精排给出的是相关性顺序，同一篇文档的相邻块可能被打散。按 `chunk_index` 升序排列后，模型读到的才是连贯的一段。文档之间的相对顺序不变。
- 不会出现版本冲突：检索只返回 `is_current`，所以“同一主题的多个版本混进上下文”在当前结构下不可能发生。
- 父子块知识库：命中子块时优先使用父块上下文，上限 1200 字符，角标仍指向子块。
- 默认抽取式：答案句子从证据里摘出来，接外部 LLM 时才做归纳。
- 引用校验：答案里的 `[n]` 必须对应真实证据。`dangling_citations` 非空时，前端要提示“这条引用失效了”。

SSE 的帧序是 `sources`、`delta`、`done`。`sources` 先到，前端可以先画引用卡片。具体帧字段见 [API 契约](./API契约.md)。

## 6. 引用坐标

目标是一句话：点开引用就能直接看到原文那一页、那个框。

整个链路分三段：

```
① 解析期：pymupdf 取 line 级 bbox（单位是 point），除以页面尺寸，归一化到 0 到 1
          存入 chunks.locations（JSONB）和索引 payload
② 返回期：检索与问答的命中里带上 locations
③ 渲染期：归一化坐标乘以页图像素，在前端页图上画矩形
```

之所以要归一化，是为了与渲染分辨率（DPI）无关。实测往返误差为 0.00e+00 point。

```jsonc
// 正文块：恰好一个框
{"page": 2, "bbox": [0.1360, 0.2301, 0.8638, 0.2585]}
// 表格块：每个非空单元格一个框，带 row 和 col 供前端排网格
{"page": 3, "bbox": [0.1055, 0.1954, 0.2446, 0.2403], "row": 2, "col": 0}
```

| `kind` | 含义 | `locations` | 前端怎么画 |
|---|---|---|---|
| `text` | 正文段落 | 恰好一个框 | 直接画矩形 |
| `table` | 整张表 | 每个非空单元格一个框，实测最多 40 个，上限 200 | 按 `row` 和 `col` 排成网格，或用 `table_json` 渲染真表格 |
| `page` | 扫描件 | 无 | 只高亮整页，因为没有文本层 |
| `chat` | 聊天 | 没有真实页码 | 高亮消息序号 |

### 6.1 坐标往返里的三个坑

**画框要乘回 point，不是像素。** 绘图 API 需要的是 PDF point：

```python
shape.draw_rect(Rect(nx0 * pix.width, ny0 * pix.height, ...))              # ❌ 框会整体下移约半行
shape.draw_rect(Rect(nx0 * page.rect.width, ny0 * page.rect.height, ...))  # ✅
```

**形态要按 `locations` 的形状分派，不能按 `kind`。** 对外返回的引用类型只有 `text`、`page`、`image` 三种，而块的形态有四种，所以一个表格块会以 `kind="text"` 加上一组带 `row` 和 `col` 的框出现。判据是形状：有 `row` 和 `col` 就按表格网格画，扫描页高亮整页，其余直接画。反过来“从画了几个框反推形态”是错的，14 格的小表会被误判。

**前端取页图不能用 `<img src>`。** 页图端点需要 `Authorization: Bearer`，而 `<img>` 带不了自定义请求头，直接写会静默 401，只在控制台里看得到。正确做法是先 `fetch` 拿到 blob，再 `createObjectURL`，并在组件卸载时释放。

### 6.2 一个比实现细节更重要的不变量

> 坐标和被渲染的页面必须来自同一个文件。

PDF 的坐标按原件排版计算。Office 文档没有原生坐标，实测原生块中只有 0/8 有坐标，所以走“转成 PDF，再在转换版上计算坐标”的路线。用户看到的页图就是这份转换版，文本和坐标同源。

推论是：画框用哪个文件由调用方决定，底图渲染函数不允许自己去找原件，否则给 Office 文档画框会直接报错。定位覆盖率低于 60% 时不给框，而不是给一个错位的框。

### 6.3 已知边界

多栏排版已经做了分栏感知：按行的水平区间找一条没有行跨越的竖直切线，单栏文档退化为原排序。但表格跨页续表仍按页处理，会被截断。页面旋转不为 0 时的坐标换算，以及横排竖排混排的情况，都还没有验证。

## 7. 如何自己验证

- 想看一次检索的完整过程：调用 `POST /kb/{id}/search/debug`，或者在普通检索里传 `include_debug=true`。返回里有每条通道的召回结果（含 `skipped` 原因）、RRF 融合明细、`route` 段（意图、权重、置信度、原因）和 `rerank` 段。
- 想看这个部署实际能跑哪几条通道：读 `GET /health` 的 `available_legs`。
- 想知道某条通道和真相源差了多少点：调用一致性对账端点，按通道分别看。顶层汇总会掩盖“只有一条通道坏了”的情况。例如视觉通道缺点要重新摄取，而不是重建文本索引。
- 想评估端到端召回质量：运行 `eval/` 下的验收脚本。注意它们会清数据，必须串行执行。
