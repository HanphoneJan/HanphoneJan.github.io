# 文档处理与切分

本文讲文件从上传到可以检索的整个过程，重点说明每一步的边界和容易出错的地方。如果你要新增一种解析器或切分策略，或者正在排查“文档入库了却搜不到”“搜出来的内容是空的”，应该先读这一篇。

## 1. 摄取链路的七个阶段

```
blob（内容寻址，没有扩展名）
  → ① 解析        按 documents.file_name 的扩展名查派发表
  → ② 切分        六选一，知识库级配置，默认 recursive；失败退回默认并记录 note
  → ③ 解析校验    空内容、乱码率、长度异常
  → ④ 切分体检    块大小分布
  → ⑤ PII 检出    统计掩码前的命中数，否则报告永远是 0
     └ 按知识库开关决定是否掩码，只掩索引侧
  → ⑥ 嵌入与索引  文本通道（512 维 dense 加 BM25 稀疏向量）与视觉通道（扫描页、照片，逐页入队）
  → ⑦ 终态结算    任务全部进入终态，且索引里确实有点，才置为 ready
```

有两个顺序约束容易踩错。

第一，切分策略在解析之后、掩码之前执行。策略作用于“内容”，包括语义分组、父块划分和上下文生成；而 PII 掩码必须作用在最终要入库的文本上。

第二，PII 必须先检出再掩码。计数要记录掩码前的数量，否则开启了掩码的知识库，报告永远显示“0 处 PII”，用户会以为库里是干净的。

### 1.1 扩展名存在数据库里

内容寻址存储刻意不保留原文件名。同一份文件可能被多个文档版本引用，按内容 sha256 存放才能天然去重，而这就意味着 blob 路径没有扩展名。

```python
# ❌ 每个 blob 都没有扩展名，解析器一律报 UnsupportedFormat
suffix = blob_path(doc.blob_sha).suffix

# ✅ 扩展名和 mime 的真相在数据库行里
parse_to_chunks(path, file_name=doc.file_name, ...)
```

这个错误会同时影响两处：解析器和页图渲染端点。所以解析入口强制要求传入 `file_name`。

## 2. 解析器派发表

`PARSERS` 是一张“后缀到处理器”的映射表，增加一种格式就是增加一条记录：

| 后缀 | 处理器 | 说明 |
|---|---|---|
| `.pdf` | pymupdf 逐页解析 | 唯一原生带坐标的格式；会逐页判断是否为扫描页 |
| `.docx` | python-docx，并修复标题层级 | 需要坐标时转成 PDF |
| `.xlsx` | 按工作表解析 | 表头和数值按列下标对齐，块文本带 `[工作表: <名称>]` 前缀 |
| `.pptx` | 按幻灯片解析 | — |
| `.md` `.markdown` `.txt` `.json` | 纯文本 | 按 Markdown 结构切分 |
| `.html` `.htm` | 去掉标签，按 `h1` 到 `h6` 切分 | — |
| `.csv` | 首行作为表头，转成 Markdown 表格 | — |
| `.jpg` `.jpeg` `.png` `.webp` `.bmp` `.tiff` | 没有文本层，标记为扫描件 | 只走视觉通道 |

上传白名单从这张表派生，不是另外维护一份清单：

```python
SUPPORTED_SUFFIXES, IMAGE_SUFFIXES = _derive_suffix_sets(PARSERS)
```

这样做是为了可测试：测试可以断言“白名单常量确实等于派发表推导的结果”，从而抓住“有人又手写了一份白名单”的漂移。历史上真实出现过的漂移，正是“白名单里有、实现里没有”。

所有解析器统一返回 `(chunks, scan_pages, is_scanned)`。文档类解析器只产出块列表，由适配层补成统一结构。

## 3. 六种切分策略

切分方式按知识库选择（字段是 `knowledge_bases.chunk_strategy`），默认 `recursive`。不同文档形态适合不同策略，没有一种能通吃：

| 策略 | 边界怎么定 | 代价或前提 | 是否影响坐标 |
|---|---|---|---|
| `fixed` | 固定长度加 overlap 硬切 | 会切断句子，语义上最差；存在的意义是作为评测基线 | PDF 不执行 |
| `recursive`（默认） | 标题、段落、硬切逐级降级 | 默认值，同时也是向后兼容契约：不传策略和显式传 `recursive` 的输出必须逐字相同 | 否 |
| `semantic` | 句子向量相似度低于阈值就断开 | 需要句向量编码器，阈值是 0.55；过小的段落会合并 | PDF 不执行 |
| `parent_child` | 子块是递归块，父块是章节（文本）或整页（PDF） | 父块文本不进向量库；父块在 PostgreSQL 里冗余存一份，命中后用父文本作为证据正文，角标仍指向子块 | 否 |
| `late` | 与 `recursive` 相同，但整篇经过 Transformer 后按 span 池化 | 受编码模型 512 token 上限约束，超长文档会被截断 | 否 |
| `contextual` | 与 `recursive` 相同，每块前置一段 LLM 生成的上下文 | 需要显式配置外部 LLM；未配置时降级为 `recursive`，并记录一条“未配置 LLM，不生效” | 否 |

PDF 不执行 `fixed` 和 `semantic`，因为这两种策略会重排文字，而坐标依赖“块的文本和它在页面上的位置一一对应”。重排后坐标会全部失效，所以 PDF 直接保持结构切分，并记录一条说明。这是取舍，不是漏做支持。`parent_child` 在 PDF 上的父子划分按页进行，而不是按章节。

### 3.1 失败一律降级

和检索通道“出问题只标记 `skipped`”是同一条纪律。未知策略、策略抛异常、依赖缺失（没有编码器或没有 LLM）三种情况都退回 `recursive`，并把结论写进 `documents.quality.strategy_notes`，让用户能看到“我选的策略没有生效”。

### 3.2 注册表与约束

`STRATEGIES` 是一张“策略名到实现标签”的表，真正的分派在 `apply_strategy` 里完成。API 白名单和知识库字段校验都从它派生，所以不会再出现“白名单里有、实现里没有”的漂移。测试会断言注册表与对外 schema 里的枚举相等。

策略是单选配置。父块和 Late 理论上可以叠加，但组合会太多，本期不做。另外，修改策略后必须重新摄取才会生效，它只影响新入库的块。`GET /kb/{id}` 返回的 `stale_strategy_docs` 就是“还停留在旧策略的当前文档数”，用来提示重摄取欠账。

## 4. 分层校验

校验分三层，贯穿一个保守原则：只在能确凿判断时报告，识别不出来就放行。

| 层 | 检查什么 | 失败怎么处理 |
|---|---|---|
| 格式 | 扩展名白名单加文件头嗅探（PDF 的 `%PDF`、ZIP 的 `PK`、PNG/JPEG/WebP/BMP/TIFF 的魔数） | 明显不符时上传返回 415 |
| 解析 | 空内容、乱码率超过 5%、长度异常（少于 100 字或多于 1000 万字） | 空内容置为 `failed`；乱码或长度异常记入 `status_msg` 和 `quality`，不阻断 |
| 切分 | 块大小分布（块长标准差超过均值的一半，或存在小于 50、大于 5000 的块） | 写进 `documents.quality` 和日志，不阻断入库 |

格式层为什么“只在确凿时报错”：识别不出、看起来像纯文本的文件一律放行，否则测试用的样例文件和“奇怪但合法”的文件会被全部挡掉。嗅探逻辑本身也刻意保守，只有明确认出是另一种二进制格式时才算不符。

解析层为什么需要校验：在这之前，上传时检查了白名单和大小，但解析出空内容、乱码或切分异常都没有检查。一份解析出 0 个块的 Office 文档会被当成扫描件，直接置为 `ready`，于是系统静默入库了一个空文档。现在的判据把两种情况分开了：

```python
if not parsed:
    if not (is_scanned or scan_pages):
        raise IngestError("解析后没有任何可检索内容（不是扫描件，也没有文本层）",
                          code="PARSE_EMPTY")
    # 扫描件或照片本来就没有文本层，交给视觉通道
```

校验模块是纯函数，不访问数据库，也不加载模型，所以每条判据都能直接写单测。“乱码率 4.9% 和 5.1% 分别怎样”是普通测试用例，不需要启动服务。

### 4.1 `documents.quality` 记录什么

```jsonc
{
  "parse":   {"chars": 18432, "garbled_rate": 0.0, "issues": []},
  "chunking": {"total": 74, "avg_size": 249.1, "stddev": 88.3, "min": 62, "max": 511,
               "acceptable": true, "issues": []},
  "strategy_notes": ["策略 semantic 会重排文字、破坏坐标，PDF 保持结构切分"]
}
```

扫描件和照片的 `parse` 段是 `{"skipped": "扫描件/照片，无文本内容，走视觉通道"}`。没有文本层就要如实写成“跳过”，不能写成“通过”。

## 5. 坐标与结构化处理

坐标的存储格式和渲染链路见[检索与融合](./检索与融合.md)的引用坐标一节，这里只讲摄取侧怎么产出坐标。

### 5.1 扫描页判定

```python
if not page.get_text().strip():
    if page.get_images(): scan_pages.append(pno)   # 扫描页 → 视觉通道
    else:                 blank_pages.append(pno)  # 空白页 → 跳过
```

如果用“文本长度小于某个阈值”来判断，会把空白页也算成扫描页。矢量图形不产生文本层，但它不是扫描件。只有整份文档“一页文本层都没有”时才算是扫描件。

扫描页有处理上限，默认 50 页。视觉编码约 15 秒一页，超过上限就拒绝并给出原因，而不是让一个任务跑几十分钟。这是一个显式上限，不是超时。

### 5.2 多栏阅读顺序

表单类 PDF 常见的问题是双栏排版被按 y 坐标读成“左一行、右一行”。项目用轻量的 XY-cut 解决：按行的水平区间找一条没有任何行跨越的竖直切线，递归地左右分栏；单栏文档自然退化为原来的顺序。

### 5.3 Office 文档的标题与坐标

标题层级通过读取段落的样式名来确定，`Heading N` 对应 N 级标题。这里必须同时看两个信号：光看样式名不够，还要看字号，否则加大字号的普通段落会被误判成标题。

Office 格式没有原生坐标，实测原生块中只有 0/8 带有坐标。做法是先转成 PDF，在转换版上计算坐标，平均定位覆盖率约为 99%。由此得到一条不变量：

> 坐标和被渲染的页面必须来自同一个文件。

所以“画框用哪个文件”由调用方决定，底图渲染函数不允许自己去找原件，否则给 Office 文档画框会直接报错。

### 5.4 表格的结构化

表格文本统一转成 Markdown 表入库，坐标中的 `row` 和 `col` 保持不变。文本给人读，坐标给前端排网格。坐标只能从按行组织的单元格里取：

```python
len(tbl.cells) != row_count * col_count      # ❌ 一维扁平列表，合并单元格会让长度对不上
tbl.rows[ri].cells[ci]                       # ✅ 与 extract() 的行一一对应，None 表示合并单元格
```

也就是说，文本用 `extract()`，坐标用 `rows[i].cells`，按行号对齐。XLSX 还多一条要求：表头和数值必须按列下标对齐，不能各自过滤空值，否则某一列缺失会让整张表错位。

同一份表格会产出三份内容：

| 产物 | 存放位置 | 给谁用 |
|---|---|---|
| Markdown 表 | `content_norm` 的后半段 | 人读，也作为上下文 |
| 表格描述（“N 行 × M 列；表头：…”） | `content_norm` 的开头一句 | 检索，让“一览表”这类查询能命中 |
| 结构化网格 | `table_json`（JSONB 列） | 前端渲染真表格，或程序化读取 |

表格描述由纯规则离线生成（`locations.describe_table`）。因为默认生成层不外传，这里不调用外部 LLM 生成摘要；需要 LLM 描述的部署必须显式配置外部 LLM。三份内容来自同一张网格，不各自解析。`table_json` 只在 `kind="table"` 时存在，正文、扫描页和聊天块为 `null`。

### 5.5 清洗去噪

去噪包括删除重复的页眉页脚、连续空行和零宽字符。只在置信度高的时候删，因为误删正文的代价远大于留下一点噪声。

重复页眉页脚的判据是同一份文档里出现至少 3 次、且长度小于 40 字的行。PDF 的页眉页脚在解析阶段单独清理：`locations._repeated_lines` 先扫描全文，找出跨页重复的短行，在分段之前丢掉。因此坐标只覆盖保留下来的正文行，引用坐标的不变量不受影响。这里只做精确重复判定，带页码的页眉（“第 3 页”和“第 4 页”文本不同）不会被删除。宁可留下噪声，也不误删正文。

## 6. PII 掩码与归属判定

### 6.1 掩码

检出类型包括身份证、手机号、邮箱、银行卡和学号。设计上有三条约束：

1. 默认关闭，按知识库开关。个人知识库的核心用途之一就是“搜我自己的手机号或证件号”，默认掩码等于把这个用途关掉。开关按库设置，所以同一个工作区里可以让日记库保持原文，让准备发出去的证件库开启掩码。
2. 只掩索引侧，不动原件。blob 原件、预览页图和文件下载都保持原文。代价要说清楚：开启掩码后就搜不到自己的号码，这是刻意的取舍，不是 bug。
3. 检出报告只读。它只回答“哪里有、有多少”，不返回原文片段，否则报告本身就成了新的泄露面。

掩码会改变文本长度，所以命中邮箱之后，块的字符偏移会相对原文偏几个字符。影响很小，因为高亮用的是块级 bbox，不是字符级偏移；但不能为了保持长度而保留完整邮箱，那等于没有掩码。实现上有两个“不报错但结果是错的”细节必须处理：

- 同一跨度的重叠命中要去重。一串 18 位数字可能同时命中身份证和银行卡，跨度完全相同，如果按起点依次拼接，会把同一段文字复制一份。
- 掩码长度要自适应。固定写法对 6 到 7 位数字会比原文更长，既没有真正掩住，又改动了内容。

### 6.2 归属判定

导入历史语料时，要先判断这份文档是不是本人的。他人的文档不应该进入本人的检索结果和时间线。

项目没有使用硬编码的人名清单，因为那会漏人。它采用规则式判断：从文件名分段里识别“姓加 1 到 3 字名”的候选，再用停用词表排除“毕业设计”这类误判。判定顺序就是优先级：

| 顺序 | 判据 | 结论 |
|---|---|---|
| 0 | 文件名含本人标识 | 本人（最先短路） |
| 0.5 | 名单型文档（表格里列了多人） | 他人 |
| 1 | 英文简历特征加人名形态的文件名 | 他人 |
| 2 | 文件名含显式的他人姓名 | 他人 |
| 3 | 注册表标记为 `other` | 他人 |
| 4 | 文件名含“姓加名”候选 | 他人（泛化，防止名单外的陌生人） |
| 5 | 正文含显式的他人姓名 | 他人（不设次数阈值） |
| 6 | 正文含本人标识 | 本人 |
| 7 | 以上都不满足 | `unknown`（模板或技术资料） |

第 5 条不设次数阈值是刻意的。设阈值会漏判正文里只出现两次的他人自传，以及“表格里列了他人学号和出生日期”的花名册。误伤的方向是把本人文档误判为他人，结果只是少索引几条，可以接受；漏判的方向不可接受。

第 1 条也是实测后补上的。一份全英文简历含电话和邮箱，但全文没有一个中文字，前面几条判据都匹配不到。它的特征是正文有独占一行的全大写节标题，同时文件名呈人名形态。

### 6.3 聊天切片不能把归属判定当门禁

聊天记录的每个切片几乎都会被判成 `other`，因为聊天一定会出现对话方的名字。拿它当门禁会把整个聊天库导空。所以导入任务只记录判定结果，不拦截。

这里有一条更通用的教训：分类器的结果要按用途决定它是门禁还是信号。在这个场景里，它是给时间线分组用的信号，不是“能不能入库”的判据。

## 7. 入库之后怎么排查遗漏

| 症状 | 先查什么 |
|---|---|
| 文档是 `ready` 但搜不到 | 三个索引集合里这个 `doc_id` 有没有点。文本通道可以用重建任务修，视觉通道要重新摄取 |
| 状态卡在中间态 | 任务是否全部进入终态。“没有待办任务却还在中间态”是不可能的状态，worker 启动时会补扫一次 |
| 某一类内容完全搜不到 | 先看该通道能力是否可用（`GET /health` 的 `available_legs`），不要先怀疑“库里没有这种数据” |
| 页数对不上 | 视觉通道是一页一个任务，所以同一文档同时存在多条未完成任务是正常状态。去重键必须包含任务负载，否则第二次调用会命中第一次那条 |
| 检索质量悄悄变差，但不报错 | 检查 BM25 的词表统计量。它在入库时增加、删除时减少，任何绕开统一删除入口的路径都会让它虚高，导致 idf 被压平，罕见词不再罕见 |

最后一条值得单独强调。“入库时加、删除时减”的统计量，必须有一个统一的减法入口。它漂移后的表现是质量下降而不是报错，所以对账里专门有一条判据：`chunks` 行数应该等于语料统计里的文档数。
