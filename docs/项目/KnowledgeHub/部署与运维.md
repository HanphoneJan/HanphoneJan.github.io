# 部署与运维

部署形态是单机自部署：三个进程加两个存储，所有服务只绑定本机地址。

本文从使用者视角讲部署和日常运维。脚本级细节，例如每个脚本的参数、蓝绿重建和对外加固清单，以 `deploy/README.md` 为准。

## 1. 基础设施

```bash
cp .env.example .env
docker compose -f deploy/docker-compose.yml up -d
curl -s http://127.0.0.1:6333/collections          # 检查 Qdrant
docker exec pkh-postgres pg_isready -U pkh         # 检查 PostgreSQL
```

| 服务 | 端口 | 绑定地址 |
|---|---|---|
| PostgreSQL | 5432 | 127.0.0.1 |
| Qdrant REST | 6333 | 127.0.0.1 |
| Qdrant gRPC | 6334 | 127.0.0.1 |

版本上有两点要说明：

- Qdrant 锁定在 `v1.15.1`。命名向量创建、多向量检索端点格式和稀疏向量字段名都踩过版本相关的坑，换版本会重新踩一遍。
- PostgreSQL 使用 `pgvector/pgvector:pg16`。装 pgvector 只是为了顺带拿到 `pg_trgm`。

如果拉取 Docker 镜像需要代理，要单独配置 docker daemon，因为 daemon 不读 shell 里的 `HTTP_PROXY`：

```bash
sudo mkdir -p /etc/systemd/system/docker.service.d
sudo tee /etc/systemd/system/docker.service.d/proxy.conf <<'EOF'
[Service]
Environment="HTTP_PROXY=http://127.0.0.1:7890"
Environment="HTTPS_PROXY=http://127.0.0.1:7890"
Environment="NO_PROXY=localhost,127.0.0.1,10.0.0.0/8"
EOF
sudo systemctl daemon-reload && sudo systemctl restart docker
```

## 2. 三个进程

```bash
bash deploy/dev.sh start      # 启动 API(8010)、worker 和视觉查询服务(8020)
bash deploy/dev.sh restart    # 修改后端代码后使用
bash deploy/dev.sh stop

bash deploy/visual.sh {start|stop|restart|status|logs}   # 单独管理视觉服务
PKH_WORKERS=4 bash deploy/dev.sh start                   # 多 worker，需要 VISUAL_WRITE_VIA_SERVICE=true
```

`dev.sh` 只有 `start`、`restart`、`stop` 三个子命令，没有 `status` 和 `logs`。

查看状态：

```bash
curl -s --noproxy '*' http://127.0.0.1:8010/health
tail -20 /tmp/pkh_api.log /tmp/pkh_worker.log /tmp/pkh_visual.log
```

视觉查询服务首次启动需要约 13 秒，要加载 colSmol，占用约 2.65 GB 内存。`dev.sh` 不会等它就绪，这段时间里视觉通道会降级为 `skipped`，检索照常工作。

如果不想装视觉服务，把 `.env` 里的 `VISUAL_SERVICE_URL` 留空即可关闭读侧，写入侧不受影响。

修改过前端要执行 `cd web && npm run build`，`dev.sh` 不会替你构建。

### 2.1 首次准备

```bash
uv run python -m services.api.scripts.create_user   # 创建账号，自助注册默认关闭
uv run python deploy/seed_photos.py                 # 初始化持久照片库，幂等
```

### 2.2 改代码之后

`uv run X` 会产生两个进程：wrapper 和真正执行 Python 的进程。只 kill 进程组 leader 杀不干净子进程，旧 worker 会继续用旧代码处理任务，症状就是“改了没生效”。

```bash
bash deploy/dev.sh restart
```

## 3. 关键环境变量

| 变量 | 作用 |
|---|---|
| `ALLOW_REGISTER` | 自助注册开关。默认开启；关闭后新建账号走本机 CLI |
| `EXPOSE_DOCS` | `/docs`、`/redoc`、`/openapi.json` 的开关。关闭后这些路由不存在 |
| `VISUAL_SERVICE_URL` | 视觉查询服务地址。留空表示关闭读侧视觉通道 |
| `VISUAL_WRITE_VIA_SERVICE` | 写入侧也调用视觉服务，默认关闭 |
| `PKH_WORKERS` | worker 数量 |
| `PKH_API_PORT` | API 端口，默认 8010 |
| `QDRANT_ALIASES` | 是否启用别名模式与蓝绿重建，默认 false |
| `IMPORT_ROOTS` | 导入路径白名单 |
| `HF_HUB_OFFLINE` / `TRANSFORMERS_OFFLINE` | 模型离线加载，`dev.sh`、conftest 和 eval 都会设置 |
| `PG_POOL_SIZE` / `PG_MAX_OVERFLOW` | 每个进程的 PostgreSQL 连接池，默认 5 加 5 |

环境变量没有前缀，因为 `Settings` 没有设置 `env_prefix`。两个安全开关默认都是开启的：本机开发、pytest 和三套 eval 都依赖自助注册，默认关闭会让基线测试全部变红。

### 3.1 连接池：并发检索的隐性预算

这里的“连接”指 API 或 worker 进程到 PostgreSQL 的连接池连接，也就是 asyncpg 的 TCP 连接，不是浏览器到 API 的 HTTP 连接，也不是 Qdrant 连接。连接池是进程级的：每个 uvicorn worker、每个 worker 进程和 CLI 各有一份。

`pg_pool_size` 默认 5，`pg_max_overflow` 默认 5，所以每个进程最多 10 条连接。一次 `hybrid` 检索最多占用 4 条，包括请求会话 1 条，dense、sparse、trgm 各 1 条。`semantic` 或 `exact` 只占用 2 条，即请求会话加一条通道。

所以池大小至少按“并发检索数 × 4 加余量”估算。池不够时症状是排队变慢，会触发 `pool_timeout`，默认 30 秒，而不是算错。极端情况下，连接都被请求会话占着，每个请求又在等通道的连接，会一直卡到超时。高并发部署要先调整这两个值，或者给多个 worker 留足每进程的池。

## 4. 内存预算

| 进程 | 常驻内存 | 峰值 |
|---|---|---|
| api | 约 400 MB | 约 600 MB |
| worker | 约 200 MB（未编码） | 约 2.8 GB（加载视觉模型后） |
| visual_service | 2.71 GB | 约 2.8 GB |
| postgres | 约 200 MB | 约 500 MB |
| qdrant | 约 300 MB | 约 800 MB |

worker 和视觉服务各自需要约 2.65 GB，同机峰值约 6 GB。15 GB 的机器够用。小机器上必须二选一：要么关闭视觉通道，要么设置 `VISUAL_WRITE_VIA_SERVICE=true`，让 worker 不再加载模型，实测内存降到约 991 MB，代价是摄取依赖视觉服务。

## 5. 十四项巡检

```bash
uv run python deploy/monitor.py            # 给人看
uv run python deploy/monitor.py --json     # 机器可读，供 cron 或 CI 使用
uv run python deploy/monitor.py --quiet    # 只在有问题时输出
uv run python deploy/monitor.py --only df index
```

退出码 0 表示正常，1 表示有问题，跳过也算有问题。

| 检查项 | 抓什么问题 |
|---|---|
| PostgreSQL 可连接 | 数据库挂了会导致全站 500 |
| Qdrant 的 `/healthz` 和可读性 | 索引挂了会导致检索降级、摄取全部失败 |
| API 的 `/health` | 进程活着但依赖坏了 |
| BM25 的 df 一致性（`n_docs` 与存活文档的 chunk 数） | 不会报错，但检索质量会悄悄变差 |
| 索引对账（`/admin/consistency` 的分通道 `legs`） | 半坏状态，例如 dense 正常而 sparse 缺失 |
| 磁盘占用 | 写满会让摄取静默失败，但上传仍然返回 202 |
| 卡住的任务（`running` 超过 30 分钟） | worker 卡住却没人知道 |
| 卡住的文档（停在中间态且没有待办任务） | 终态判定的兜底 |
| 视觉通道对账 | `VDR_ENABLED=false` 时标记为跳过，而不是报红 |
| 最近有备份（3 天内） | 事实上没有备份 |
| 其它若干项 | 队列、模型、配置一致性等 |

巡检有三种状态：通过、失败、跳过。“跳过”表示这项没法验证，最常见的原因是 `.env` 里没有配置 `PKH_MONITOR_KEY`。跳过不算健康，返回 `ok=false` 且 `counts.skipped>0`。巡检一半没跑成却报告“一切正常”，是监控工具最糟糕的失败。

cron 示例：

```bash
0 8 * * * cd /path/to/knowledge-hub && \
  uv run python deploy/monitor.py --quiet || mail -s '[PKH] 巡检异常' you@your.domain
```

退出码有意义，才有“报警”可言。`--quiet` 只影响输出，退出码照常返回。

## 6. 备份与恢复

```bash
bash deploy/backup.sh                    # 做一份备份，写完立刻自检
bash deploy/backup.sh --keep 7           # 只保留最近 7 份，默认 14 份
bash deploy/backup.sh --list             # 列出已有备份，含自检结果
bash deploy/backup.sh --verify DIR       # 只校验
```

| 内容 | 是否备份 | 理由 |
|---|---|---|
| `pg_dump -Fc` | 是 | 唯一的权威数据源 |
| `data/blobs/` | 是 | 内容寻址的原件，缺了就会变成“文档还在、文件没了” |
| Qdrant | 否 | 索引可以重建，但期望点数会记进 manifest，重建后按它对账 |

每份备份目录里都有 `manifest.json`，记录各表的精确行数、每个产物的 sha256，以及 Qdrant 各集合的点数。校验会检查文件哈希、tar 能否解开，以及 dump 里有没有 `TABLE DATA` 条目，因为空的 `-Fc` dump 也会成功退出。

```bash
# 演练，推荐每月一次
bash deploy/restore.sh --scratch data/backups/<时间戳>

# 真恢复
bash deploy/dev.sh stop
bash deploy/restore.sh --force --into pkh data/backups/<时间戳>
```

演练会校验备份完整性，创建临时库并执行 `pg_restore`，逐表核对行数，逐个校验原件的 sha256，最后删除临时库，并提示“重建索引后按 `qdrant_expect` 对账”。已经实测过一次：18 张表行数全部正确，126 个 blob 的 sha256 全部正确。

## 7. 对外访问

部署形态是：域名经 Cloudflare Tunnel 转发到本机的 `127.0.0.1:8010`。

| 事实 | 怎么验证 |
|---|---|
| 请求经过 Cloudflare 边缘 | `curl -sI https://<域名>/api/v1/health`，响应里有 `server: cloudflare` 和 `cf-ray` |
| 请求确实到达应用 | 同一个响应里有 `x-request-id` 和 `x-elapsed-ms` |
| tunnel agent 在本机手工启动 | `pgrep -a cloudflared`，能看到 `--token-file /etc/cloudflared/token` |
| 没有启用 Cloudflare Access | 不带凭证的请求会被转发到应用，不会 302 跳到 `*.cloudflareaccess.com` |

### 7.1 访问界面

`web/dist` 由 FastAPI 托管。执行 `cd web && npm run build`，再执行 `bash deploy/dev.sh restart` 就会挂载；目录不存在时不挂载，API 照常工作。

- 访问 `https://<域名>/` 打开界面，深链 `/kb/123` 和 `/settings` 刷新也正常；
- `/api/v1/*`、`/mcp`、`/a2a` 和 `/health` 是真实端点，路径打错仍然返回 404 的 JSON；
- CORS 仍然只允许 `http://localhost:5173` 和 `127.0.0.1:5173`。

### 7.2 无凭证时的状态

| 探测 | 状态 |
|---|---|
| `/api/v1/kb`、`/audit`、`/admin/*`、`/mcp` 和所有写端点 | 401 |
| `/`（登录和注册界面） | 200，因为需要使用它，必须公开 |
| `POST /auth/register` | 403 `REGISTRATION_CLOSED`，公网关闭了自助注册 |
| `POST /auth/login` | 允许，但同一 IP 在 300 秒内失败超过 10 次，或同一账号在 900 秒内失败超过 20 次，会返回 429 |
| `/docs`、`/redoc`、`/openapi.json` | 404，已经关闭 |
| `GET /health` | 200，公开版不包含队列细节 |

### 7.3 为什么不挂 Cloudflare Access

这是一次已经做出的决定，理由有三条：

1. 登录限流和 Access 无关。通过 Access 的账号照样没有次数上限。
2. 本项目是个人单用户实例，应用层已经有 API Key 鉴权，Access 只会多引入一条外部配置。
3. `/mcp` 在根路径，不在 `/api/v1` 下，Access 的 cookie 对程序无效，客户端还得额外带 Service Token。

如果以后要上 Access，清单在云隧道的 Access 文档里。生效后本机 `curl` 探测也会被挡住，验收必须在浏览器里做。

## 8. 常见故障

| 症状 | 真正原因 | 处理方式 |
|---|---|---|
| 改了代码但行为没变 | 旧 worker 子进程还在 | `bash deploy/dev.sh restart` |
| 检索返回 200，但只有 dense 的结果 | 三条数据库通道共用了会话，并发 `execute` 失败 | 查看 `/search/debug` 的 `skipped`；确认引擎为每条通道各建会话（`tests/test_leg_concurrency.py`） |
| 视觉通道一直 `skipped` | 服务还没起来、不可达，或 `VISUAL_SERVICE_URL` 为空 | 等服务预热（13 秒），或检查配置 |
| 上传返回 202 但文档不动 | 磁盘写满导致摄取静默失败 | 查看巡检的磁盘占用；清理 `/tmp` 和备份 |
| 文档停在中间态 | 没有待办任务却未进入终态 | worker 启动补扫，巡检也有“卡住的文档”一项 |
| 恢复演练提示 sha 不符 | 备份不完整或被改动 | 换一份备份，检查 `manifest.json` |
| 前端页面 401 | 页图端点需要 Bearer，但使用了 `<img src>` | 改成 `fetch` 加 blob objectURL |
| 磁盘莫名被占用 | headless Chrome 的临时 profile 泄漏，每轮约 150 MB | 清理临时目录 |
| 请求走了错误的出口 | 代理设置 | 使用 `--noproxy '*'`，或检查代理环境变量 |
