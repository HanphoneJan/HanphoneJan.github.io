# 架构总览

本文从顶层说明这套系统由哪些部分组成、为什么要这样划分，以及一次上传和一次提问分别经过什么。目标是让第一次接手代码的人先建立全局认识，具体的表结构、检索算法和权限细节放在各自的文档里。

## 1. 三个进程与两个存储

整套系统跑在一台机器上。单机自部署是明确的目标，不是临时方案：没有分片，没有副本，也没有独立的消息队列。

```
                      ┌──────────────────────────────────────┐
   浏览器 / 客户端 ──→│ api（FastAPI） :8010                 │──→ Qdrant   :6333
                      │  · 检索编排（四条通道）               │──→ PostgreSQL :5432
                      │  · 托管前端静态产物                   │
                      │  · MCP /mcp · A2A /a2a               │
                      └───────┬──────────────────────────────┘
                              │ 入队任务 / 查询进度
                              ▼
                      ┌──────────────────────────────────────┐
                      │ worker（无监听端口）                  │
                      │  · 轮询任务队列 · 摄取 · 清理         │
                      │  · 可选的视觉写入编码                 │
                      └──────────────────────────────────────┘

                      ┌──────────────────────────────────────┐
                      │ visual_service :8020                 │
                      │  · 常驻视觉编码模型，启动即预热        │
                      │  · POST /encode（文本）· /encode_image │
                      │  · 不查 Qdrant，不做租户过滤           │
                      └──────────────────────────────────────┘
```

| 进程 | 监听端口 | 职责 | 常驻内存 |
|---|---|---|---|
| `api` | 8010 | REST、SSE、MCP、A2A，托管前端，检索编排 | 约 400 MB，峰值约 600 MB |
| `worker` | 无 | 领取任务，执行解析、切分、嵌入、清理和导入 | 约 200 MB；本地加载视觉模型时峰值约 2.8 GB |
| `visual_service` | 8020 | 只做“文本或图片 → 向量”的编码 | 2.71 GB，启动即预热 |

存储方面，PostgreSQL 是唯一真相源，Qdrant 是可重建的派生索引，原始文件按内容寻址存放在本地磁盘。

## 2. 为什么视觉编码要单独一个进程

视觉模型 `colSmol-500M` 在 CPU 上的实测特性，决定了它不能和 API 跑在同一个进程里：

| 指标 | 实测值 |
|---|---|
| 模型加载 | 12.8 到 15.0 秒，常驻内存增加 2.64 GB |
| 单张图片编码 | 约 15 秒，且与分辨率无关（float32） |
| 查询文本编码 | 每条 119 到 128 毫秒，p95 为 157 毫秒 |
| 6 路并发 | 实际耗时 0.96 秒，消耗 CPU 8.36 秒，并行度 8.7 倍 |

最后一行是关键。如果视觉模型和 API 在同一个进程里，用户上传文档期间提问，视觉编码会把所有 CPU 核心占满，API 长时间没有响应。因此有一条硬约束：

> API 进程不得加载视觉编码模型。`pool.get_visual_model()` 在没有显式启用视觉编码的进程里会直接抛错。

代价是 API 进程自己无法完成视觉查询的编码。解决办法不是放宽约束，而是增加第三个进程：API 通过 HTTP 调用 `visual_service` 获取查询向量，Qdrant 查询和租户过滤仍然留在 API 侧。

### 2.1 视觉服务的边界为什么切得这么干净

`visual_service` 只接收文本或图片并返回向量。它不连接 Qdrant，也不做任何租户判定。原因是租户过滤的构造入口在全仓库只有一处（`services/common/auth.py`），如果复制进第三个进程，就会多出一份迟早会漂移的实现，而漂移的方向是越权。

因此视觉检索被拆成三步，只有第一步可能运行在远端：

| 步骤 | 运行位置 | 原因 |
|---|---|---|
| 查询文本编码为多向量 | 本进程或远端 `visual_service` | 只有这一步需要重模型 |
| 构造租户过滤条件 | 始终在 API 进程 | 过滤唯一入口，不能复制 |
| 在 Qdrant 上做 MaxSim 查询 | 始终在 API 进程 | 同上 |

这条约束由 `tests/test_visual_service.py` 守住：视觉服务里不允许出现 Qdrant 或鉴权相关代码。

### 2.2 内存预算

所有服务挤在一台 15 GB 的机器上，需要提前算清楚内存：

| 进程 | 常驻内存 | 峰值 |
|---|---|---|
| api | 约 400 MB | 约 600 MB |
| worker（不编码） | 约 200 MB | 约 2.8 GB（加载视觉模型后） |
| visual_service | 2.71 GB | 约 2.8 GB |
| postgres | 约 200 MB | 约 500 MB |
| qdrant | 约 300 MB | 约 800 MB |

worker 和 `visual_service` 各自需要约 2.65 GB，同机运行峰值约 6 GB。15 GB 的机器够用，但在 2 核 4 GB 的小机器上只能二选一。

还有第三种形态：把写入侧的编码也改成调用 `visual_service`（设置 `VISUAL_WRITE_VIA_SERVICE=true`），worker 不再自己加载模型，实测内存降到约 991 MB。这样同一台机器可以跑多个 worker，不必把 2.65 GB 乘以 worker 数量。代价是摄取从此依赖视觉服务可用，所以默认关闭。

## 3. 数据流

### 3.1 一次上传

```
文件
  → ① 上传（同步校验：扩展名白名单、大小不超过 50MB、文件头嗅探）
  → ② 按 sha256 写入 blob（内容寻址，同一份内容只存一次）
  → ③ 写入 documents 行（status=pending），并入队 ingest 任务
  → ④ worker 领取任务（FOR UPDATE SKIP LOCKED）
  → ⑤ 解析（PDF、Office、文本、图片）
  → ⑥ 执行切分策略（六选一，默认 recursive；失败退回默认并记录 note）
  → ⑦ 分层校验：格式嗅探、解析体检、切分体检
  → ⑧ PII 检出（按知识库决定是否掩码，只作用于索引侧）
  → ⑨ 文本嵌入（512 维）与 BM25 稀疏向量，写入 PostgreSQL 的 chunks 行
  → ⑩ 扫描页和照片页入队 embed_visual，多向量写入 kb_visual
  → ⑪ 终态结算：任务全部进入终态，且索引里确实有点，才置为 ready
```

第 ⑪ 步需要单独解释。`jobs.status` 和 `documents.status` 是两套状态：

- 只看任务状态，部分失败会被报成 `ready`；
- 只看索引点数，全部失败时文档会永远停在 `pending`。

所以判定必须同时看两件事。而且结算发生在任务收尾事务之外，并且不抛异常，避免一次状态写入失败把前面的模型计算一起回滚。

### 3.2 一次检索

```
客户端
  → auth：API Key → UserContext(readable_kb_ids)      ← 租户范围的唯一来源
  → routing：判断查询意图（photo / scan / table / chat / date / general）
             置信度低于 0.35 时不路由，等权处理且不过滤
  → engine：并行执行四条通道
       dense   编码查询 → Qdrant
       sparse  查 PostgreSQL 词表算 BM25 权重 → Qdrant
       trgm    在 PostgreSQL 里做 word_similarity
       visual  ① 编码（本地或远端）② 构造过滤条件 ③ MaxSim 查询
               任何一步失败，该通道标记 skipped 并给出原因，不影响其它通道
  → fusion：RRF 融合（只使用排名，不使用分数）；每路候选取 min(100, max(top_k × 3, 30))，
             融合池取 top_k × 2
  → 软删除二次过滤（PostgreSQL 已删但索引还在的点必须挡掉）
  → routing.prefer：按意图做软偏好过滤（过滤后为空则退回全部）
  → rerank：仅当该知识库配置了精排模型时执行（跨库检索一律不执行）
  → ask：组装证据 → 生成（默认抽取式）→ 校验引用（块级和页面级坐标）
```

并发这里有一个容易理解错的细节。四条通道确实是并发执行的，但三条需要访问数据库的通道（dense、sparse、trgm）各自从会话工厂拿一个独立会话，也就是各自占用一条 PostgreSQL 连接，而不是共用同一个 `AsyncSession`。

早期版本让三条通道共用一个会话，结果 SQLAlchemy 不允许并发 `execute`，sparse 和 trgm 被记成 `skipped`，`hybrid` 就静默退化成 dense 单通道。改成独立会话后并发恢复正常，代价从延迟变成了连接数：一次 `hybrid` 最多占用请求会话加三条通道，共 4 条连接，连接池要按“并发检索数 × 4”估算。

## 4. 存储分工

### 4.1 真相源与派生索引

整个系统遵循一条一致性原则：

> 允许 Qdrant 短暂不一致，绝不允许“PostgreSQL 里有而 Qdrant 里没有”。

删除文档的顺序是：

1. 修改 PostgreSQL（写入 `deleted_at`，并把 `is_current` 置为 `FALSE`），此刻立即生效；
2. 删除 blob，仅在引用计数归零时执行；
3. 入队清理任务，删除 Qdrant 里的索引点；
4. 30 天后物理清理数据库行。

检索时会用 PostgreSQL 的 `is_current` 再做一次过滤。因此即使清理任务还没跑完，被删除的文档也不会被召回。

### 4.2 为什么用三个 Qdrant 集合

Qdrant 的单个集合不支持把“匿名向量”和“命名多向量”混在一起，而系统里的三种向量表示形态本来就不同：

| 集合 | 向量形态 | 模型或算法 | 承载内容 |
|---|---|---|---|
| `kb_dense` | dense 512 维 | `bge-small-zh-v1.5` | 所有文本 chunk |
| `kb_sparse` | 稀疏向量（顶层 `sparse_vectors`） | jieba 分词加自实现 BM25 | 文本 chunk 的词元级匹配 |
| `kb_visual` | 命名向量加 128 维多向量 `max_sim` | `colSmol-500M` | 扫描件页和照片 |

三个集合的点 ID 完全一致。页级点用负的块序号避开冲突，其余点由 `(kb_id, doc_id, chunk_index)` 经 blake2b-64 哈希算出。之所以用哈希而不是自增序号，是为了能从业务键直接算出点 ID，不必先查数据库。这也是“删掉索引后用同一个脚本重建，结果仍然一致”的前提。

三个集合的 payload 结构保持一致，融合时不需要关心一条命中来自哪条通道。

### 4.3 装了 pgvector 为什么不用它存向量

镜像自带 `pg_trgm`，而子串检索需要它，所以顺带装了 pgvector。但向量没有放进 PostgreSQL，原因有两条：

- 全局只用一个嵌入模型，而 Qdrant 已经是既有选型；
- pgvector 不支持 late-interaction 多向量，与视觉通道冲突。

PostgreSQL 的职责是真相源、子串检索、任务队列和审计。

另外有一个实测结论：PostgreSQL 内置的全文分词对中文完全无效，整行会被当成一个 token，而该镜像里也没有中文分词扩展。所以 BM25 留在 Qdrant 里用 jieba 实现，PostgreSQL 只承担字符级子串搜索。

## 5. 多租户与三档可见性

- 租户的唯一来源是 API Key，请求体不接受 `user_id`；
- 三档可见性（`private`、`workspace`、`global`）必须写成三个独立分支，不能塞进一个 `IN`；
- 无权限和不存在返回同一个错误码；
- 过滤条件有两个构造入口（Qdrant 和 PostgreSQL），但两者都只读同一份 `readable_kb_ids`。

详细设计和踩过的坑见[多租户与权限](./多租户与权限.md)。

## 6. 三个对外入口，一套检索实现

```
web/ → services/api → services/common → services/retrieval → services/ingest
```

对外有三个入口：REST API、MCP（给 AI 客户端）和 A2A（给别的 Agent）。三者的检索与问答都调用 `services/retrieval/` 里的同一个入口，各自只负责协议适配。

这样做的理由不是抽象的代码复用。三套检索逻辑一旦各自演化，半年后就会出现“API 搜得到、MCP 搜不到”这类不一致，而且很难排查，因为两边看起来都正常。

这条约束由 AST 扫描保证：运行时只有一棵依赖树，“唯一一份实现”靠扫描全仓库的定义点来确认。

## 7. 刻意保留的边界

| 边界 | 现状 | 取舍理由 |
|---|---|---|
| 文件存储 | 只有本地磁盘和内容寻址 blob，没有对象存储 | 单机自部署是目标形态；blob 按 sha256 分片，同一份只存一次，引用计数归零才物理删除 |
| 原件永远保留 | PII 掩码只作用于索引侧文本，blob、预览和下载始终是原文 | 个人知识库的核心用途之一就是“搜我自己的证件号” |
| 生成层默认抽取式 | 不配置外部 LLM 时，答案句子全部摘自原文 | 隐私默认，同时引用可以 100% 核验 |
| 精排默认关闭 | 按知识库开启 | 精排只能重排候选，不能扩大召回；CPU 上处理 20 个候选需要 0.6 到 1.2 秒 |
| 不引入多节点 | 没有分片，没有副本 | 这个规模下，复杂度换不来收益 |
| 不做 OCR | 扫描件交给视觉通道 | 不引入 tesseract 这条独立链路 |
| 不使用 pdf.js | 底图使用后端渲染的页图 | 框位与服务端同源；代价是页面不能选中文字 |
