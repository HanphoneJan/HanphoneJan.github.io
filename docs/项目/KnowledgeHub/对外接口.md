# 对外接口

KnowledgeHub 对外有三个入口，共用同一套检索与问答内核。任何一个入口自己另起一份检索实现，半年后就会出现「网页搜得到、MCP 搜不到」这类两端都无报错的差异，所以检索、问答、权限各有且只有一份实现。

![HTTP、MCP、A2A 汇聚到同一套检索与问答内核](/img/knowledge-hub/interfaces-kernel.png)

## 1. 三个入口

| 入口 | 传输 | 能力 | 内核函数 |
|---|---|---|---|
| HTTP | REST + SSE | 82 个契约端点 | `engine.search`；`ask.prepare` + `stream_answer` |
| MCP | `POST /mcp`，Streamable HTTP，无状态 | 4 个工具 | 同上 |
| A2A | `GET /.well-known/agent-card.json`、`POST /a2a/tasks` | `answer`、`research` 两个 skill | 同上 |

MCP 与 A2A 挂在根路径，不在 `/api/v1` 之下。原因：MCP 客户端按固定路径找服务端点，A2A 的 Agent Card 是规范写死的发现路径。三个入口用同一个 Bearer API Key、同一份 `UserContext.readable_kb_ids`。

## 2. HTTP

基址 `/api/v1`，除 `/health` 与 `/auth/*` 外都要 Bearer Token。

契约文件是源码仓库的 `docs/DESIGN-API.md`，`eval/contract_check.py` 逐条对账：

```
契约声明 82 个端点 · 实现 81 个 operation（其中 1 个已决议不做）
覆盖率 81/82（实现里有 0 个契约没写）
```

`POST /api/v1/jobs/{id}/retry` 是决议不做的那个：文档级 `POST /documents/{id}/retry` 已是唯一重试入口，给 job 再开一条，同一次摄取就有了两个入口，入队去重只能覆盖其中一个。

错误响应统一形状：

```json
{
  "error": {
    "code": "KB_NOT_FOUND",
    "message": "资源不存在或无访问权限",
    "detail": {"kb_id": 999},
    "request_id": "req_..."
  }
}
```

错误码分层见《多租户与权限》§4（操作级 `FORBIDDEN` 与资源级 `KB_NOT_FOUND` 的分界）。

分页形状不统一：一部分端点返回 `{items, total, page, page_size}` 包，一部分返回裸数组。裸数组也接受这两个参数，只是丢掉 `total`。新端点一律用分页包。把历史端点改成包属于破坏性变更。

SSE 固定用于 `POST /ask` 与 `POST /kb/{id}/ask`，帧序 `sources → delta* → done`，响应带 `X-Accel-Buffering: no`（防 nginx 把增量攒到结束才吐）。`stream=false` 仍返回 SSE，只是一个 `delta`——三种客户端共用一条响应格式。

检索三个端点：单库 `POST /kb/{id}/search`、跨库 `POST /search`、调试 `POST /kb/{id}/search/debug`。调试块与 `include_debug=true` 共用同一个 `_debug_block`，形状一致。

文件预览三个形态：

| 请求 | 返回 |
|---|---|
| `GET /documents/{id}/preview` | 预览文件本身（PDF 原件、图片原件、Office 转换版） |
| `?page=n` | 该页 JPEG |
| `?chunk_index=k` | 画出坐标框的该页 JPEG |

Office 返回的是转换版，响应头 `X-Preview-Source: converted` 如实标注。DOCX / XLSX / PPTX 的坐标由 `pdf_preview` 任务补，没跑完时带框预览返回 415 与说明（先看任务状态），不是 500——那个 415 指向的是可修的依赖，不是接口故障。

## 3. MCP

协议方法覆盖 `initialize` / `notifications/initialized` / `ping` / `tools/list` / `tools/call`。未知方法回 `-32601`。四个工具：

| 工具 | 参数 | 说明 |
|---|---|---|
| `list_kb` | — | 列出调用者有权限的 KB |
| `search_kb` | `kb_id`、`query`、`top_k`、`mode` | 三路 RRF 检索 |
| `ask_kb` | `kb_id`、`question`、`top_k`、`session_id` | RAG 问答，非流式 |
| `get_document` | `kb_id`、`doc_id`、`limit` | 文档元信息 + 前 N 个 chunk |

传输层的三个决定：

1. **无状态**。不实现 `Mcp-Session-Id`：鉴权是每请求自带，没有会话状态可维持。
2. **响应是 `application/json`**。单条请求直接回 JSON，不包 SSE 帧。协议错误也回 HTTP 200（错误在 body 的 `error` 里），只有「根本不是 JSON-RPC」（`-32700` / `-32600`）才回 400——客户端库会把 HTTP 4xx 当传输层故障处理，那样 `error.code` 就丢失了。
3. **权限裁剪做两处**。`tools/list` 的 `kb_id` schema 用 `enum` 只列有权限的库（提前给模型正确的取值域）。`tools/call` 仍走 `assert_kb_access`——只做第一处，客户端改一次入参就能越权。

一个库都没有时，三个带 `kb_id` 的工具不出现，`list_kb` 仍返回空列表。给一个空 `enum` 让调用方必失败，不如直接说明当前没有可用库。

错误分两层：

| 情况 | 落点 |
|---|---|
| 未知方法 / 未知工具 | `-32601` |
| 参数不合法（缺必填、类型错、越界、未知参数、enum 不符） | `-32602`，message 形如 `search_kb: 缺少必填参数 kb_id` |
| 库不存在 / 无权限 | `result.isError=true` + `{"error":"KB_NOT_FOUND"}` |
| 未预期异常 | `-32603` |

参数错是协议错、业务失败是结果失败，两层分开：混在一起时，模型会把「我少传了一个参数」误读成「这个库不存在」，然后换一个不存在的 `kb_id` 反复试。

`top_k` 越界在 MCP 侧报错、不夹取——schema 已写上限，悄悄改成 50 会把「我要 80 条」变成「我拿到 50 条」而无人察觉。HTTP 侧对同一参数夹取，因为那边是给人调用的。

工具结果一律是 JSON 字符串塞进 `content[0].text`。MCP 客户端必须支持 `text` 类型。自造内容类型会被客户端当未知类型丢弃，表现为「调用成功但没有内容」。

## 4. A2A

| skill | 用途 | 实现 |
|---|---|---|
| `answer` | 单轮查资料，答案带 `[n]` 引用 | `ask.prepare` + `stream_answer(one_shot=True)` |
| `research` | 多角度检索，按文档分组给摘录 | 同一内核，`top_k` 放宽到 30 |

`research` 的定位要写清：它不做「让 LLM 规划多轮检索」这件事。默认生成层是抽取式、本机不配 LLM、数据是私人的，所以多角度由固定逻辑完成——命中先按文档分组，每份文档保留最相关的两句摘录并标出处，最后的综合交给调用方。

| 参数 | 值 |
|---|---|
| `RESEARCH_TOP_K` | 30 |
| `MAX_RESEARCH_DOCS` | 10 |
| 每份文档摘录句数 | 2 |
| 返回标记 | `extractive: true`；超出 10 份时 `truncated` 标记 |

`POST /a2a/tasks` 收两种入参，同走一个内部函数。只收协议形状的入参（JSON-RPC 信封）会让手测与排障都变难：

```jsonc
// 协议面
{"jsonrpc":"2.0","id":1,"method":"tasks/send",
 "params":{"skill":"answer","kb_id":88,
           "message":{"parts":[{"kind":"text","text":"…"}]}}}
// 便捷面（curl / 手测）
{"skill":"answer","kb_id":88,"query":"…"}
```

响应是 A2A Task 对象。读取路径按真实结构来，不是按直觉：

| 内容 | 位置 |
|---|---|
| 正文 | `artifacts[0].parts[0].text`，没有顶层 `answer` 字段 |
| 来源列表 | 顶层 `metadata.sources`，`idx` 与正文 `[n]` 对应 |
| 引用角标 / 悬空角标 | `artifacts[0].parts[0].metadata.citations` / `dangling_citations` |
| research 的按文档明细 | 顶层 `metadata.documents` |

`kb_id` 必填。Agent Card 刻意不列可用值——那是权限信息。`capabilities.streaming=false` 是如实声明，端点确实非流式。无权限与不存在同码 403。

Agent Card 的 `inputSchema` / `outputSchema` 必须与真实响应对得上：`tests/test_a2a_skill_schemas.py` 拿真实调用逐字段核对，否则它就是第二份契约，时间一长相撞。

## 5. 三方共用的一致性

| 内核 | 说明 |
|---|---|
| 检索唯一 | `services/retrieval/`，任何入口自己拼 Qdrant 查询或 SQL 子串查询都是架构错误 |
| 问答唯一 | MCP 的 `ask_kb` 与 A2A 的 `answer` 都调 `stream_answer(one_shot=True)`，解析 SSE 帧回结构化结果 |
| 权限唯一 | 都走 `ctx.readable_kb_ids` 与 `assert_kb_access`，不重算三档 |
| 审计统一 | `tools/call` 记 `mcp_call`，A2A 每任务记 `a2a_call`，HTTP 检索/问答记 `search` / `ask` |

审计在开流之前提交：检索失败时不能跟着回滚，否则失败的尝试在审计表查不到。MCP 只审计 `tools/call`，`tools/list` 不带查询也不改数据，记它只会把审计表淹没在「列了一次工具」这类噪声里。

## 6. 不声明做不到的能力

| 不做 | 原因 |
|---|---|
| MCP 的 resources / prompts / logging | 声明了客户端就会来用，而这些没有实现 |
| A2A 的流式与 push notification | `capabilities` 必须反映实际实现 |
| `/jobs/{id}/retry` | 文档级重试端点已覆盖 |
| 在 Agent Card 或 `tools/list` 列「存在但无权」的库 | 等于给调用方探测权限边界 |

`capabilities.streaming=false` 与 `research` 的 `extractive: true` 是同一原则的两个实例：能力声明只说做了什么，不假装更多。
