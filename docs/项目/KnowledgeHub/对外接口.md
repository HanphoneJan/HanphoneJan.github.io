# 对外接口

> **阅读目标**: 三个入口各自的协议形状、错误码怎么分层，以及哪些东西三个入口必须共用一份实现。

---

## 1. 三个入口与一个内核

![HTTP、MCP、A2A 汇聚到同一套检索与问答内核](/img/knowledge-hub/interfaces-kernel.png)

| 入口 | 传输 | 能力 | 内核 |
|---|---|---|---|
| HTTP | REST + SSE | 82 个契约端点 | `engine.search` / `ask.prepare` + `stream_answer` |
| MCP | `POST /mcp`，Streamable HTTP，无状态 | 4 个工具 | 同上 |
| A2A | `GET /.well-known/agent-card.json`、`POST /a2a/tasks` | `answer`、`research` | 同一 `ask` 内核 |

MCP 与 A2A 挂在根路径，不在 `/api/v1` 下。MCP 客户端按固定路径找 `/mcp`，A2A 的 Agent Card 是规范写死的发现路径。

三个入口用同一个 Bearer API Key，同一套 `UserContext.readable_kb_ids`。任何一方想自己拼 Qdrant 查询或 SQL 子串查询，都会让半年后出现"网页搜得到、MCP 搜不到"这类两边都不报错的差异。

## 2. HTTP 的形状

基址 `/api/v1`，除 `/health` 与 `/auth/*` 外都要 Bearer Token。契约在源码仓库的 `docs/DESIGN-API.md`，`eval/contract_check.py` 逐条对账：

```
契约声明 82 个端点 · 实现 81 个 operation（其中 1 个已决议不做）
覆盖率 81/82（实现里有 0 个契约没写）
```

`POST /api/v1/jobs/{id}/retry` 是决议不做的那一个。重试入口是文档级 `POST /documents/{id}/retry`；给 job 再开一条重试路径，同一次摄取就有两个入口，去重语义只能覆盖其中一个。

错误响应统一：

```json
{
  "error": {
    "code": "KB_NOT_FOUND",
    "message": "资源不存在或无访问权限",
    "detail": {"kb_id": 999},
    "request_id": "req_..."
  }
}
```

分页不统一：一部分端点返回 `{items, total, page, page_size}`，一部分返回裸数组。裸数组也接受 `page` / `page_size`，只是丢掉 `total`。新端点一律用分页包；把历史端点改成包属于破坏性变更。

SSE 固定在 `POST /ask` 与 `POST /kb/{id}/ask`，帧序 `sources` → `delta`* → `done`。响应头带 `X-Accel-Buffering: no`，避免 nginx 把增量攒到结束才吐。`stream=false` 仍然返回 SSE，只是 `delta` 只有一帧。

检索三个端点：单库、跨库、单库调试。`mode` 只控制文本三腿，视觉腿由服务可用性决定。`include_debug=true` 与 `/search/debug` 共用同一个 `_debug_block`，形状一致。

文件预览有三个形态：

| 请求 | 返回 |
|---|---|
| `GET /documents/{id}/preview` | 预览文件本身（PDF 原件、图片原件、Office 转换版） |
| `?page=n` | 该页的 JPEG |
| `?chunk_index=k` | 把坐标框画进页图的 JPEG |

Office 返回的是转换版本，响应头 `X-Preview-Source: converted` 如实标注。DOCX / XLSX / PPTX 的坐标由预览任务补，没跑完时带框预览返回 415 并说明去看任务状态，不是 500。

## 3. MCP：四个工具与两层权限

`initialize` / `notifications/initialized` / `ping` / `tools/list` / `tools/call`。未知方法回 `-32601`。

| 工具 | 参数 | 说明 |
|---|---|---|
| `list_kb` | — | 列出调用者有权限的 KB |
| `search_kb` | `kb_id`、`query`、`top_k`、`mode` | 三路 RRF 检索 |
| `ask_kb` | `kb_id`、`question`、`top_k`、`session_id` | RAG 问答，非流式 |
| `get_document` | `kb_id`、`doc_id`、`limit` | 文档元信息 + 前 N 个 chunk |

传输层三个决定：

1. **无状态**：不实现 `Mcp-Session-Id`。鉴权是每请求自带的 Bearer Key，没有会话状态要维护。
2. **响应是 `application/json`**：单条请求直接回 JSON，不必包成 SSE 帧。协议错误也回 HTTP 200（错误在 body 的 `error` 里），只有"根本不是 JSON-RPC"（`-32700` / `-32600`）才回 400。客户端库会把 HTTP 4xx 当传输故障，那样拿不到 `error.code`。
3. **权限裁剪两处**：`tools/list` 的 `kb_id` schema 用 enum 只列有权限的库；`tools/call` 仍然走 `assert_kb_access`。只靠第一处，改一次客户端入参就能越权。

一个库都没有时，三个带 `kb_id` 的工具不出现，`list_kb` 仍然返回空列表。给一个空 enum 让调用方每次调用都失败，不如直接告诉它现在没有可用的库。

错误分两层：

| 情况 | 落点 |
|---|---|
| 未知方法 / 未知工具 | `-32601` |
| 参数不合法（缺必填、类型错、越界、未知参数、enum 不符） | `-32602`，message 形如 `search_kb: 缺少必填参数 kb_id` |
| 库不存在 / 无权限 | `result.isError=true` + `{"error":"KB_NOT_FOUND"}` |
| 其它未预期异常 | `-32603` |

参数错是协议错，业务失败是结果失败。混在一起，模型会把"我少传一个参数"误读成"这个库不存在"，然后换一个不存在的 `kb_id` 反复试。

`top_k` 越界在 MCP 侧报错而不是夹取：schema 已经写明上限，悄悄改成 50 会让"我要 80 条"变成"我拿到 50 条"而无人察觉。HTTP 侧仍是夹取，因为那里是给人调用的。

工具结果一律是 JSON 字符串塞进 `content[0].text`。MCP 客户端必须支持 `text` 内容类型，自造类型会被当未知类型丢掉，表现为"调用成功但没有内容"。

## 4. A2A：两个 skill 与响应路径

| skill | 用途 | 实现 |
|---|---|---|
| `answer` | 单轮查资料，答案带 `[n]` 引用 | `ask.prepare` + `stream_answer(one_shot=True)` |
| `research` | 多角度检索，按文档分组给摘录 | 同一内核，`top_k` 放宽到 30 |

`research` 不是"让 LLM 规划多轮检索"。默认生成层是抽取式，本机没有 LLM，内容是私人数据。它做的是可解释的多角度汇总：把命中按文档分组，每份文档给出最相关的两句摘录与出处，调用方自己综合。

| 参数 | 值 |
|---|---|
| `RESEARCH_TOP_K` | 30 |
| `MAX_RESEARCH_DOCS` | 10 |
| 每份文档摘录句数 | 2 |
| 返回标记 | `extractive: true`，`truncated` 表示是否被文档数上限截断 |

`POST /a2a/tasks` 收两种入参，都走同一个内部函数：

```jsonc
// 协议面
{"jsonrpc":"2.0","id":1,"method":"tasks/send",
 "params":{"skill":"answer","kb_id":88,
           "message":{"parts":[{"kind":"text","text":"…"}]}}}
// 便捷面（curl / 手测）
{"skill":"answer","kb_id":88,"query":"…"}
```

只收协议形状会让手测与排障都变难，所以两种都支持。

响应是 A2A Task 对象。读取路径要按真实响应来，不能按直觉：

| 内容 | 位置 |
|---|---|
| 正文 | `artifacts[0].parts[0].text`，没有顶层 `answer` |
| 引用来源 | 顶层 `metadata.sources`，`idx` 与正文 `[n]` 对应 |
| 引用角标与悬空角标 | `artifacts[0].parts[0].metadata.citations` / `dangling_citations` |
| research 的按文档明细 | 顶层 `metadata.documents` |

`kb_id` 必填。Agent Card 刻意不列出可用值，那是权限信息。`capabilities.streaming=false` 是如实声明，端点确实非流式。无权限与不存在同码 403。

Agent Card 的 `inputSchema` / `outputSchema` 必须与真实响应对应。`tests/test_a2a_skill_schemas.py` 拿真实调用逐字段核对，否则它就是第二份契约，会与真实响应不一致。

## 5. 三方共用的边界

- **检索唯一**：`services/retrieval/`。任何一方自己拼 Qdrant 查询或 SQL 子串查询，就是架构性错误。
- **问答唯一**：MCP 的 `ask_kb` 与 A2A 的 `answer` 都调 `stream_answer(one_shot=True)`，再把 SSE 帧解析回结构化结果。少一条响应格式，就少一条会漂的路径。
- **权限唯一**：两边都读 `ctx.readable_kb_ids`，都走 `assert_kb_access`，不重算三档可见性。
- **审计**：`tools/call` 记 `mcp_call`，A2A 每个任务记 `a2a_call`，HTTP 检索与问答记 `search` / `ask`。

审计在开流之前提交。检索失败时不能跟着回滚，否则失败的尝试在日志里查不到。MCP 只审计 `tools/call`：`tools/list` 不带 query 也不改数据，记它只会让审计表被"列了一次工具"这类噪声淹掉。

## 6. 不声明做不到的能力

| 不做 | 原因 |
|---|---|
| MCP 的 resources / prompts / logging | 声明了客户端会尝试用，而这些调用没有实现 |
| A2A 流式与 push notification | 能力声明要反映实际实现 |
| `/jobs/{id}/retry` | 重试入口已有文档级端点 |
| 在 Agent Card 或 `tools/list` 里列"存在但无权"的库 | 等于让调用方探测权限边界 |

`capabilities.streaming=false` 与 `research` 的 `extractive: true` 是同一件事的两个例子：说清自己做了什么，不假装有更强的能力。
