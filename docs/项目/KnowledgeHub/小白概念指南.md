# 小白概念指南

## 1. 三种检索范式

信息检索按「怎么表示文档、怎么打分」分三条路线，这个项目四条腿里的三条各属一条。

| 路线 | 表示 | 打分 | 训练 | 强项 | 短板 |
|---|---|---|---|---|---|
| 稀疏（BM25） | 词表维度上的权重向量，绝大多数为 0 | 词权重相加 | 不需要 | 精确匹配、可解释、便宜 | 词汇鸿沟：换个说法就搜不到 |
| 稠密（双塔） | 低维实数向量（512 维） | 余弦/内积 | 需要 | 语义泛化、跨说法 | 数字串与生僻专名、需要 ANN 索引 |
| 多向量（late interaction） | 每个 token 一个向量 | 逐 token 取最大再求和 | 需要 | 细粒度、接近精排 | 存储放大、打分慢 |

另外两种不属于「召回」但常被混着问：**cross-encoder 精排**（query 与 doc 拼起来过一遍模型，只用于重排少量候选）、**trgm 子串匹配**（Postgres 按 trigram 重合度打分，是字符级相似度，不是检索模型）。

本项目的对应关系见《检索与问答》§1。

## 2. BM25

### 2.1 它是什么

Okapi BM25 是 1990 年代 TREC 评测里胜出的概率检索模型，把「文档与查询的相关性」拆成三个可独立调节的信号：词在文档里出现几次、词在全库有多稀有、文档有多长。Elasticsearch、Lucene、Solr 的默认相似度函数就是它的变体（`BM25Similarity`）。

### 2.2 相对 TF-IDF 修正了什么

TF-IDF 的两个假设不符合实际：

1. **词频线性增长**：出现 2 次的相关性是 1 次的 2 倍。真实分布里，一篇讲「算法」的文章提到 10 次和 5 次，相关性差不了多少——第 6 次之后信息量迅速衰减。
2. **长度不加区分**：5000 字的长文提到某个词一次，与 200 字的短文提到一次，后者证据强度高得多，因为前者天然更容易「顺带」提一句。

BM25 用两个参数分别修正：`k1` 控制词频饱和，`b` 控制长度归一化。

### 2.3 公式

```
score(D, Q) = Σ_{q∈Q} IDF(q) · tf(q,D)·(k1+1)
              ─────────────────────────────────────────────
              tf(q,D) + k1·(1 - b + b·|D|/avgdl)
```

- `tf(q,D)`：词 `q` 在文档 `D` 里的出现次数
- `|D|`：文档长度（通常按 token 数），`avgdl`：全库平均长度
- `IDF(q)`：词的稀有度权重
- `k1`、`b`：两个可调参数

IDF 有多种写法，Lucene 用的是

```
IDF(q) = ln(1 + (N - df(q) + 0.5) / (df(q) + 0.5))
```

`N` 是文档总数、`df` 是包含该词的文档数。`ln(1 + …)` 这一层是为了让 idf 恒为正：经典写法 `log((N-df+0.5)/(df+0.5))` 在词出现在超过一半文档时会变负，把总分往下拉，Lucene 用加一取对数绕开它。

另一个常被追问的点：**BM25 的 `tf` 不是原始次数**。分母里的 `tf + k1·…` 让贡献上界收敛到 `k1+1`，这就是「饱和」。

### 2.4 两个参数怎么理解

| 参数 | 典型取值 | 调大 | 调小 |
|---|---|---|---|
| `k1` | 1.2 ~ 2.0（Lucene 默认 1.2） | 饱和更慢，词频影响接近线性 | 饱和更快；`k1→0` 退化成「出现过 / 没出现过」的二值模型 |
| `b` | 0 ~ 1（默认 0.75） | 长度惩罚更重；`b=1` 完全按长度归一化 | 忽略长度；`b=0` 长文档不再吃亏 |

`b=1` 的副作用：同内容被切成不同大小块时，分数完全由块长决定，切分策略的差异会直接变成排序差异。`k1` 过大则堆砌关键词重新有效。

**本项目的取值见 `services/retrieval/bm25.py`**，不在文档里写死，改了不用回来同步。

### 2.5 复杂度与代价

打分只碰查询词对应的倒排表（posting list），复杂度约 `O(|Q| · 命中数)`，与全库文档数无关。这是它比稠密检索便宜的根本原因：稠密检索要为每个查询做一次 ANN 搜索，且需要 GPU/CPU 前向编码 query。

但 BM25 有两个绕不开的成本：

- **需要全局统计**：`df` 与 `avgdl` 是全库量，必须随入库、删除、重建一起维护。
- **增量会漂移**：新文档进来 `N` 变大、`df` 变化，旧文档的 idf 随之微调，而已经写进索引的权重不会自动重算。漂移到一定程度要重建索引。

本项目的落地就是这两张表：`terms` 存词的 `df` 与 id，`corpus_stats` 存 `N` 与 `avgdl`（见《数据与一致性》§1）。删除文档时必须把 token 从词表减回去——漏了不会报错，只是 `df` 只增不减、idf 被压平，检索质量慢慢变差（见《数据与一致性》§5）。

中文场景还有一层：分词粒度直接决定 `df` 与召回。「成本核算」切成一个词还是两个词，命中与不命中是两回事。所以入库与删除必须用同一个分词函数。

### 2.6 怎么判断调对了

参数改完要有对照，否则只是换了一组主观数字。检索常用三个指标：

| 指标 | 回答的问题 |
|---|---|
| recall@k | 该找到的 k 个里找回了几个（召回够不够） |
| MRR | 第一个正确结果排在第几名（头部质量） |
| nDCG@k | 带相关度分级的排序质量（相关性有强弱之分时） |

BM25 的典型失败不是「排错了」而是「根本召回不到」（分词不对、词表没登记），所以先看 recall@k，再看 MRR。本项目的评测入口在 `eval/`。

## 3. 稠密检索

### 3.1 双塔与余弦

双塔（bi-encoder）把 query 和文档**分别**编码成向量，打分只做一次点积。关键性质是文档向量可以离线算好塞进索引，查询时只编码一次 query——这是它能在毫秒级响应里跑全库的原因。

余弦相似度衡量方向夹角：

```
cos(a, b) = a·b / (|a|·|b|)
```

向量先做 L2 归一化（`|a|=|b|=1`）之后，余弦等价于内积，内积检索与余弦检索可以互换。这就是很多论文里两者混用的原因。

### 3.2 ANN：用召回率换延迟

精确最近邻是 `O(N·d)`，全库扫一遍不可能。实际系统用近似最近邻（ANN）：

| 索引 | 结构 | 关键参数 | 权衡 |
|---|---|---|---|
| HNSW | 多层可导航小世界图 | `M`（每层邻居数）、`efConstruction`、`efSearch` | `efSearch` 越大召回越高、越慢；内存换速度，工业界默认选择 |
| IVF | 先聚类再只搜最近几个簇 | `nlist`、`nprobe` | `nprobe` 越大召回越高；需要训练，数据分布漂移要重训 |
| PQ | 分段量化压缩 | 段数、每段比特 | 存储降一到两个数量级，精度有损 |

面试里常见追问是「ANN 的召回率怎么评估」：拿精确检索的 top-k 当基准，算 recall@k；召回率掉下来优先调 `efSearch`/`nprobe`，而不是换模型。

### 3.3 稠密的边界

- **输入有上限**：bge 系列单次最多 512 token，超长内容会被截断（本项目的 `late` 策略就受这条约束，见《文档摄取》§3）。
- **数字串与生僻专名不敏感**：tokenizer 切碎了，语义空间里「工号 A1234」和「工号 A1235」几乎重合。
- **不可解释**：给出的是距离，说不出「因为哪个词命中」。

这三条正是 sparse 与 trgm 存在的理由。

维度本身也是一个取舍：索引内存与检索算力大致正比于 `d`，512 维相对 768/1024 维省一半以上，代价是表达能力弱一点。本项目选小尺寸的直接原因是它要常驻在每个进程里（见《架构与进程》§4）。

## 4. 混合检索与 RRF

### 4.1 为什么不能直接把分数相加

不同腿的分数分布不同量纲、不同形状：余弦集中在 0.2~0.9、BM25 可以到几十且随语料规模变化、trgm 的 `word_similarity` 只在 0.25 以上有值。直接加权求和的实际效果是「数值天生大的那条腿说了算」，而不是「更准的那条腿说了算」。

分数校准（min-max 归一化、z-score）能缓解，但每批候选的分布不同，归一化参数本身成了新的不确定来源。

### 4.2 RRF 只看名次

Reciprocal Rank Fusion（Cormack 等，2009）：

```
score(d) = Σ_{leg} w_leg / (k + rank_leg(d))
```

`rank` 从 1 开始，`k` 是平滑常数，原论文取 60。它只用排名，因此天然跨量纲；一个结果被多条腿同时排前面就累加得多。

`k` 的作用是压头部差距。`k=60` 时：

| rank | 1/(60+rank) |
|---|---|
| 1 | 0.01639 |
| 2 | 0.01613 |
| 3 | 0.01587 |
| 5 | 0.01538 |

相邻名次只差约 1.6%，所以「第二条腿也认它」几乎总能压过「第一条腿多给一名」。`k` 调小会让单腿头部更强势，调大则趋于「被几条腿同时提到」的投票。

### 4.3 与学习型融合的分界

RRF 不需要标注、不需要训练、加一条腿零成本，这是它在本项目里成立的原因。它的上限也在这里：不会学到「照片类查询该重视觉」。

更上一档是 learning-to-rank：用点击或人工标注训练一个融合模型，或者直接做分数校准加线性加权。代价是要标注数据和离线评估集，且新腿加入要重训。

本项目的折中是**在路由层换权重**：先按 query 意图分类，再给不同腿不同 `w`，融合仍然用 RRF（见《检索与问答》§4）。照片类权重是实测出来的——等权时照片进不了池子，权重加大到某个值后池子装满，再大不涨。

## 5. 精排（cross-encoder）

双塔的问题在于 query 与文档在编码阶段互不知道对方，交互被压缩成一次点积。cross-encoder 把两者拼成一个输入过模型，让注意力在每个 token 之间交互，精度显著更高。

代价是**不能预计算**：每个 (query, doc) 对都要一次前向，`n` 个候选就是 `n` 次推理。所以它只能放在召回之后，对 top-k 重排，k 通常几十。

这条约束直接决定参数：单对耗时 × 候选数 = 额外延迟。本项目单对耗时的量级见《架构与进程》§4，所以候选上限必须小、`top_k` 不能开大。

两个面试常问的边界：

- **精排救不回召回**：真值不在候选里，精排只能重排已有项。
- **精排也要截断**：模型有最大长度，长文档会被截断，截断位置之外的证据对精排不可见。

## 6. 多向量与 MaxSim（late interaction）

ColBERT 的思路是保留 token 级表示：

```
score(q, d) = Σ_{i∈q} max_{j∈d} q_i · d_j
```

每个 query token 去文档里找最像的那个 token，取最大值，再对 query 求和。这比「整篇压成一个向量」保留了细粒度——「页面上某个小表格里的某一列」这种局部证据不会被平均掉。

用 `max` 而不是 `mean` 的原因是语义：`max` 近似回答「文档里有没有一处和这个词高度对应」，`mean` 会被文档长度和无关 token 稀释。代价是 `max` 有噪声放大效应，长文档里出现一个偶然极值就能拉高分数。

三种交互方式的对照：

| 方式 | 交互时机 | 存储 | 精度 | 典型用途 |
|---|---|---|---|---|
| 双塔 | 只比最后的单向量 | 1 个向量/文档 | 低 | 大规模召回 |
| late interaction | 打分时逐 token 交互 | N 个向量/文档 | 中高 | 细粒度召回 |
| cross-encoder | 编码时就全交互 | 不存 | 最高 | 精排 |

代价很实在：存储是 `N × d`，`N` 是文档的 token 数（视觉里是 patch 数），打分是 `|q| × N` 次点积。所以它通常配合降维（ColBERT 用 128 维而非 768）与量化使用，并且只对**页级**这种数量有限的对象建索引。

本项目的 `kb_visual` 就是这一形态：一页图对应一组 128 维向量，距离用 `max_sim`（见《架构与进程》§3）。

**为什么扫描件走视觉而不是 OCR**：OCR 会丢版面（表格行列、图注位置），识别错误又不可逆；而引用要能画框回到原页。视觉索引直接用页图，引用落在页上，误差只剩「这一页对不对」。

## 7. 点 ID：内容寻址

### 7.1 为什么不用自增

自增号是存储状态，重建索引就变。随之出现的问题：外部引用（缓存、标注、反馈）全部错位；三个 collection 各自自增则同一个 chunk 在三处 id 不同，融合时要多一张映射表；增量更新时插入顺序一变，后面所有 id 漂移。

哈希是三元组的纯函数：同样的 `(kb_id, doc_id, chunk_index)` 在任何机器、任何时刻都算出同一个 64 位整数。于是 `upsert` 天然幂等，重建不换号，三条腿天然对齐。

### 7.2 三个实现细节

- **编码必须无歧义**：`(1, 23, 4)` 与 `(12, 3, 4)` 不能拼成同一个输入。用固定宽度二进制拼接（`u32 || u64 || i64`），不要用 `"1-2-3"` 这种字符串拼接。
- **右移一位**：Qdrant 的 id 是 uint64，但客户端链路里它常被当有符号 64 位或更窄的类型处理（protobuf `int64`、Java 没有 `unsigned long`、JS `Number` 只有 53 位精度）。右移一位把值压进 `[0, 2^63)`，牺牲 1 bit 熵换跨语言序列化安全。
- **负数做命名空间**：页级点用 `chunk_index = -(page_no + 1)`，保证页级点永远为负、块级点永远非负。直接用 `-page_no` 会让第 0 页与第 0 块撞号。

### 7.3 碰撞概率

`n` 个点落在 `2^63` 空间里的生日碰撞期望约 `n² / 2^64`：

| 点数 | 碰撞概率量级 |
|---|---|
| 10^6 | 5 × 10^-8 |
| 10^8 | 5 × 10^-4 |

百万级可以忽略；真要上十亿级，要么换 128 位（Qdrant 也支持 UUID），要么在检测到写冲突时加盐重算。

### 7.4 前提条件

点 ID 能复算的前提是**块序号稳定**：`chunks` 上有 `UNIQUE (doc_id, chunk_index)`，同一份内容切出来的块序号不变。改切分策略后必须重摄取，否则同一个块会算出新号、旧点成为孤儿（见《数据与一致性》§3、§6）。

## 8. 引用溯源与坐标

「点回原文」需要三层信息：哪份文档、哪一页、页面上哪个框。

- **L1**：文档 id，落在 `documents` 行上。
- **L2**：页号，PDF 与扫描件才有。
- **L3**：框，`bbox` 归一化到 `0~1`，乘回渲染尺寸即可画框——分辨率、缩放、DPI 都无关。

坐标来自 PDF 的文本层：PyMuPDF 给出每个 block/word 的 bbox，按阅读顺序（多栏要自己排）合并成段落/表格的框。表格块精确到非空单元格并带 `row`/`col`，这样「表头第三列」能高亮到格子而不是整张表。

扫描件没有文本层，坐标退化成整页；这也是为什么它必须走视觉索引——没有位置信息就没有 L3。

为什么不用字符偏移（`char_start` / `char_end`）做引用：偏移只对纯文本有意义，PDF 的换行、分栏、页眉页脚都要单独还原；而且 PII 掩码会改变文本长度，掩码后的偏移与原页对不上。bbox 不受这两件事影响。

工程上两个约束：单页框数要封顶（前端渲染几百个框会卡），跨页不合并（否则点一次引用会画出多页的框）。

## 9. 软删与删除链

删除拆两步是索引型系统的常规做法：**逻辑删除**先让检索看不见，**物理删除**延迟到某个安全窗口之后再真删。

原因是物理删除不可逆且跨系统：Postgres 的行可以事务回滚，Qdrant 的点不行，磁盘上的文件更不行。一旦在三者之间出现半完成状态，你要么丢了还需要的文件，要么留下永远删不掉的向量。

本项目的顺序是六步，每一步漏掉都不报错：减词表 `df` → 删三个 collection 的点 → 删行（`chunks`/`jobs` 靠 `ON DELETE CASCADE`）→ `blobs.ref_count` 减一 → 归零才删目录 → 不动审计。顺序不能换：先删行就不知道要减哪些 `df`，先删容器就找不到它下面的文档（见《数据与一致性》§5）。

软删与索引之间必然有一段不一致：`deleted_at` 写进 Postgres 之后，Qdrant 里的点要等清理任务才删。兜住它的是检索侧的二次过滤（`is_current AND deleted_at IS NULL`）——先让结果看不见，再让存储慢慢对齐。这个窗口的长度与兜底机制见《数据与一致性》§7.2。

内容寻址的 `ref_count` 是为了去重：同一份内容被多个文档版本引用时只存一份，减到 0 才真删。少减一次是磁盘只增不减，多减一次是删掉别人还在用的文件。

## 10. 术语速查

| 术语 | 说明 |
|---|---|
| 稀疏检索 | 词表维度上的权重向量，绝大多数维度为 0 |
| BM25 | Okapi BM25，词频饱和 + 长度归一化的概率检索模型 |
| df / idf | 包含该词的文档数 / 由它算出的稀有度权重 |
| 稠密检索 | 低维实数向量，用余弦或内积衡量语义相近 |
| 双塔（bi-encoder） | query 与文档分别编码，可预建索引 |
| cross-encoder | query 与文档拼接后联合编码，精度高但只能精排 |
| ANN | 近似最近邻，用召回率换延迟 |
| HNSW | 分层可导航小世界图，向量库默认索引 |
| IVF / PQ | 聚类倒排 / 乘积量化，分别换速度与存储 |
| 稀疏鸿沟 | 换个说法就搜不到，稀疏检索的固有问题 |
| RRF | Reciprocal Rank Fusion，只按名次融合多路结果 |
| late interaction | 保留 token 级向量，打分时才交互 |
| MaxSim | 每个 query token 取文档内最大相似度再求和 |
| 点 ID | 由三元组哈希出的稳定编号，可重算 |
| 内容寻址 | 用内容哈希当路径，同样内容只存一份 |
| 归一化 bbox | 缩放到 0~1 的坐标框，与分辨率无关 |
| 软删 | 只打时间戳，检索过滤，窗口到期后物理删除 |
| recall@k / MRR / nDCG | 召回率 / 首个正确项排名倒数均值 / 带相关度分级的排序质量 |
| fail-closed | 拿不到授权范围时把条件判成恒假，而不是不过滤 |
