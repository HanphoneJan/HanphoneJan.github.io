# 工程约定与踩坑

本文列出的是约定，不是建议。带警告标记的条目，都是踩过坑之后立下的规矩。

## 1. 五条硬约束

**运行时只有一棵依赖树。**

```
web/ → services/api → services/common → services/retrieval → services/ingest
```

系统里没有第二套实现。判断“只有一份实现”的方式是扫描全仓库的 AST，查找定义点，这样可以抓住“有人在第三个地方又写了一份”。顶层目录有白名单，固定在测试里。

**租户过滤没有第二个地方。** 入口全部在 `services/common/auth.py`：`build_qdrant_filter` 负责 Qdrant，`build_kb_scope_sql` 负责 PostgreSQL 的 trgm 通道，`visible_kb_clause` 和 `writable_kb_clause` 负责知识库列表与回收站。前两个同源。

**检索唯一实现在 `services/retrieval/`。** API、MCP 和 A2A 三方共用。

**无权限等于不存在。** 返回同一个错误码 `KB_NOT_FOUND` 和 HTTP 403。

**API Key 是唯一的租户来源。** 请求体不接受 `user_id`；全局角色（超管）一样从用户行经 API Key 推导。

## 2. 三档可见性：不要写进一个 `IN`

这个问题已经真实造成过一次越权漏洞。

```python
# ❌ 这里有两个独立漏洞
or_(visibility.in_(("workspace", "global")), created_by == me)
#   1. 所有 workspace 库对任何用户可见
#   2. 同工作区成员能看到别人的 private 库
```

`IN` 表达的是“任一条件成立即可”，而可见性要表达“不同档位有各自不同的限定条件”，两者语义不匹配。

修复时最容易犯的二次错误，是保留裸的 `workspace` 分支，把带成员资格限定的分支追加成另一个 `or`，等于没有修改。两个条件必须写在同一个 `and_` 里。

由此得到一条推论，后来又踩过一次同类问题：任何附加的限定条件，都要先问它是 `or` 的一项还是 `and` 的一项。拿不准就写成 `and_(or_(可见性...), 额外限定)`，让结构本身表达意图。

给工作区可见性增加“工作区还活着”这个条件时，先写成了第四条 `or`，结果只要库里存在任意一个存活的工作区，每一行都通过。改成 `EXISTS` 之后，又踩了一次没有关联到当前知识库行（correlate）的问题。两次 pytest 都是全绿，最后都是靠 e2e 加真库探测抓住的。

还有一条：软删的行必须先按行读取，再判断权限。用 `readable_kb_ids` 过滤回收站列表会恒为空，因为软删行按定义不在那个集合里。同时要用写判据而不是读判据，否则会出现“列表里有、点恢复 403”。

## 3. 检索侧

### 3.1 `skipped` 是字符串，不是布尔值

调试面板里的 `legs[].skipped` 必须携带可操作的原因。一条没有内容的 `skipped: false` 会让人查错方向。

“查询侧没跑”和“写入侧没数据”在数据面上看起来一模一样，都是“这条通道返回 0 条”。所以能力检测只回答“本进程能不能跑”，不看集合里有没有点。

### 3.2 三条数据库通道不能共用一个会话

`dense`、`sparse`、`trgm` 都要访问数据库。如果把它们交给同一个 `AsyncSession` 并发 `execute`，SQLAlchemy 会抛出：

```
This session is provisioning a new connection; concurrent operations are not permitted
```

后果非常隐蔽：sparse 和 trgm 被记成 `skipped`，`hybrid` 静默降级成 dense 单通道，接口照样返回 200，`/search/debug` 也不报错。

修法是每条数据库通道从会话工厂各拿一个会话，也就是各自一条连接，四条通道真正并发。不要退回“共用会话加锁串行”的做法，它能跑对，但把并发收益丢了。代价是连接数：一次 `hybrid` 最多占用请求会话加三条通道，共 4 条连接，池要按“并发检索数 × 4”估算。守卫是 `tests/test_leg_concurrency.py`，检查真并发和独立会话，另外还有 `tests/test_retrieval_e2e.py` 的冷会话用例。

### 3.3 RRF 的两个工程细节

- 融合 key 必须带命名空间，例如 `text:` 和 `visual:`。两个集合的点 ID 空间独立，直接拿点 ID 做 key 会让两者互相抵消。
- 排序要有确定的 tiebreaker。RRF 分数是浮点数，并列时顺序会抖动，前端的引用角标会在刷新后对调。

### 3.4 日期归一化：检索质量问题可能出在分词

`2025-02-14` 和“2025年2月14日”两边没有任何共同 token，而 BM25 又无法表达“多个词共现”。增加一个归一化 token `d20250214` 之后，这类查询的 R@10 从 0.20 提升到 1.00。

### 3.5 trgm 只能用 `word_similarity`

`ILIKE '%<整句提问>%'` 和对整段调用 `similarity()` 都会静默漏召回，各自返回 0 条，因为两者都要求 query 和整段文本可比。把两者用 `OR` 连起来也会漏，因为放宽的是同一个错误判据。代价是全表扫描，但“慢能被发现，漏召回不能”。

### 3.6 嵌入模型必须一致

不同模型的向量空间不通用，混用等于在两个空间里计算相似度，整个排序基础都坏了，而且不会报错。所以：

- 建索引时写入 `index_models`；
- dense 通道查询前校验，不一致就标记 `skipped`，并说清“索引用的是哪个、现在配的是哪个、怎么修”；
- `index_models` 为空表表示未知，此时放行，因为还没记录不等于不一致。

### 3.7 BM25 的统计量必须有统一减法入口

`terms` 和 `corpus_stats` 在入库时增加、删除时减少。任何绕开统一删除入口的路径都会让它虚高，导致 idf 被压平，罕见词不再罕见。表现是质量下降而不是报错，所以对账里专门有一条：`chunks` 行数应该等于语料统计里的文档数。

## 4. 摄取与坐标

### 4.1 扩展名存在数据库行里

内容寻址的 blob 没有扩展名。从路径取后缀会让解析器和页图端点各炸一次。解析入口强制要求传入 `file_name`。

### 4.2 画框要乘回 point，不是像素

```python
shape.draw_rect(Rect(nx0 * pix.width, ny0 * pix.height, ...))              # ❌ 框整体下移约半行
shape.draw_rect(Rect(nx0 * page.rect.width, ny0 * page.rect.height, ...))  # ✅
```

### 4.3 形态按 `locations` 的形状分派，不按 `kind`

对外返回的引用类型只有 `text`、`page` 和 `image`，而块的形态有四种，所以表格块会以 `kind="text"` 加上带 `row` 和 `col` 的框出现。判据是形状：有 `row` 和 `col` 就画网格，`kind === "page"` 高亮整页，其余画单框。反过来“从画了几个框反推形态”是错的。

### 4.4 坐标与被渲染页面必须同源

Office 文档没有原生坐标，走“转成 PDF，再在转换版上计算坐标”的路线。画框用哪个文件由调用方决定，底图渲染函数不允许自己去找原件。定位覆盖率低于 60% 时不给框，而不是给一个错位的框。

### 4.5 表格坐标取自 `rows[i].cells`

`len(tbl.cells) != row_count * col_count`，因为合并单元格会让长度对不上。文本用 `extract()`，坐标用 `rows[i].cells`，按行号对齐。

### 4.6 页图端点需要 Bearer，前端不能用 `<img src>`

`<img>` 带不了自定义请求头，直接写会静默 401，只在控制台里看得到。要先用 `fetch` 拿到 blob，再 `createObjectURL`，并在组件卸载时释放。

## 5. 任务与状态

### 5.1 进度 100% 只归 `finish_job`

handler 结尾的 `progress(1.0)` 和 `finish_job` 是两次提交，中间有一个几毫秒的窗口，会读到 `running` 加 `progress=1.0`。偶发失败比稳定失败代价更高。所以非终态的进度封顶 0.999，并且必须单调不减。

### 5.2 文档终态要同时看两件事

只看任务状态，部分失败会被报成 `ready`；只看索引点数，全部失败时文档会永远停在 `pending`。判定要同时看“任务是否全部进入终态”和“索引里实际有多少点”，并且结算发生在 `finish_job` 事务之外，且不抛异常。

### 5.3 阻止终态的 kind 白名单

只有 `ingest` 和 `embed_visual` 会阻止文档进入终态。`thumbnail` 和 `pdf_preview` 不阻止，否则“缩略图还没生成”会把一份页级点已经齐了的文档永远按在 `pending`。

### 5.4 “没有待办任务却还在中间态”是不可能的状态

它要么说明终态判定漏了，要么说明任务被删了。worker 启动时会补扫，巡检也会兜底。

### 5.5 kind 变更要登记三处

`common/jobs.py` 的 `ALL_KINDS`、`worker/handlers/__init__.py` 的 `HANDLERS`、`models.py` 的 CHECK 约束，另外还有一条手写迁移。第三处最容易漏。

## 6. 数据库与代码

### 6.1 时间列一律带时区

裸的 `mapped_column(default=utcnow)` 会被 autogenerate 生成 `TIMESTAMP WITHOUT TIME ZONE`。统一使用 `DateTime(timezone=True)`。

### 6.2 同步和异步会话工具必须分成两个名字

```python
def register_blob(session, ...): ...             # ✅ worker 用同步 session
async def register_blob_async(session, ...): ... # ✅ API 用 AsyncSession
# ❌ 只写一个，然后两边都调
```

在 `AsyncSession` 上调用同步的 `session.execute()` 不会报错，只会返回一个从未被 await 的 coroutine。守卫 `tests/test_unawaited_coroutines.py` 用 AST 扫描整个 `services/`。

### 6.3 SSE 生成器里不能碰数据库会话

FastAPI 对 `yield` 依赖的退出码，会在“发送响应之前”执行，所以 `DbSession` 依赖在响应体开始流式输出之前就已经 commit 并关闭了。铁律有三条：

1. 检索和获取生成器全部在开流之前，用请求级 session 完成；
2. SSE 生成器里只允许做 LLM 的 HTTP 往返；
3. 问答记录的落库在流结束后新开 `session_scope()`，两条记录一起写。

违反第 2 条时，`session.execute()` 返回的 coroutine 永远不会被 await，消息会静默丢失。这和“忘了 await 的 enqueue”属于同一种问题：不报错、不告警，功能就是不工作。

### 6.4 `ON CONFLICT` 与覆盖式更新

上传同名文件时，旧文档进回收站，新文档成为当前版本。旧向量由周期清理任务清掉，不保留 30 天。

## 7. 文档与仓库纪律

- 入口文档（README、MEMORY、HANDOFF）里的路径、命令、端口和基线数字必须对得上，守卫是 `tests/test_docs_pointers.py`；
- `docs/` 里不放脚本，只放文档；
- 决策写进决策记录，包含“为什么”和实测数字；踩过的坑写进踩坑记录；基线数字同步更新；
- 代码和文档冲突时以代码为准，并把文档改过来；
- 已跟踪文件里不允许有真实信息，守卫是 `tests/test_no_real_data.py`；
- 备份和截图都不要使用真实数据。

## 8. 本地环境类坑

| 症状 | 真正原因 | 处理方式 |
|---|---|---|
| 改了代码没生效 | 旧 worker 子进程还在 | `dev.sh restart` |
| 请求走错出口或代理报错 | 代理环境变量 | 使用 `--noproxy '*'`，或检查代理 |
| 磁盘满但没有明确报错 | 临时目录里 Chrome profile 泄漏 | 清理临时目录 |
| `got Future … attached to a different loop` | 事件循环混用 | 检查 async 测试和共享 loop |
| 每次模型加载约 23 秒 | 没有设置离线环境变量 | 设置 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1` |
| 检索质量悄悄变差 | BM25 统计量漂移，或某条通道被标记 `skipped` | 按通道查看对账结果，跑检索回放 |

### 8.1 async 测试的配置节名

`pytest.ini` 的节名写错，会让整份配置都不生效。写 async 测试时，按“同步函数加模块级共享 loop”的约定处理。

## 9. 判据与测试纪律

- 判据要指向性质，而不是中间状态。判了某个中间状态或某行实现的字面量，改实现就会误报。
- AST 类断言必须做变异验证。故意改坏一处，确认测试真的会变红，并单独判断 pytest 的 `exit 5`，它表示没有收集到测试，不是通过。
- 抽了 helper 必须接线。不接线的 helper 等于没有。
- “仍然全部通过”要分清是判据太弱、变异无效，还是 `-k` 指错了目标。
