# 检索与问答

一次检索的完整路径：查询先走改写，然后四条腿并发召回，RRF 融合成一个排序列表，再做软删二次过滤、按查询意图的软偏好、（可选的）按库精排，最后组装证据。问答在这条链后面接生成：默认抽取式（摘原文句子），配置了外部 LLM 才归纳，失败退回抽取式。

## 1. 检索模式与四条腿

检索模式只控制文本三腿。视觉腿不在模式里，由服务可用性决定。

| mode | 走的腿 | 适合查什么 |
|---|---|---|
| `semantic` | dense | 意思相近的段落 |
| `exact` | trgm | 子串：手机号、工号、错误码、变量名 |
| `hybrid`（默认） | dense + sparse + trgm | 三路 RRF，日常查询 |
| —（不受 mode 控制） | visual | 照片与扫描页 |

| 腿 | 实现 | 查询方式 | 强项 |
|---|---|---|---|
| dense | `bge-small-zh-v1.5` 编码，查 `kb_dense` | 余弦 | 语义泛化 |
| sparse | jieba 分词 + 自实现 BM25，查 `kb_sparse` | 稀疏内积 | 关键词、人名、编号 |
| trgm | Postgres `word_similarity >= 0.25`，查 `chunks` | trigram 字符相似度 | 非词字符串 |
| visual | colSmol multi-vector + MaxSim，查 `kb_visual` | 页级 late-interaction | 照片、扫描件 |

visual 不在 `MODE_LEGS` 里，但 `engine._gather_legs` 总是把它并进任务列表，服务不可用时它自己返回 `skipped`。这样调试面板能显示「这一腿存在但没跑」。若直接不列出来，用户看到的是零命中，会将「服务没起」读成「库里没有照片」。

每腿候选深度：

```python
per_leg = min(100, max(top_k * 3, 30))   # CANDIDATE_MULTIPLIER=3, MAX_CANDIDATES=100
```

加深几乎免费：查询编码只做一次，多召几条只多查一轮索引。上限 100 防 `top_k=100 × 3` 把 payload 拖得过大。

## 2. 三条 DB 腿的并发

三条文本腿都要碰 Postgres：dense 查 `index_models` 校验模型一致性，sparse 查词表与 `corpus_stats`，trgm 直接查 `chunks`。

同一个 `AsyncSession` 上的并发 `execute` 会抛：

```
This session is provisioning a new connection; concurrent operations are not permitted
```

抛错之后 sparse / trgm 被记成 `skipped`，`hybrid` 静默退化成 dense 单腿，接口仍然返回 200。单库路径因为 `assert_kb_access` 预热过会话而碰巧没触发。跨库、MCP、A2A 与直接调 `engine.search` 的冷会话都会踩。

因此每条 DB 腿从 `get_async_sessionmaker()` 各拿一个会话：

```python
async with factory() as s:
    return await search_dense(ctx, query, ..., session=s)
```

视觉腿不碰 DB，不需要会话。四条腿一起 `anyio.gather`。

连接代价：一次 `hybrid` 最多 4 条连接（请求会话 + 三条腿），连接池按并发检索数 × 4 估算。

## 3. RRF 融合

四条腿的分数没有可比性：

| 腿 | 分数形态 | 观测范围 |
|---|---|---|
| dense | 余弦 | 0.2 ~ 0.9 |
| sparse | BM25 | 0 ~ 40+，随语料增长 |
| trgm | `word_similarity` | 0.25 ~ 0.40 |
| visual | MaxSim | 0 ~ 1 |

融合只看排名（k = 60，论文原始值）：

```python
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))
```

`k=60` 意味着相邻名次的贡献只差约 1.6%（`1/61` 与 `1/62` 差 0.00026）。头部的微小差距压不过「第二条腿也把它排前」的共识，所以 RRF 实际奖励的是多腿共同认可，而不是单腿的绝对高分。`k` 调小会让单腿头部更强势，`k` 调大则趋近于投票。

融合键带命名空间（`text:<id>` / `visual:<id>`）。两个 collection 的点 ID 来自同一套哈希，不带命名空间时「文本 chunk 3」与「扫描页 3」会互相抵消——页级点的 `chunk_index` 是负数本来就是第一道区分，命名空间是第二道保险。

排序键是 `(-score, key)`。只按分数排时，并列项的先后随哈希序抖动，前端的引用角标 `[1]` `[2]` 刷新一次就对调。

默认权重全为 1.0。等权 RRF 在每个类别上都没有赢过该类别表现最好的一条腿，所以权重调整放在路由层做，不在融合层做。

## 4. 查询路由与软偏好

`routing.classify` 用正则识别六类意图，置信度低于 `MIN_CONFIDENCE = 0.35` 退回 `general`（等权、不过滤）。

| 意图 | 命中词示例 | 权重调整 | 软偏好 |
|---|---|---|---|
| `photo` | 照片、合影、自拍、拍的 | visual 3.0 | `source_kind=photo` |
| `scan` | 扫描件、影印件、拍下来的那份 | visual 2.0 + sparse 1.2 | `kind in (page, table)` |
| `table` | 哪一栏、怎么填、表头 | sparse 1.3 + trgm 1.2 | `kind=table` |
| `chat` | 聊天、提过、说过什么 | sparse 1.6 | `kind=chat` 或 `source_kind=chat` |
| `date` | 哪天、什么时候、2023年5月 | sparse 2.5 | 无 |
| `general` | 其余 | 全 1.0 | 无 |

photo 的 3.0 是实测出来的最小值：在 60 个 photo 点 + 60 个 text 点、`top_k=10` 的配置下，权重 2.0 时融合池 20 条里只有 10 条是照片、top10 里 5/10。权重 3.0 时是 20/20 与 10/10。继续加到 4.0、6.0 不再变化。3.0 是「照片正好填满 `top_k*2` 池子」的最小值。

权重作用于 `rrf(limit=top_k*2)` 的入池阶段。池确定后 `prefer()` 只能在池内重排或过滤，不能把池外的东西捞回来。

`prefer` 是软过滤，不是硬排除：

```python
sub = [h for h in kept if _hit_kind(h) in route_obj.prefer_kinds]
if sub:
    kept = sub
else:
    note += "。库里没有对应类型，不做过滤"
```

过滤后为空就退回全部候选，并在 `route_note` 里说明。硬排除会把「过滤后为空」呈现成零命中，用户看到的 0 条没有解释。

多意图同时命中时取更具体的那一个，不叠加：「去年五月去旅游拍的照片」同时命中 photo 与 date，取 photo。`date` 的识别也包括日期字面量本身（如 `2023年5月1日`），此时置信度 0.6——纯日期串落进 general 的话，dense 召不回它。

## 5. 二次过滤、精排与证据质量

融合之后先挡软删，再按路由偏好排序：

```python
alive = {id for id in ... where Document.is_current and Document.deleted_at is None}
```

一次 `IN (...)` 查询，代价与 `top_k` 成正比、与语料规模无关。这两步的顺序不能颠倒：先做路由偏好再挡软删的话，被偏好滤掉的命中会先计入 `filtered_out`，这个计数就不再反映软删。

精排按库启用。`knowledge_bases.rerank_model` 为 `NULL` 表示不启用，不回退到全局默认。跨库检索一律不启用——跨库时排序结果取决于「哪些库碰巧配了模型」，不可解释。

| 项 | 值 |
|---|---|
| 模型 | `BAAI/bge-reranker-v2-m3` |
| 候选集 | 前 `limit` 个，其余保持原顺序跟在后面 |
| 截断 | `max_length=512` token |
| 失败 | 保持原顺序，返回 `skipped` + 原因 |

它的单对耗时（114ms/对）决定候选上限不能大：候选数涨几倍，耗时近乎涨几倍。精排只重排候选，召回不到的东西它救不回来。

证据质量是三档纯函数，只看已知的 `legs` 字段：

| 档位 | 条件 | 用途 |
|---|---|---|
| `ok` | 头部 5 条里最强证据有 ≥2 条腿认可 | 正常 |
| `weak` | 有命中，但只来自一条腿 | 给生成器的「证据不足」信号 |
| `none` | 没有任何命中 | 外部生成器直接拒答，不调模型 |

`none` 抽取式不额外处理：抽取式自己会在摘不出句子时拒答。

## 6. 证据组装与 SSE 问答

`ask.prepare` 在开流之前完成全部计算：

1. 读最近 `ask_history_turns=4` 条消息，按 `ask_history_chars=4000` 裁剪，丢弃最旧的整轮。
2. 短追问（长度 ≤ `ask_anaphora_max_chars=24`）把上一轮问句合并进检索 query。这层改写不依赖生成器，抽取式也受益。
3. 检索取 `top_k=8`（HTTP 上限 50）。
4. `to_evidences` 去重、重排 `idx`、同一文档的相邻片段按 `chunk_index` 升序排列。

第 4 步的两个细节各有理由：去重按 `(doc_id, chunk_index)`，否则重复证据会有两个引用角标指向一段文字。文档间的相对顺序取首次出现的位置，只重排文档内部块——模型读到的同一篇文档是连续的，不是跳读。

证据正文默认 400 字符，带 `parent_text` 时改用父块（上限 1200 字符）。

SSE 帧序固定：

```
event: sources   ← 检索完成即发，前端此时能画引用卡片
event: delta     ← 逐段。stream=false 时只有一个
event: done      ← citations / dangling_citations / degraded / session_id / legs
```

`sources` 先于任何 `delta` 是契约要求，前端据此区分「还在检索」与「正在生成」。

三个实现约束：

- SSE 生成器里只做 LLM 的 HTTP 往返，不碰 DB。FastAPI 在 `yield` 之后的退出阶段才执行生成器清理，请求级会话在开流时已提交并关闭。在生成器里调 `session.execute()` 得到的是从未被 await 的 coroutine。
- 落库在流结束后新开 `session_scope()`，user 与 assistant 两条消息一起写。中途失败就都不写，不产生「有提问没回答」的孤儿会话。
- `stream=false` 仍返回 SSE，只是 `delta` 只有一帧。这样 MCP、A2A、浏览器共用一条响应格式。

`done` 帧的字段：

| 字段 | 含义 |
|---|---|
| `citations` | 答案里出现的、范围在 1..N 的角标 |
| `dangling_citations` | 引用了不存在来源的角标，正常应为空 |
| `degraded` | 外部生成器失败后的降级原因，未降级为 `null` |
| `history_turns` | 本轮带进生成的上下文轮数 |
| `quality` | `{level, reason, max_legs}` |
| `legs` | 每腿的 `n` / `ms` / `skipped` |

外部 LLM 失败不会变成 500：`openai_compat` 的 401、超时、5xx 都退回抽取式，用同一批证据再讲一遍，原因写进 `done.degraded`。已流出部分 LLM 文本时不再追加，避免两份答案拼接。

## 7. 降级清单

`skipped` 是字符串「没跑」。`null` 是「跑了但零命中」。两条语义在接口与调试面板里都不混。

![四条检索腿、融合与降级分支](/img/knowledge-hub/retrieval-legs.png)

| 腿 / 环节 | 触发条件 | 检索结果 |
|---|---|---|
| dense | `index_models` 的模型或维度与当前配置不一致 | 200，其余腿照常 |
| sparse | 查询词分词后全不在词表 | 200，该腿 0 候选 |
| trgm | query 短于 3 字；语句超 `TRGM_STATEMENT_TIMEOUT_MS=800` | 200，降级说明带调参提示 |
| visual | 未配置 `VISUAL_SERVICE_URL`、服务不可达、模型未加载完、编码超 2s、并发排队超时 | 200，该腿 `skipped` |
| rerank | 库未配 `rerank_model`、模型加载失败、推理失败 | 原顺序，`skipped` + 原因 |
| 生成 | 外部 LLM 不可用 | 抽取式答案，`done.degraded` 说明 |

`mode` 只控制文本三腿、视觉腿看服务可用性，这条分工让「只跑文本检索」成为显式配置（`VISUAL_SERVICE_URL=` 留空），而不是依赖「服务恰好没起」的状态。
