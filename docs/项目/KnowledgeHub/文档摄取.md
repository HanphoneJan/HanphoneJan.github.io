# 文档摄取

一份文件从上传到可检索，经过的步骤是：上传校验 → 内容寻址落盘 → 排入 `ingest` 任务 → worker 解析 → 切分 →（可选）PII 掩码 → 写两条文本腿 → 视觉与预览等派生任务 → 状态结算为 `ready` 或 `failed`。多数步骤在 worker 里异步执行，API 只做同步校验与落库排队。

![从上传到 ready 的九个步骤](/img/knowledge-hub/upload-to-ready.png)

## 1. 上传时挡掉什么

`POST /api/v1/kb/{kb_id}/documents` 接收 1~20 个文件，返回 202，响应里带 `batch_id` 与每份文档的初始行。摄取是异步的，前端调 `GET /kb/{kb_id}/documents` 轮询看文档状态。

同步校验按固定顺序执行，能挡在上传时就不拖到 worker：

| 顺序 | 检查 | 不通过的结果 |
|---|---|---|
| 1 | 写权限 `assert_kb_write` | 403 `KB_NOT_FOUND` |
| 2 | 单请求文件数 ≤ 20 | `FILE_TOO_LARGE` |
| 3 | 扩展名在白名单内 | 415 `UNSUPPORTED_FORMAT` |
| 4 | 文件非空 | `VALIDATION_FAILED` |
| 5 | 单文件 ≤ 50MB | `FILE_TOO_LARGE` |
| 6 | 扩展名与文件头一致（`format_mismatch`） | 415 `UNSUPPORTED_FORMAT` |

注意分派依据与路径的区别：格式分派读 `documents.file_name` 的扩展名，绝不读 `path.suffix`——后者来自 blob 路径，而 blob 路径没有扩展名。

白名单从解析派发表派生，不另存一份分派列表：

```python
SUPPORTED_SUFFIXES, IMAGE_SUFFIXES = _derive_suffix_sets(PARSERS)
```

格式嗅探只认确凿的证据：PDF 看 `%PDF`、Office 看 `PK\x03\x04`、图片看各自的文件头。识别不出或长得像纯文本的文件一律放行，理由是挡住合法的怪文件，代价大于放进一份坏数据。

通过校验后：

```python
sha, size = store_bytes(data)                  # data/blobs/{sha[:2]}/{sha}/original
await register_blob_async(session, sha, size)  # documents.blob_sha 有外键指向 blobs
```

同名文件走覆盖式更新：旧版本 `is_current=false`、`deleted_at` 置当前时间，新版本 `version_id` 加一。这一步与目录导入共用 `ingest/versions.py` 的实现——两处各写一份，会漂出「同名双 current」的脏数据，症状是该库之后再传同名文件直接 500。

最后建 `Document(status=pending)` 并入队 `KIND_INGEST`。

## 2. 解析派发表

格式分派依据的是 `documents.file_name` 的扩展名，不是 blob 路径的 `path.suffix`。blob 是 `{sha}/original`，没有扩展名。内容寻址刻意不保留原文件名，这也是去重的前提。

| 格式 | 解析方式 | 坐标 | 说明 |
|---|---|---|---|
| PDF | pymupdf，段落 + 表格 | 0~1 归一化 bbox | 多栏按阅读顺序重排，页眉页脚清洗，8~12ms/页 |
| DOCX | python-docx，标题层级 + 表格 | 无 | 表格转 Markdown 文本 |
| XLSX | openpyxl，首行当表头，按列对齐 | 无 | 每组数据行一个 chunk |
| PPTX | python-pptx，每页一个 chunk | 无 | — |
| MD / TXT / JSON | 直接读，标题 + 段落切 | 无 | — |
| CSV | `csv.reader`，与 XLSX 同一套行分组 | 无 | 表头随每个 chunk 重复 |
| HTML | 转 Markdown 后切 | 无 | — |
| 图片 | 不产文本 chunk | 整页 | `scan_pages=[1]`、`is_scanned=True` |

`PARSERS` 里每条记录统一返回三元组 `(chunks, scan_pages, is_scanned)`。文档类解析器只返回列表，由 `_as_document_parser` 在注册时补齐。这层适配漏了，调用点会报 `not enough values to unpack`。

PDF 的坐标走 `locations.py`：单页最多 200 个框（防止前端画满几百个框卡死），一段落一格框、跨页不合并。表格整张是一个 chunk，`locations` 精确到每个非空单元格并带 `row` / `col`。

## 3. 六种切分策略

`knowledge_bases.chunk_strategy` 是库级单选，默认 `recursive`。

| 策略 | 切分边界 | 编码方式 | 备注 |
|---|---|---|---|
| `fixed` | 定长 + overlap | 标准 | 作为评测基线存在 |
| `recursive` | 标题 > 段落 > 硬切 | 标准 | 默认策略 |
| `semantic` | 句子 embedding 相似度断界 | 标准 | 纯 PDF 文本不执行（重排会打乱坐标对应的段落） |
| `parent_child` | 子块 = 递归块，父块 = 章节或整页 | 标准 | 用小子块召回，生成用 `parent_text` |
| `late` | 同 `recursive` | Late | 整篇前向，按 span 池化 |
| `contextual` | 同 `recursive` | 标准 | 每块前置一段 LLM 生成的上下文 |

三种情况会触发切分降级，均记入 `documents.quality.strategy_notes`：

- `fixed` / `semantic` 遇到 PDF：保持结构切分，note 说明原因。
- `contextual` 没配外部 LLM：退回 `recursive`，note 说明。
- 任何策略执行出错：退回 `recursive`，note 带异常信息。

`late` 的边界是整篇，受 bge-small 单次 512 token 上限约束。超出部分落在截断后的 span 里（`pool.encode_late_spans` 的注释有说明）。

改动策略只对之后摄取的文档生效。旧文档要 `POST /api/v1/documents/{id}/reparse` 才按新策略重切，这一库级差异称为重摄取欠账。

## 4. PII 检出与掩码

检出在掩码之前：报告要回答「原文里有多少敏感信息」，而不是「索引里还剩几处」。

| 类型 | 规则 |
|---|---|
| `id_card` | 18 位，含出生日期结构与校验位 |
| `phone` | 大陆手机号 |
| `email` | 常规邮箱 |
| `student_id` | `202` 开头的 8~12 位数字 |
| `bank_card` | `62` 开头的 16~19 位 |

掩码是库级开关 `knowledge_bases.pii_mask`，默认关闭：个人库的典型用途就是搜自己的手机号，默认掩掉等于取消这个用途。打开后：

- 只改索引侧文本（`chunks.content_norm`）。blob 原件、`/preview` 页图、`/documents/{id}/file` 下载仍然给原文。
- 掩码不可逆，重新摄取才会拿回可搜的原文形式。
- `documents.pii_hits` 存掩码前的计数 `{total, by_type}`。`null` 表示没跑过检测，`{}` 表示跑了但零命中，两者分开。
- 报告端点只回「哪里有、有多少」，不回原文片段。

已知边界：检出与掩码都以 chunk 为单位，跨 chunk 边界的号码会漏检。掩码值不会比原文长，因此掩码后的字符偏移只会变小，L3 高亮用的是块级 bbox，不受掩码影响。

## 5. 写进两条文本腿

chunk 的写入顺序固定：先落 Postgres 的 `chunks` 行，再进 Qdrant。两条腿的稀疏权重依赖 `term_id` 与 `corpus_stats`，BM25 的 `df` 在写向量之前登记：

```python
reg = register_chunks(session, doc_tokens)      # 先登记，拿 term_id
n_docs, avgdl = get_corpus_stats(session)
```

编码分批，`EMBED_BATCH = 16`。分批不是为了省内存：74 个 chunk 编码一次约 6.5s，这段时间进度条会停在同一位置。同一批文本的向量与分批顺序无关，结果一致。

两条文本腿的点 ID 由三元组算出（见《架构总览》§3.1），RRF 靠它对齐。Qdrant payload 固定带 `kb_id`、`doc_id`、`workspace_id`、`visibility`、`source_kind`、`owner_id`、`file_name`、`mime`、`updated_at`、`chunk_index`、`kind`、`page`、`embed_model`，以及有则带上的 `locations` / `table_index` / `parent_text` / `section_path`。

dense 写完立刻 `record_current_text_model()`——record 只在这一处，「记下的模型」与「真的编出这批向量的模型」是同一个值。查询前 dense 腿拿 `index_models` 比对，不一致就 `skipped`：在两个向量空间里算相似度是整个排序基础损坏，不能归为「结果变差」。

## 6. 视觉腿与派生任务

三种内容都进 `documents.scan_pages`：整份扫描件、混合 PDF 里没有文本层的页、照片。`scan_pages` 是页级索引在 Postgres 侧唯一的页码来源——`is_scanned` 只能表达「这份要走视觉路径」，不能回答「应该有几个视觉点」。

视觉任务一页一个，payload 是 `{"page": n}`。入队去重要按 `(doc_id, kind, payload)` 的 key，只按 `(doc_id, kind)` 会让 3 页扫描件只入队第 1 页，另 2 页不入队、任务状态仍一直为 `done`。

| 限制 | 值 | 依据 |
|---|---|---|
| 单文档扫描页数上限 | 50 页 | 单页编码 15s，50 页约 12 分钟 |

`MAX_PAGES = 2000` 在 `common/schemas.py` 与 `pipeline.py` 两处声明，但摄取路径没有据此拒绝：超过 50 页的纯扫描件在 `scan_pages` 的闸就被拦下，其余格式按解析实际结果处理。

`VDR_ENABLED=false` 时不派生视觉任务，纯扫描件直接置 `ready`，不接处理中：已经写进索引的页级向量照样能搜，只是不再新增。

摄取成功后有两条派生任务：

- `pdf_preview`：Office 文档转 PDF，顺带补 DOCX / XLSX / PPTX 缺失的坐标。LibreOffice 是外部进程，实测 0.7s 起，大 PPT 可到 30s+。转换失败只标任务失败、不动文档状态，文档照样能搜、能引用、能下载。
- `thumbnail`：PDF 的前 20 页，宽 400px，列表页直接显示。

纯扫描件的 `ingest` 结束时停在 `pending`，等所有视觉任务到终态再翻状态。

## 7. 进度与文档终态

`jobs.progress` 是页面上百分比的唯一来源，没有任务行就不显示进度条。阶段的权重来自实测（15 页 PDF、74 chunk 的分解：解析 0.6s、分块 0.2s、编码 6.5s）：

```python
STAGE_PROGRESS = {"start": 0.02, "parsed": 0.35, "chunked": 0.45, "indexed": 0.97}
EMBED_FROM, EMBED_TO = 0.45, 0.97     # 编码段按 done/total 映射
```

handler 上报进度封顶 0.999，1.0 只归 `finish_job`。否则会出现 `running + progress=1.0` 的瞬间，前端误任务完成、实际还在收尾。

`jobs.status` 与 `documents.status` 是两份状态。任务到终态后，worker 调 `settle_doc_state` 把结论写在文档行上。成功和失败两条路径都调它。文档的终态判定用的条件有三个：

1. 文档是否在中间态（`pending` / `parsing` / `chunking` / `embedding`）。`ready` 与 `failed` 是终态。`failed` 不能被程序翻案，只能由用户 retry/reparse 改变。
2. 该文档是否还有 `ingest` / `embed_visual` 未完成。`thumbnail` / `pdf_preview` 不阻止终态（预览没生成不影响能否搜到）。
3. 有 `scan_pages` 的文档，`kb_visual` 的页级点数应等于页数。页数对不上且没有待办任务，判 `failed`。

`scan_pages IS NULL` 视为「没有视觉页码信息」的旧行。这类文档的视觉任务已经全部终态失败时，也判 `failed`——它承诺的处理链不会再有任何进展。

worker 启动时会补扫一次「中间态却无任何待办任务」的文档（`sweep_stuck_docs`）。这一状态由 worker 被杀时 `finish_job` 已提交、文档结算未提交的几毫秒产生，一旦发生就永久卡住。

## 8. 状态机与任务表

`jobs.status`：`pending → running → done / failed / cancelled`。领取、租约与重试的细节见《运维与验收》。

`documents.status` 取值：`pending` / `parsing` / `chunking` / `embedding` / `ready` / `failed`。阶段进度对 worker 的每一步都可见，`STAGE_PROGRESS` 的写法即推导自各环节的耗时占比。

失败用 `IngestError(retryable=…)` 分类。明确的失败原因（损坏文件、页数超限）标 `retryable=False`，以避免无意义的重试。其他异常按可重试处理（`jobs.max_attempts = 3`）。
