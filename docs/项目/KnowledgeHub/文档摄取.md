# 文档摄取

> **阅读目标**: 一份文件从上传到可检索经过哪些步骤、每步在哪个进程里做、失败与降级落在哪一列上。

---

## 1. 上传时挡掉什么

`POST /api/v1/kb/{kb_id}/documents` 返回 **202**，响应里带 `batch_id` 与每份文档的初始行。摄取是异步的，前端轮询 `GET /kb/{kb_id}/documents` 看状态。

同步校验按顺序做，能在上传时发现的错误不拖到 worker：

| 检查 | 不通过的结果 |
|---|---|
| 写权限 `assert_kb_write` | 403 `KB_NOT_FOUND` |
| 单请求文件数 ≤ 20 | `FILE_TOO_LARGE` |
| 扩展名在白名单内 | 415 `UNSUPPORTED_FORMAT` |
| 文件非空 | `VALIDATION_FAILED` |
| 单文件 ≤ 50MB | `FILE_TOO_LARGE` |
| 扩展名与实际内容一致（`format_mismatch`） | 415 `UNSUPPORTED_FORMAT` |

白名单从解析派发表派生，不另存一份：

```python
SUPPORTED_SUFFIXES, IMAGE_SUFFIXES = _derive_suffix_sets(PARSERS)
```

格式嗅探只认确凿的证据：PDF 看 `%PDF`、Office 看 `PK\x03\x04`、图片看各自文件头。识别不出或看着像纯文本一律放行，因为把合法的怪文件挡在门外比放进一份坏数据更糟。

通过之后写原件：

```python
sha, size = store_bytes(data)                  # data/blobs/{sha[:2]}/{sha}/original
await register_blob_async(session, sha, size)  # documents.blob_sha 有外键指向 blobs
```

同名文件走覆盖式更新：旧版本 `is_current=false`、`deleted_at` 置当前时间，新版本 `version_id` 加一。这一步与目录导入共用 `ingest/versions.py`，两处各写一份会漂出「同名双 current」，症状是那个库之后再传同名文件就 500。

最后建 `Document(status=pending)` 并入队 `KIND_INGEST`。

## 2. 解析派发表

格式分派以 `documents.file_name` 的扩展名为准，不是 `path.suffix`。blob 路径是 `{sha}/original`，没有扩展名；内容寻址刻意不保留原文件名，这是去重的前提。

| 格式 | 解析方式 | 坐标 | 说明 |
|---|---|---|---|
| PDF | pymupdf，段落 + 表格 | ✅ 0~1 归一化 bbox | 多栏按阅读顺序；页眉页脚清洗；8~12ms/页 |
| DOCX | python-docx，标题层级 + 表格 | ❌ | 表格转 Markdown |
| XLSX | openpyxl，首行当表头，按列对齐 | ❌ | 每组数据行一个 chunk |
| PPTX | python-pptx，每页一个 chunk | ❌ | |
| MD / TXT / JSON | 直接读，标题 + 段落切 | ❌ | |
| CSV | `csv.reader`，与 XLSX 同一套行分组 | ❌ | 表头随每个 chunk 重复 |
| HTML | 转 Markdown 后切 | ❌ | |
| 图片 | 不产文本 chunk | 整页 | `scan_pages=[1]`、`is_scanned=True` |

`PARSERS` 里每条记录统一返回三元组 `(chunks, scan_pages, is_scanned)`。文档类解析器只返回列表，由 `_as_document_parser` 在注册时补齐；这层适配漏掉时，调用点会报 `not enough values to unpack`。

PDF 的坐标由 `locations.py` 产出。两个实测约束：单页最多 200 个框（防前端卡死），以及跨页不合并（否则点一次引用会画出满屏框）。表格整张一个 chunk，`locations` 精确到每个非空单元格并带 `row` / `col`。

## 3. 六种切分策略

`knowledge_bases.chunk_strategy` 是库级单选，默认 `recursive`。

| 策略 | 边界 | 编码 | 备注 |
|---|---|---|---|
| `fixed` | 定长 + overlap | 标准 | 评测基线；PDF 不执行 |
| `recursive` | 标题 > 段落 > 硬切 | 标准 | 默认 |
| `semantic` | 句子 embedding 相似度 | 标准 | PDF 不执行（重排会毁坐标） |
| `parent_child` | 子块 = 递归块，父块 = 章节或整页 | 标准 | 召回小子块，生成用 `parent_text` |
| `late` | 同 `recursive` | Late | 整篇前向，按 span 池化 |
| `contextual` | 同 `recursive` | 标准 | 每块前置 LLM 生成的上下文 |

三条降级路径都记在 `documents.quality.strategy_notes` 里，不让摄取失败：

- `fixed` / `semantic` 遇到 PDF：保持结构切分，note 说明原因。
- `contextual` 没配外部 LLM：退回 `recursive`，note 说明。
- 任何策略抛错：退回 `recursive`，note 带异常信息。

`late` 的边界是整篇，受 `bge-small` 512 token 上限约束。超出部分落在截断后的 span 里，这一点在 `pool.encode_late_spans` 的注释里写明，不假装它对长文档一定更好。

改策略只对之后摄取的文档生效。旧文档要 `POST /api/v1/documents/{id}/reparse` 才按新策略重切，界面上把这件事叫作重摄取欠账。

## 4. PII 检出与掩码

检出在掩码之前，因为报告要回答"原文里有多少敏感信息"，而不是"索引里还剩几处"。

| 类型 | 规则 |
|---|---|
| `id_card` | 18 位，含出生日期结构与校验位 |
| `phone` | 大陆手机号 |
| `email` | 常规邮箱 |
| `student_id` | `202` 开头的 8~12 位数字 |
| `bank_card` | `62` 开头的 16~19 位 |

掩码是库级开关 `knowledge_bases.pii_mask`，默认关闭。个人库的常见用途就是搜自己的手机号，默认掩掉就关掉了这个用途。打开之后：

- 只改索引侧文本（`chunks.content_norm`）。blob 原件、`/preview` 页图、`/documents/{id}/file` 下载都还是原文。
- 掩码不可逆。重新摄取才会拿回可搜的形式。
- `documents.pii_hits` 存掩码前的计数 `{total, by_type}`。`null` 表示没跑过检测，`{}` 表示跑了但零命中，两件事分开。
- 报告端点只回"哪里有、有多少"，不回原文片段。

两个已知边界写在代码里：跨 chunk 边界的号码会漏检（检出与掩码都以 chunk 为单位）；掩码值不会比原文长，所以掩码后的字符偏移只会变小。L3 高亮用的是块级 bbox，不受这个偏移影响。

## 5. 写进两条文本腿

chunk 先落 PG，再进 Qdrant。两步之间有一件容易漏的事：BM25 的 `df` 必须在写向量之前登记，因为稀疏权重依赖 `term_id` 与 `corpus_stats`。

```python
reg = register_chunks(session, doc_tokens)      # 先登记，拿 term_id
n_docs, avgdl = get_corpus_stats(session)
```

编码分批做，`EMBED_BATCH = 16`。分批不为省内存：74 个 chunk 一次编 6.5 秒，其间进度条不动。同一批文本的向量与顺序无关，分批不改变结果。

两条腿的点 ID 必须相同（算法见《架构与进程》§3），RRF 靠它对齐。payload 里带 `kb_id`、`doc_id`、`workspace_id`、`visibility`、`source_kind`、`owner_id`、`file_name`、`mime`、`updated_at`、`chunk_index`、`kind`、`page`、`embed_model`，以及 `locations` / `table_index` / `parent_text` / `section_path`（有才带）。

dense 写完立刻 `record_current_text_model()`。只有这里能保证"记下的模型"与"真的编出这批向量的模型"是同一个。查询前 dense 腿拿 `index_models` 比对，不一致就 `skipped`：在两个向量空间里算相似度不是"随机变差"，是整个排序基础坏了。没有记录时放行，未知不等于不一致。

## 6. 视觉腿与后续任务

扫描页、混合 PDF 里没有文本层的页、照片，都进 `documents.scan_pages`。它是页级索引在 PG 侧唯一的真相来源：`is_scanned` 只说"这份要走视觉路径"，说不出"该有几个点"。

视觉任务一页一个，payload 是 `{"page": n}`。入队去重必须比 payload，只比 `(doc_id, kind)` 会让 3 页扫描件只入队第 1 页，另两页不会编码，而任务状态全是 `done`。

| 上限 | 值 | 依据 |
|---|---|---|
| 扫描页数 | 50 | 单页编码成本见《架构与进程》§4，50 页约 12 分钟 |

`common/schemas.py` 与 `pipeline.py` 都声明了 `MAX_PAGES = 2000`，但摄取路径没有据此拒绝文档：超过 50 页的纯扫描件会先在 `scan_pages` 那道闸被拦下，其余格式按解析实际结果处理。

`VDR_ENABLED=false` 时根本不入队视觉任务，纯扫描件直接置 `ready`，不留处理中。已经写进索引的页级向量照样能搜，只是不再新增。

摄取成功后还会派生两个任务：

- `pdf_preview`：Office 文档转 PDF，顺带补 DOCX / XLSX / PPTX 缺失的坐标。转换是外部进程（LibreOffice），实测 0.7s 起，大 PPT 可到 30s+。失败只标任务失败，不动文档状态：文档照样能搜、能引用、能下载。
- `thumbnail`：PDF 的前 20 页，宽 400px，供列表页直接显示。

纯扫描件在 `ingest` 结束时停在 `pending`，等所有页级任务到终态再翻状态。

## 7. 进度与文档终态

`jobs.progress` 是百分比的唯一来源。没有任务行就不显示进度条。

```python
STAGE_PROGRESS = {"start": 0.02, "parsed": 0.35, "chunked": 0.45, "indexed": 0.97}
EMBED_FROM, EMBED_TO = 0.45, 0.97     # 编码段按 done/total 映射
```

阶段权重不是耗时占比，是"编码占大头"这个事实的形状：解析 0.6s、分块 0.2s、编码 6.5s（15 页 PDF、74 chunk）。

handler 上报的进度封顶 0.999，`1.0` 只归 `finish_job`。否则会出现 `running + progress=1.0` 的瞬间，前端以为完成了，任务其实还在收尾。

`jobs.status` 与 `documents.status` 是两份状态。任务到终态后，worker 调 `settle_doc_state` 把结论搬给文档，成功与失败两条路径都调。

终态判定看三件事：

1. 文档还在中间态（`pending` / `parsing` / `chunking` / `embedding`）吗？`ready` 与 `failed` 都是终态，`failed` 尤其不能替用户翻案。
2. 还有未完成的 `ingest` / `embed_visual` 吗？`thumbnail` / `pdf_preview` 不挡，预览没生成不影响内容能不能搜。
3. `scan_pages` 非空时，`kb_visual` 的页级点数够吗？不够且没有待办任务，判 `failed`。

`scan_pages IS NULL` 的老文档如果视觉任务已经全部终态失败，也判 `failed`：那个 `pending` 承诺没人能兑现，用户需要拿到「重解析」入口。

worker 启动时 `sweep_stuck_docs` 补扫"中间态却没有任何待办任务"的文档。正常情况下这里什么都没有；它存在是因为 worker 可能在 `finish_job` 提交之后、文档结算提交之前被杀，窗口只有几毫秒，一旦发生就是永久卡住。
