# 任务队列与进程模型

本文讲后台任务是怎么完成的：任务表如何设计，worker 如何领取和重试任务，文档状态什么时候确定下来，以及三个进程之间如何分工。

## 1. 为什么用 PostgreSQL 任务表

需求本身很具体：

- 进度条本来就需要一份任务状态表；
- 待办任务放进同一张表的成本几乎为零；
- 单机部署、任务量不大，不需要独立的消息中间件；
- 需要 `FOR UPDATE SKIP LOCKED` 来保证多个 worker 不会抢到同一行。

于是系统使用 `jobs` 表加轮询 worker。API 只负责入队和查询进度，worker 负责执行。

## 2. 任务类型

| kind | 谁执行 | 成本 | 说明 |
|---|---|---|---|
| `ingest` | worker | 约 50 毫秒一页 | 解析、分块、嵌入、写 Qdrant 文本通道，一次做完 |
| `embed_visual` | worker | 约 15 秒一张图 | colSmol 编码，必须独立成任务，否则会卡住 API |
| `thumbnail` | worker | 约 30 毫秒一页 | 预生成缩略图 |
| `pdf_preview` | worker | 视情况而定 | Office 转 PDF，供预览和坐标使用 |
| `cleanup` | worker | 视情况而定 | 过期数据清理和回收站物理清理 |
| `import_chat` | worker | 视情况而定 | 服务端读取 JSONL，每 50 条消息切一个文档 |
| `import_dir` | worker | 视情况而定 | 从服务器目录批量导入照片 |
| `reindex` | worker | 分钟级 | 重建索引，或修正 BM25 词表漂移 |

早期 `parse`、`chunk`、`embed` 是三个独立的 kind，后来合并成 `ingest`。原因是三步加起来不到 1 秒，拆开只会多三次事务，而且进度回传要跨三个任务拼装。

### 2.1 领取协议

```sql
UPDATE jobs SET status='running', locked_at=now(), locked_by=:worker_id, ...
WHERE id = (
  SELECT id FROM jobs
  WHERE status='pending'
    AND (locked_at IS NULL OR locked_at < now() - interval '5 min')
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
) RETURNING *;
```

- `FOR UPDATE SKIP LOCKED` 保证多个 worker 不会抢同一行；
- `locked_at < now() - 5 min` 让 worker 崩溃后的任务可以被重新领取；
- `max_attempts` 默认为 3；
- 未注册的 kind 永远不会成功，直接进入终态失败，不占用重试额度。

### 2.2 空闲退避

worker 的轮询间隔会随空闲程度递增，从 1 秒到 2 秒再到 5 秒；一旦有任务，立刻回到 1 秒。空闲时只轮询 PostgreSQL，几乎不消耗 CPU。

## 3. 进度：100% 只归 `finish_job`

```python
PROGRESS_NONTERMINAL_MAX = 0.999
```

每个 handler 结尾都会调用 `progress(1.0)`，而这次调用走独立事务；`finish_job` 在之后另一个事务里才把 `status` 改成 `done`。两次提交之间存在一个窗口，读到的状态会是 `running` 加 `progress=1.0`。

这个窗口只有几毫秒，在 200 多次运行里偶尔出现一次。偶发失败比稳定失败代价更高，因为下一个人会以为索引坏了，去查一个根本不存在的问题。

语义上也应该这样：“100%”表示“已经完成”，而“完成”由 `finish_job` 判定，其中还包含重试判定。handler 说“我干完了”不等于任务真的完成。这里选择封顶 0.999，而不是丢弃这次上报，因为进度必须单调不减，直接丢弃会让界面从 0.67 倒退到 1.00。

## 4. 文档终态判定

`jobs.status` 和 `documents.status` 是两套状态。早期版本没有任何代码把前者的终态同步到后者，于是文档永远停在中间态：

| 任务终态 | 文档实际停在 | 用户看到 |
|---|---|---|
| `ingest` 重试耗尽 | `pending`、`parsing` 等 | “一直在处理中” |
| `embed_visual` 全部失败 | `pending` | “一直在处理中” |

下游其实都已经准备好了：契约写着失败要写 `failed`，重试端点只接受 `failed`，前端徽章也按 `failed` 绘制。唯独那个状态从来不会被写进去。

### 4.1 判定要同时看两件事

```
1. 文档还在中间态吗？已经进入终态的不要再改，包括 failed。
2. 还有未完成的 ingest 或 embed_visual 吗？有就说明还没到终态。
3. 该有的页级点齐了吗？
```

只看点数，全部失败时点数永远不够，文档会一直停在 `pending`。只看任务状态，任务 `done` 只说明“没有抛异常”，而页面上的点到底在不在索引里才是事实。所以两个都要看。

### 4.2 kind 白名单

只有 `ingest` 和 `embed_visual` 会阻止文档进入终态：

- `thumbnail` 和 `pdf_preview` 不阻止。它们不影响“视觉页够不够”，算进去会让“缩略图还没生成”把一份页级点已经齐了的文档永远按在 `pending`；
- `ingest` 必须算。它会重新计算 `scan_pages` 并派发视觉任务，它还在排队就说明这份文档马上会被重新处理。

### 4.3 结算在事务之外，且不抛异常

```python
def settle_doc_state(kind: str, doc_id: int | None) -> None:
    if kind not in DOC_STATE_KINDS or doc_id is None:
        return
    try:
        with sync_session_scope() as s:
            reconcile_doc_state(s, doc_id)
    except Exception:
        logger.error(...)   # 只记日志，让巡检报出来
```

结算必须在 `finish_job` 的事务之外执行。任务终态已经落库，如果绑在同一事务里，“改文档状态失败”会把 15 秒的模型前向计算一起回滚。

结算失败也不能抛异常。它的调用点在 worker 主循环中间，抛出去会被当成“任务失败”，再走一遍 `finish_job(error=...)`，把一个已经 `done` 的任务改回 `pending` 或重试。这个副作用比原问题严重得多。

代价是存在“任务成功但文档还在中间态”的窗口，由启动时的补扫 `sweep_stuck_docs` 和巡检兜底。

“没有待办任务却还在中间态”是不可能的状态。worker 启动时会补扫一次，巡检里也有“卡住的文档”这一项。

## 5. 三个进程

### 5.1 API

- 监听 8010；
- 提供 REST、SSE、MCP 和 A2A；
- 托管 `web/dist`，目录存在时才挂载；
- 始终不加载视觉模型。

### 5.2 Worker

- 没有监听端口；
- 轮询任务、执行 handler、结算文档状态；
- 默认在本地加载视觉模型做写入编码，峰值约 2.8 GB。

### 5.3 视觉查询服务

- 监听 8020，只绑定 `127.0.0.1`；
- 常驻 colSmol，启动即预热，约 13 秒，常驻内存 2.71 GB；
- 提供 `POST /encode`（文本）和 `POST /encode_image`（图片）；
- 不查询 Qdrant，不做租户过滤；
- 只负责编码。失败时 API 侧把视觉通道标记为 `skipped`，检索照常返回 200。

`dev.sh` 的视觉服务起停委托给 `deploy/visual.sh`，只保留一份实现，避免两套 pid、日志和重启策略发生漂移。

## 6. 多 worker 与写入侧改造

默认形态下，worker 自己加载 colSmol。同一台机器跑 N 个 worker 会把 2.65 GB 乘以 N，内存吃不消。

可选形态是把写入侧也改成调用视觉服务：

```bash
VISUAL_WRITE_VIA_SERVICE=true
PKH_WORKERS=4 bash deploy/dev.sh start
```

此时 worker 不再加载模型，实测内存降到约 991 MB，同一台机器可以跑多个 worker。代价是摄取从此依赖视觉服务可用，所以默认关闭，按机器规格决定是否开启。

| 形态 | worker 常驻内存 | 前提 | 适合 |
|---|---|---|---|
| 默认 | 峰值约 2.8 GB | 无 | 单 worker、小机器 |
| 写入侧走服务 | 约 991 MB | 视觉服务必须在线 | 多 worker、内存宽裕 |

## 7. 视觉编码的成本特性

| 指标 | 数值 | 含义 |
|---|---|---|
| 模型加载 | 12.8 到 15.0 秒 | 启动即预热，约 13 秒后就绪 |
| 单图编码 | 约 15 秒（float32） | 与分辨率无关，内部固定切成 13 个 512×512 图块 |
| 查询文本编码 | 每条 119 到 128 毫秒 | p95 为 157 毫秒 |
| 6 路并发 | 实际 0.96 秒，消耗 CPU 8.36 秒 | 并行度 8.7 倍 |
| 常驻内存 | 2.64 GB | 小机器上必须与 worker 二选一 |

本机 CPU 是 i5-13420H，没有 `avx512_bf16`。colSmol 走 bf16 会慢 4.6 倍，每张图需要 68 秒，而 float32 只要 15 秒。代码已经固定使用 float32，换机器后要重新测量。

### 7.1 渲染尺寸的安全上限

视觉页渲染的长边封顶为 2048 像素。这不是画质参数，而是安全措施：

- colSmol 内部会把长边重采样到 2048 像素再切图块，渲染得更大一个 token 也不会多；
- 不封顶时，工程图纸、海报或 CAD 导出这类超大页面会让 pymupdf 报 `Overly large image`，这一页的视觉任务永久失败，而纯扫描件文档会永远停在 `pending`。

## 8. 失败与重试

| 情况 | 处理方式 |
|---|---|
| handler 抛出可重试异常 | `attempts` 加 1，状态回到 `pending`；超过 `max_attempts` 后置为 `failed` |
| 不可重试异常 | 直接置为 `failed`，不浪费重试额度 |
| 未注册的 kind | 直接置为 `failed` |
| worker 崩溃 | `locked_at` 超过 5 分钟后，任务可以被重新领取 |
| 文档停在中间态 | worker 启动时补扫，巡检里也有“卡住的文档” |
| 任务长时间处于 `running` | 巡检里的“卡住的任务”，超过 30 分钟会报告 |

## 9. 改代码之后先杀掉旧进程

`uv run X` 会产生两个进程：一个是 wrapper，一个是真正执行 Python 的进程。只 kill 进程组 leader 杀不干净子进程，旧 worker 会继续抢任务并用旧代码处理，症状就是“改了没生效”。

```bash
bash deploy/dev.sh restart
```

`dev.sh` 只有 `start`、`restart`、`stop` 三个子命令，没有 `status` 和 `logs`。查看状态用下面两条命令：

```bash
curl -s --noproxy '*' http://127.0.0.1:8010/health
tail -20 /tmp/pkh_api.log /tmp/pkh_worker.log /tmp/pkh_visual.log
```
