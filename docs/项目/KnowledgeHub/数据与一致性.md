# 数据与一致性

---

## 1. 18 张表分四层

| 层 | 表 | 作用 |
|---|---|---|
| 身份与容器 | `users`、`api_keys`、`workspaces`、`workspace_members`、`workspace_invites` | 账号、Key、工作区、成员、邀请码 |
| 内容 | `knowledge_bases`、`documents`、`blobs`、`chunks` | 库、文档版本、原件、块 |
| 任务与审计 | `jobs`、`audit_log` | 异步任务、操作留痕 |
| 检索与对话 | `terms`、`corpus_stats`、`index_models`、`chat_sessions`、`chat_messages`、`chat_day_stats`、`llm_settings` | BM25 词表与统计、建索引模型、会话消息、聊天按天聚合、外部 LLM 配置 |

`migrations/versions/` 下 23 个迁移文件：初始迁移建 12 张表，其余 22 个加到 18 张，另含 CHECK 约束取值变更、`pg_trgm` 扩展、部分索引。

时间列统一 `TIMESTAMPTZ`。软删除统一 `deleted_at`，查询默认带 `deleted_at IS NULL`。`pg_trgm` 由迁移创建，不在 ORM 里声明。`pgvector` 镜像装了但不用：向量归 Qdrant，colSmol 的 late-interaction 不是 pgvector 的形状。

CHECK 约束的取值变更不能靠 autogenerate：它只比对外键、索引、列，不检测约束表达式。`chunk_strategy`、`jobs.kind`、`users.role` 这几处都是手写迁移，改完要跑 `alembic check`，否则会出现模型里有、库里没有的漂移。

## 2. 原件：内容寻址与引用计数

```
data/blobs/{sha[:2]}/{sha}/original
data/blobs/{sha[:2]}/{sha}/preview.pdf
data/blobs/{sha[:2]}/{sha}/thumbs/{page}.jpg
```

目录名是文件的 sha256，前两位分 256 个子目录。原始文件固定叫 `original`，因为 `{sha}` 一旦被当文件名占用，再想在同一路径下 `mkdir` 放预览就会报 `NotADirectoryError`。

同一份内容被多个文档版本引用时只存一份：

| 字段 | 含义 |
|---|---|
| `blobs.sha256` | 主键，也是目录名 |
| `blobs.ref_count` | 被几个 `documents` 行引用 |
| `blobs.storage_path` | 写入时记下的路径，没有代码读它做分发 |
| `documents.blob_sha` | 外键指向 `blobs.sha256` |

漏登记 `blobs` 行会直接撞 `documents_blob_sha_fkey`，而不是"文件写不进去"。上传与目录导入两条路径共用 `register_blob` / `register_blob_async`，一边记得、一边忘了的情况不会发生。

`ref_count` 减到 0 才删目录。这个减一动作在物理删除链里，不在软删时。

## 3. chunk：检索的最小单位

| 字段 | 用途 |
|---|---|
| `content_norm` | 归一化文本，嵌入与 trgm 用 |
| `char_start` / `char_end` | 在全文里的字符偏移，部分格式有 |
| `locations` | L3 坐标数组 `[{page, bbox, row?, col?}]`，bbox 已归一化到 0~1 |
| `kind` | `text` / `table` / `page` / `chat` |
| `table_json` | 表格的结构化网格 `{header, rows}`，前端渲染真表格 |
| `parent_text` | Parent-Child 的父块上下文，不进向量库 |
| `section_path` | `H1 > H2 > H3` |
| `token_count` | 估算 token 数 |

表格块的 `content_norm` 仍是 Markdown，另外带一句规则生成的描述（"N 行 × M 列；表头：…"），让"一览表"类查询能召回表格。正文块通常一个框，表格块每个非空单元格一个框并带 `row` / `col`，扫描页只有整页。

判断"有没有坐标"要看内容，不能看 `locations IS NULL`：这一列是 JSONB，空列表常存成 JSON `null` 而不是 SQL NULL，用 SQL 判会一条都筛不出来。

`chunks` 上有三个索引，其中两个承担不同查询：

```sql
UNIQUE (doc_id, chunk_index)                          -- 点 ID 复算的前提
GIN (content_norm gin_trgm_ops)                       -- 子串腿的唯一索引
```

## 4. 软删、版本与恢复

`documents` 用三个字段表达"哪一版活着"：

| 字段 | 含义 |
|---|---|
| `is_current` | 为真时参与检索 |
| `deleted_at` | 非空表示进了回收站，30 天后物理清理 |
| `version_id` | 同一 `(kb_id, file_name)` 的第几版，从 1 起 |

覆盖式更新时，旧版本 `is_current=false` 且 `deleted_at` 置为当前时间，新版本 `version_id` 取"现有最大值 + 1"。取 max 而不是"当前版本 + 1"是因为历史脏数据里可能已经有多个同名 current 文档，按当前版本加会撞回旧值。

`supersede()` 是唯一实现，上传与目录导入共用。它幂等：已经是历史版本的文档不会被再次处理。

恢复不复用旧向量。`POST /documents/{id}/restore` 与 `POST /kb/{id}/restore` 都把状态改回 `pending` 并重新入队 `ingest`，因为期间可能改过 `chunk_size` 或切分策略，旧块已经过时。

删库时 `delete_kb` 把库的 `deleted_at` 盖到它下面所有当前文档上，共享同一个时间戳。恢复按这个时间戳**精确相等**匹配，只带回"那次删除带走的"文档：

```python
Document.deleted_at == stamp        # 不是 <=
```

用 `<=` 会把更早单独删掉的、或被同名新版本顶替的文档也捞回来。

`knowledge_bases` 与 `workspaces` 同样是软删。删工作区不级联软删其下的库与文档，只标记工作区一行，代价是可见性判定里必须多一个"工作区还活着"的条件。这一条在《多租户与权限》里展开。

## 5. 删除链六步

物理删除只有一个实现（`ingest/purge.py`），两个入口共用：

| 入口 | 谁调 | 选谁 |
|---|---|---|
| `KIND_CLEANUP` | worker，30 天到期 | `deleted_at < now - 30 天` |
| `DELETE /api/v1/trash` | 用户手工清空 | 调用方指定的范围 |

每一步漏掉都不报错：

| # | 动作 | 漏掉的后果 |
|---|---|---|
| 1 | 把 chunk 的 token 从 BM25 词表减回去 | `df` 只加不减，idf 被压平，检索质量悄悄变差 |
| 2 | 删 Qdrant 三个 collection 里属于该文档的点 | 已删内容还能被搜到 |
| 3 | 删 `documents` 行 | `chunks` / `jobs` 不跟着走（它们靠 `ON DELETE CASCADE`） |
| 4 | `blobs.ref_count` 减一 | 磁盘只增不减 |
| 5 | 归零才删 blob 目录 | 原件留在盘上 |
| 6 | 不动 `audit_log` | 审计保留 180 天，人走了记录还在 |

第 1 步用的分词必须与入库时同一个函数 `bm25.tokenize`。换成 `.split()` 也能跑，只是减掉的 df 与加进去的对不上，而这件事不会报错。

同步与异步各一份驱动（`purge_documents` / `purge_documents_async`），但选择条件的 SQL 与 df 算法只有一份。在 `AsyncSession` 上调同步版不报错，只是返回一个从未被 await 的 coroutine，所以两份必须成对存在。

容器清理（软删的库与工作区）只由 worker 的 30 天路径触发，没有额外的 API 端点。顺序必须是先把它下面的文档走完六步，再删容器行；反过来先删容器，文档的 df 就减不回去。

## 6. 对账：三条腿分开比

| 腿 | 期望点来自 | 点 ID |
|---|---|---|
| `kb_dense` | `chunks` 行 | `point_id(kb_id, doc_id, chunk_index)` |
| `kb_sparse` | `chunks` 行 | 同上 |
| `kb_visual` | `documents.scan_pages` | `point_id_for_page(kb_id, doc_id, page)` |

期望集合的 SQL 只有一处：

```sql
SELECT documents.kb_id, chunks.doc_id, chunks.chunk_index
FROM chunks JOIN documents ON documents.id = chunks.doc_id
WHERE documents.kb_id IN (...) AND documents.is_current AND documents.deleted_at IS NULL
```

`kb_id` 取自 `documents`，不去 join `knowledge_bases`。多 join 一次就是笛卡尔积，实测把期望点数从 399 放大到 8379，报出来的是"缺 8379 个点"。

三条腿不能取并集。取并集时"只有一条腿坏了"会报成一致，而那正是真实故障模式：`kb_visual` 恒 0 个点，看起来像库里没照片。

`scan_pages IS NULL` 的文档要跳过：那是加这一列之前摄取的，页码无从得知，当成"应该有 0 个点"会把它的页级点全报成残留。

对账**只报告、不自动删**。摄取时 chunk 行先 `flush`（不提交），点已经 upsert；在事务提交之前，另一个连接看到的"点存在、行不存在"其实是正在写的。自动删会把刚写进去的点删掉，随后行提交，留下永久索引空洞。

## 7. 重建、蓝绿与一致性窗口

### 7.1 重建与蓝绿

`POST /admin/reindex` 入队 `KIND_REINDEX`，不同步跑。默认范围是"我有权访问的库"，不是全库。

重建的顺序有三处是刻意的：

1. **词表先为全体 chunk 重新登记**，再重建向量。`df` 与 `corpus_stats` 是全局量，只登记目标库会把别的库 idf 弄坏。
2. **向量只重建目标库，按 `kb_id` 排序**，切到哪个库就先删哪个库的两条文本腿再重建。排序不能省：不排序时同一个库会在不同位置被删多次，后一次删会抹掉前一次刚重建的点。
3. **视觉腿既不重建也不删**。页级向量要重读原件 + colSmol 前向（15s/页），那是重新摄取，不是重建索引。删了建不回来，比漂移更糟。

孤儿点（Qdrant 有、PG 里连 `kb_id` 都不存在）清理覆盖三条腿。它们永远不可能被重建，删掉零风险。实测第一次清出 19733 个/腿。

`swap=true` 是整实例蓝绿重建，需要超管与别名模式：

```bash
uv run python deploy/bootstrap_index_aliases.py --yes   # 一次性迁移
# .env 设 QDRANT_ALIASES=true，重启 API/worker
curl -X POST -H "Authorization: Bearer $KEY" \
  'http://127.0.0.1:8010/api/v1/admin/reindex?swap=true'
```

流程是建影子集合 → 灌数据 → 验点数 → 原子切别名 → 保留旧集合回滚。别名模式下逻辑名是别名，物理集合是 `kb_dense__<gen>`；`GET /collections` 不列别名，巡检列的是物理集合名。

### 7.2 已知的一致性窗口

| 窗口 | 长度 | 挡住它的东西 |
|---|---|---|
| 软删后 Qdrant 点还在 | 最多 5 分钟（`_STALE_SWEEP_INTERVAL=300`） | 检索侧二次过滤 `is_current AND deleted_at IS NULL` |
| 新增 payload 字段只对之后摄取的文档生效 | 直到重新摄取 | 带时间过滤的查询会排除旧点 |
| BM25 idf 随增量入库漂移 | 直到下一次 `reindex` | 无，属于已知折中 |
| 备份不含 Qdrant | 直到重建完成 | 重建后按 manifest 里的 `qdrant_expect` 对账，超出 5% 要查 |

非当前点清理与 30 天物理删除是两条不同的路径。前者只删 Qdrant 点，不碰 df / blob / PG 行，宽限 5 分钟，worker 每 5 分钟扫一批（最多 1000 份文档）。后者才走六步链。把两者合并，就会重新踩进 df 减不回去的坑。
