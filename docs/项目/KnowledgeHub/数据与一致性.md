# 数据与一致性

Postgres 持有全部事实：账号、库、文档、块、任务、审计、词表、会话，共 18 张表。Qdrant 只有三个可重建的索引 collection。本文沿这个划分写：表结构、原件存储、row 与索引之间的一致性怎么维护，以及发生漂移时如何发现与修复。

![18 张表的四层分组与关键外键](/img/knowledge-hub/data-model.png)

## 1. 18 张表与迁移

| 层 | 表 | 作用 |
|---|---|---|
| 身份与容器 | `users`、`api_keys`、`workspaces`、`workspace_members`、`workspace_invites` | 账号、Key、工作区、成员、邀请码 |
| 内容 | `knowledge_bases`、`documents`、`blobs`、`chunks` | 库、文档版本、原件、块 |
| 任务与审计 | `jobs`、`audit_log` | 异步任务、操作留痕 |
| 检索与对话 | `terms`、`corpus_stats`、`index_models`、`chat_sessions`、`chat_messages`、`chat_day_stats`、`llm_settings` | BM25 词表与语料统计、索引模型登记、会话消息、聊天按天聚合、外部 LLM 配置 |

`migrations/versions/` 下初始迁移是 11 张表，后续迁移发展出 18 张，涵盖 `pg_trgm` 扩展、部分索引与 CHECK 约束改动。时间列统一用 `TIMESTAMPTZ`。软删除统一是 `deleted_at` 字段，查询默认带 `deleted_at IS NULL` 条件。`pgvector` 镜像已安装但项目中不用：向量归 Qdrant，colSmol late-interaction 的多向量形态不是 pgvector 结构能承载的。

CHECK 约束的取值变更不能依赖 alembic autogenerate：autogenerate 只比对外键、索引与列，不检测约束表达式。`chunk_strategy`、`jobs.kind`、`users.role` 几处的取值变更都用手写迁移，且改模型后应跑 `alembic check`，否则会出现「模型里有、库里没有」的漂移。

## 2. 原件：内容寻址与引用计数

由文件的 sha256 决定存储路径：

```
data/blobs/{sha[:2]}/{sha}/original
data/blobs/{sha[:2]}/{sha}/preview.pdf
data/blobs/{sha[:2]}/{sha}/thumbs/{page}.jpg
```

原始文件固定名 `original`：`{sha}` 目录下用 `mkdir` 扩展其他产物（`preview.pdf`、`thumbs/`）不会有冲突。若 `{sha}` 直接作文件名占用，此处会报 `NotADirectoryError`。

同一份内容多处引用只存一份，靠引用计数管理：

| 字段 | 含义 |
|---|---|
| `blobs.sha256` | 主键，同时是目录名 |
| `blobs.ref_count` | 引用该原件的 `documents` 行数 |
| `blobs.storage_path` | 写入时记录的路径（无分发用途） |
| `documents.blob_sha` | 外键指向 `blobs.sha256` |

上传与目录导入两条路径共用 `register_blob` / `register_blob_async`，`blobs` 行漏登记会直接撞 `documents_blob_sha_fkey` 外键错误——外键兜底先行，晚于写盘才会发现。`ref_count` 减到 0 才删目录（动作在物理删除链里，见 §4）。

## 3. chunks 表

`chunks` 是检索的最小单位，其上定义了两个关键索引：

```sql
UNIQUE (doc_id, chunk_index)                          -- 稳定点 ID 的前提
GIN (content_norm gin_trgm_ops)                       -- 子串腿使用的 trgm 索引
```

| 字段 | 用途 |
|---|---|
| `content_norm` | 归一化文本；嵌入与 trgm 都基于它 |
| `char_start` / `char_end` | 在全文中的字符偏移（部分格式有） |
| `locations` | L3 坐标数组 `[{page, bbox, row?, col?}]`；bbox 已归一化 0~1 |
| `kind` | `text` / `table` / `page` / `chat` |
| `table_json` | 表格的结构化网格 `{header, rows}`，前端渲染成真表格 |
| `parent_text` | Parent-Child 策略的父块文本，不进向量库 |
| `section_path` | `H1 > H2 > H3` |
| `token_count` | 估算 token 数 |

表格块的一个特殊语义：`content_norm` 仍是 Markdown 文本，另外带一句纯规则生成的描述（「N 行 × M 列。表头：…」），进检索索引、不外传，让「一览表」类查询靠这句话召回到表格。正文块通常一段落一个框。表格块每个非空单元格一个框并带 `row` / `col`。扫描页只有整页框。

判断「这一行有没有坐标」不能写 `locations IS NULL`：这一列是 JSONB，空列表常存 JSON `null` 而非 SQL NULL。应按内容判断（列表是否为空）。

## 4. 软删、版本与删除链

### 4.1 三字段表达的「哪一版活着」

| 字段 | 含义 |
|---|---|
| `is_current` | 为真时参与检索 |
| `deleted_at` | 非空即进了回收站，30 天后物理清理 |
| `version_id` | 同一 `(kb_id, file_name)` 下的第几版，从 1 递增 |

覆盖式更新时，旧版本 `is_current=false` 且 `deleted_at` 置当前时间，新版本 `version_id` 取「现有最大值 + 1」。取 max 而非「当前版本 + 1」的原因：历史脏数据可能存在多个同名 current，后者会撞回已占用的号。

`supersede()` 是唯一实现，上传与目录导入共用。它本身幂等，已经是历史版本的文档不会被再次处理。

恢复不复用旧向量。`POST /documents/{id}/restore` 与 `POST /kb/{id}/restore` 都将状态置回 `pending` 并重新入队 `ingest`，因为回收站期间可能改过 `chunk_size` 或切分策略，旧块已过时。

### 4.2 删库的时间戳匹配

`delete_kb` 把库的 `deleted_at` 时间戳盖到该库全部当前文档上，共享同一个 stamp。恢复按这个 stamp **精确相等** 匹配：

```python
Document.deleted_at == stamp        # 不是 <=
```

用 `<=` 会把更早被单独删掉的、或被同名新版本顶替的文档一并捞回。

`knowledge_bases` 与 `workspaces` 同样是软删。删工作区不级联软删其下的库与文档，只标记工作区一行。代价是所有可见性判定必须多一条「工作区还活着」的条件（见《多租户与权限》）。

### 4.3 六步物理删除链

物理删除只有一个实现（`ingest/purge.py`），两个入口共用：worker 的 30 天到期清理（选 `deleted_at < now - 30 天` 的文档）与用户手工清空回收站（`DELETE /api/v1/trash`），后者只清调用者指定的范围。

每一步漏了都不报错：

| 顺序 | 动作 | 漏掉的后果 |
|---|---|---|
| 1 | 把 chunk 的 token 从 BM25 词表减回 | `df` 只加不减，idf 被压平，检索质量慢慢变差且无报错 |
| 2 | 删 Qdrant 三个 collection 里该文档的点 | 已删内容仍可被搜到 |
| 3 | 删 `documents` 行 | `chunks` / `jobs` 靠 `ON DELETE CASCADE` 跟着删 |
| 4 | `blobs.ref_count` 减一 | 磁盘只增不减 |
| 5 | 归零才删 blob 目录 | 原件留在磁盘上 |
| 6 | 不动 `audit_log` | 审计行保留 180 天 |

第 1 步用的分词必须和入库时同一个函数（`bm25.tokenize`）。换成 `.split()` 不会报错，只是减掉的 df 与加进去的对不上——这是六步链中最隐蔽的一步。

同步与异步各有驱动（`purge_documents` / `purge_documents_async`），但选择条件的 SQL 与减 df 的算法只有一份：在 `AsyncSession` 上调用同步版不会立刻报错，只是返回一个从不被 await 的 coroutine，所以异步版必须存在且被 worker 使用。

![软删、非当前点清理与 30 天物理删除](/img/knowledge-hub/delete-chain.png)

容器清理（软删的库与工作区）只由 worker 的 30 天路径触发，无独立 API。顺序必须先走其下文档的六步、再删容器行——反过来时，文档先失联，df 减不回去。

## 5. 三腿对账

Qdrant 与 Postgres 之间会漂移，对账给定分腿独立比较：

| 腿 | 期望点来自 | 点 ID |
|---|---|---|
| `kb_dense` | `chunks` 行 | `point_id(kb_id, doc_id, chunk_index)` |
| `kb_sparse` | `chunks` 行 | 同上 |
| `kb_visual` | `documents.scan_pages` | `point_id_for_page(kb_id, doc_id, page)` |

期望集合的 SQL 只有一处：

```sql
SELECT documents.kb_id, chunks.doc_id, chunks.chunk_index
FROM chunks JOIN documents ON documents.id = chunks.doc_id
WHERE documents.kb_id IN (...) AND documents.is_current AND documents.deleted_at IS NULL
```

三个容易踩的坑，各留一条已踩过的证据：

- 期望点的 `kb_id` 必须取自 `documents`，不 join `knowledge_bases`。实测 join 后把期望点数从 399 放大到 8379，报出「缺 8379 个点」的误报。
- 三条腿不能取并集判断。取并集时「只有一条腿坏了」会算成一致，而那正是真实故障（`kb_visual` 恒 0 点）。分腿报缺/多才是能定位的形态。
- `scan_pages IS NULL` 的旧行要跳过，否则该加列之前摄取的文档被当成「应有 0 点」，页级点全报成残留。

对账**只报告、不自动修**。摄取过程中 chunk 行先 `flush` 而不提交、点已 upsert，事务提交之前别的连接看到的就是「点在、行不在」。自动删会把正在写的点删掉，随后行提交，留下永久索引空洞。

## 6. 重建与蓝绿

### 6.1 普通重建

`POST /admin/reindex` 入队 `KIND_REINDEX`（异步任务），默认范围是「调用者可访问的库」而非全库。

重建顺序有三处刻意安排：

1. **先为全体 chunk 重新登记词表**，再动向量。`df` 与 `corpus_stats` 是全局统计量，只重登记目标库会把其他库的 idf 弄坏。
2. **向量只重建目标库，按 `kb_id` 排序逐个来**：切到哪个库，先删这个库的两条文本腿，再重建。不排序时同一个库会在不同位置被删多次，后一次删会把前一次刚重建的点清掉。
3. **视觉腿不动**：页级向量需要重读原件 + colSmol 前向，成本约 15s/页，重建覆盖不了。只能重新摄取。删掉即建不回来，比漂移更糟。

孤儿点（Qdrant 有点、PG 连 `kb_id` 都不存在）清理覆盖三条腿——永远无法被重建，删无可删。首次清理实测给出每条腿 19733 个孤儿点。

### 6.2 蓝绿重建（`swap=true`）

适用对象：所有 collection 都要重建（如换 embedding 模型维度），不能在线做两腿对账。前提是启用别名模式。

```bash
uv run python deploy/bootstrap_index_aliases.py --yes   # 一次性迁移到别名模式
# .env 设 QDRANT_ALIASES=true，重启 API/worker
curl -X POST -H "Authorization: Bearer $KEY" \
  'http://127.0.0.1:8010/api/v1/admin/reindex?swap=true'
```

流程：建影子集合（`kb_dense__<gen>` 等物理名）→ 灌数据 → 验点数 → 原子切别名 → 保留旧集合以便回滚。别名模式下，逻辑名（`kb_dense`）是别名，物理名带代号。`GET /collections` 不列别名，巡检时列物理名。

## 7. 已知的一致性窗口

| 窗口 | 长度 | 兜底机制 |
|---|---|---|
| 软删后 Qdrant 点仍在 | worker 清理间隔最多 5 分钟（`_STALE_SWEEP_INTERVAL=300`） | 检索侧二次过滤 `is_current AND deleted_at IS NULL` |
| 新增 payload 字段只在之后摄取的文档上有 | 直到重新摄取 | 带时间过滤的查询会排除旧点 |
| BM25 idf 随增量入库漂移 | 直到下一次 `reindex` | 无自动修复，属于已知折中 |
| 备份不含 Qdrant，恢复后需重建 | 重建完成时长 | 按 manifest 的 `qdrant_expect` 对账，超出 5% 需查原因 |

非当前点清理与 30 天物理删除是两条不同的路径：前者只删 Qdrant 点、不碰 df/blob/Postgres 行，宽限 5 分钟，worker 每 5 分钟扫一批（最多 1000 份文档）。后者走 §4.3 的六步链。这两条不能合并，合并会把 df 减不回去的问题重新引入。
