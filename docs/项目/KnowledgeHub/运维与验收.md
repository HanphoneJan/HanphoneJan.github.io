# 运维与验收

这一章覆盖交付之后的部分：任务怎么排队与重试、怎么巡检、怎么备份与恢复演练、CI 绿到底覆盖了什么、出问题按什么顺序排查。

![五层测试与各自依赖的基础设施](/img/knowledge-hub/test-layers.png)

## 1. 任务队列

`jobs` 是 Postgres 的一张表，没有 Redis。任务与业务同库，`ON DELETE CASCADE` 能随文档一起清掉待办。规模是几个人的团队，峰值几百条任务，数据库完全承担得起。

| kind | 谁入队 | 成本 | 说明 |
|---|---|---|---|
| `ingest` | 上传、恢复、重解析、重试 | 解析约 50ms/页 + 逐块编码 | 解析 → 切分 → 嵌入 → 写两条文本腿，一个任务做完 |
| `embed_visual` | 摄取时按扫描页/照片 | 15s/页 | 一页一任务，不与 ingest 合并 |
| `thumbnail` | PDF 摄取后 | 约 30ms/页 | 前 20 页，宽 400px |
| `pdf_preview` | Office 摄取后 | 0.7s 起，大 PPT 可 30s+ | LibreOffice 转 PDF，顺带补坐标 |
| `cleanup` | 删库后、定时 | 变化大 | 30 天到期清理、容器清理 |
| `import_chat` | `POST /kb/import/chat` | 分钟级 | 聊天 jsonl 切片成文档 |
| `import_dir` | `POST /kb/{id}/import/dir` | 分钟级 | 服务器目录里的图片批量入库 |
| `reindex` | `POST /admin/reindex` | 分钟级 | 重建词表与两条文本腿 |

两个任务拆分/合并的依据：

- 视觉任务不能并进 `ingest`：单页编码以十秒计，并进去会让一次上传的进度长时间停在 90%，API 侧还区分不出「在编码」还是「在解析」。
- `ingest` 也不拆成三个任务：解析、切分、编码三步加起来通常不到 1 秒（大文档另算），拆开只多三次事务，进度还得跨任务拼装。

## 2. 领取、租约、重试与结算

`jobs.status` 状态机：

```
pending → running → done / failed / cancelled
```

**领取**用 `FOR UPDATE SKIP LOCKED`，多 worker 不抢同一行：

```sql
SELECT * FROM jobs
WHERE status = 'pending' AND (locked_at IS NULL OR locked_at < now() - interval '15 min')
ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED
```

没有 `pending` 时，再找 `locked_at` 超过 15 分钟的 `running` 接管——那就是任务的处理租约。租约必须大于单个任务的最长耗时。视觉任务运行时会周期性心跳续租，15 分钟只是兜底。

入队去重按 `(doc_id, kind, payload)`：payload 不同就不是同一件事（视觉任务按页分 payload，见《文档摄取》§6）。

**心跳**把 `progress` 与业务计数写回 `jobs`，走独立事务，主任务还在跑时 `GET /jobs` 就能读到。payload 用 JSONB `||` 浅合并，不覆盖调用方下发的参数。

**进度封顶**：handler 上报的值压不到 1.0，1.0 只归 `finish_job`。否则会出现 `running + progress=1.0` 的瞬间，前端误读为完成。

**结算**：

| 结局 | 动作 |
|---|---|
| 成功 | `done` + `progress=1.0` |
| 失败可重试且 `attempts < 3` | 回 `pending`，清空锁 |
| 重试耗尽 | `failed` |
| `IngestError.retryable=False` | 第一次就 `failed`，不占重试额度 |
| 文档删除或覆盖版本 | 未完成任务置 `cancelled` |

`is_retryable` 默认 `True`：把「其实瞬时的错误」多试两次的代价有界，反过来把瞬时错误当永久失败，用户要手动补跑。

任务终态后 `settle_doc_state` 给文档行结算，成功失败两条路径都调。它在 `finish_job` 的事务**之外**执行：文档结算失败不能回滚任务结果，否则一次十几秒的视觉前向白跑，任务还会被反复重试。

worker 空闲时轮询间隔从 1s 升到 2s、5s，来任务立刻回到 1s。空闲分支另跑两条旁路：

| 旁路 | 首次延迟 | 间隔 | 动作 |
|---|---|---|---|
| 索引对账 | 180s | 900s | 只报告，不修 |
| 非当前点清理 | 120s | 300s | 删已提交为非当前文档的三腿点 |

忙时不跑对账：那时漂移多半正被正常的摄取与清理修掉，报出来只是噪音。

## 3. 巡检

```bash
uv run python deploy/monitor.py            # 人看
uv run python deploy/monitor.py --json     # cron / CI
uv run python deploy/monitor.py --quiet    # 只在有问题时输出
uv run python deploy/monitor.py --only df index
```

12 个检查函数，报告通常 14 项（Qdrant 函数多两条，另有备份一项）。退出码 0 正常 / 1 有问题。

| 检查 | 抓什么 |
|---|---|
| Postgres 可连 | 库挂了全站 500 |
| Qdrant 活着 / 可列集合 | 索引服务挂了检索降级、摄取全失败 |
| API 健康 | 进程活着但依赖坏了 |
| BM25 df 一致 | `corpus_stats.n_docs` 与 chunk 行数不符，检索质量慢慢变差 |
| Embedding 模型一致 | 建索引用的模型与当前配置不一致，dense 腿静默错排序 |
| 索引对账 dense / sparse | 分腿漂移 |
| 视觉腿对账 | `kb_visual` 点数与 `scan_pages` 不符 |
| 无卡住的文档 | 中间态却无待办任务 |
| 磁盘占用 | 写满会让摄取静默失败（上传仍 202） |
| 无卡住任务 | `running` 超 30 分钟 |
| 失败任务积压（近 24h） | 是否有需要人看的失败 |
| 队列滞后 | 最老 `pending` 等了多久，阈值 30 分钟 |
| 最近有备份（≤3 天） | 恢复点太旧 |

巡检是**三态**，不是两态：通过 / 失败 / 跳过。「跳过」的含义是这项没法验，例如巡检账号没配、`VDR_ENABLED=false`、索引模型还没有记录。跳过的项在报告里标 `?` 而不是 `✓`——`✓` 会让人以为验过了，所以跳过不算健康，退出码按有问题算。

索引对账不走 API：巡检账号无法加入别人的工作区，走 `/admin/consistency` 只能看到自己的库。巡检直连判据（`common/consistency.py`），与 API 端点共用同一份期望集计算。

## 4. 视觉服务的安全边界

8020 上的 visual_service **没有鉴权**，接口只做编码（文本或图 → 向量）。安全边界只有一条：只绑 `127.0.0.1`。三个进程同机，API 走 HTTP 调它，没有跨机需求。

绑到 `0.0.0.0` 的后果：同网段机器可以直接打这个端口。4 个并发槽被占满后，检索的视觉腿一直 `skipped`，照片与扫描页任务持续失败重试。全程没有一条鉴权失败日志——它本来就不鉴权。

确认方式（巡检不覆盖监听地址，这两条是手工项）：

```bash
ss -ltnp | grep 8020        # 期望 127.0.0.1:8020
bash deploy/visual.sh status
```

三条「看起来还在回环、实际已暴露」的路径：

| 路径 | 为什么 |
|---|---|
| 反向代理到外网 | nginx 绑 `0.0.0.0` 再转发到 8020，后端看到的源地址是 `127.0.0.1`，8020 侧没有第二道判断 |
| 容器端口映射 | `-p 8020:8020` 把容器内回环变成宿主机公开端口 |
| 本机 SSRF | 同机上任何能发 HTTP 请求的服务都能打到 `http://127.0.0.1:8020` |

真要跨机共享视觉编码，得加一层带鉴权的反代并给 `services/retrieval/pool.py` 的远端客户端补鉴权头。或者 SSH 隧道把对端 8020 转到本机回环，不改代码。

## 5. 备份与恢复演练

```bash
bash deploy/backup.sh                    # 做一份，写完立即自检
bash deploy/backup.sh --keep 7           # 只留最近 7 份（默认 14）
bash deploy/backup.sh --list             # 列出已有备份与自检结果
bash deploy/backup.sh --verify DIR       # 只校验
```

| 内容 | 是否备份 | 理由 |
|---|---|---|
| Postgres | 是，`pg_dump -Fc` 从容器拷出 | 唯一的权威数据源 |
| `data/blobs/` | 是，tar 打包 | 内容寻址的原件 |
| Qdrant | 否 | 索引可按 `reindex`/重摄取重建 |

Qdrant 不备份替代方案：manifest 里记录三个 collection 的期望点数（`qdrant_expect`），恢复重建后按它对账。manifest 同时记录逐表行数与每件产物的 sha256。

`pg_dump` 的输出先落容器内文件再拷出，不用管道重定向：管道中途断掉会得到大小正常但截断的 dump，恢复时才知道。

恢复默认是演练模式：

```bash
bash deploy/restore.sh --scratch data/backups/<时间戳>              # 临时库 → 对账 → 删掉
bash deploy/restore.sh --force --into pkh data/backups/<时间戳>     # 真恢复前先停 API/worker
```

演练建临时库 `pg_restore`，逐表行数对账、逐个校验 blob sha256，最后删临时库。2026-10-11 在真实数据上跑过一轮：18 张表行数全对，126 个 blob sha256 全对。

恢复后必须重建索引，并把重建点数与 manifest 的 `qdrant_expect` 对账，误差超过 5% 就要查原因。

## 6. 测试分层

| 层 | 规模 | 依赖 | 抓什么 |
|---|---|---|---|
| 后端全量 pytest | 1335 项，80 个 `test_*.py`，约 23k 行 | 真 Postgres + Qdrant + 本地模型 | 端到端、权限、状态机、索引对账 |
| CI 免基础设施单测 | 449 项，27 个文件 | 无 DB、无模型、无服务、无 locale 依赖 | 纯函数、契约解析、文档指向、结构守卫 |
| HTTP 验收三套 | 138 / 218 / 199（2026-10-19 实测） | API + worker；1c/1d 需真实多页 PDF | 权限边界、上传到检索、SSE、MCP/A2A |
| 前端 vitest | 316 项，18 个文件 | Node | 组件、纯函数、状态 |
| 巡检 | 12 个检查函数，约 14 项 | 真服务 + PG + Qdrant | 队列、对账、磁盘、卡住文档、备份 |

全量里的集成用例用 `pytest.mark.skipif` 探测依赖。被跳过只说明本 checkout 缺依赖，CI 不跑它们——CI 绿不覆盖这些用例，这是验收时要区分的覆盖面差异。

测试的异步约束：所有集成用例共一个 session 级 event loop。`common/db.py` 的异步引擎是模块级单例，asyncpg 连接池绑定创建它的 loop。用例里各自 `asyncio.run()` 会报 `attached to a different loop`。

清理测试账号走 `eval/_reset.py::reset_users_and_bm25`，不能裸 `DELETE FROM users`——硬删级联删掉 `chunks`，而 `df` 只在入库与重建维护，删完 `corpus_stats.n_docs` 虚高。

## 7. CI 门禁与契约检查

```bash
bash deploy/ci.sh            # 全部
bash deploy/ci.sh web        # typecheck + vitest + build
bash deploy/ci.sh py         # 契约覆盖率 + 免基础设施单测
```

`deploy/ci.sh` 是 CI 与本地同一条命令，`.github/workflows/ci.yml` 只装依赖再调它。白名单里加测试文件（`PURE_TESTS`）要过三个验证，任一不过就说明文件不纯：

1. 数据库指向不存在的库，仍全绿。
2. 服务地址指向没人听的端口（或确认无真 HTTP），仍全绿。
3. `LANG=C LC_ALL=C` 下前端测试仍全绿（防 `localeCompare` / `toLocaleString` 只在本机绿）。

契约检查：

```bash
uv run python eval/contract_check.py --strict
```

三个数字各有含义：声明 82、实现 81、决议不做 1。`/jobs/{id}/retry` 被实现时，检查会报「与决议相反地实现」。它只对账路径、方法与 query 参数面，字段名与返回类型等形状漂移靠 pytest 与前端测试兜住。

## 8. 排障顺序

**「搜不到」**按序查：

1. `GET /api/v1/health`：`available_legs`、`queue`、`index_models`。
2. `POST /kb/{id}/search/debug`：每腿的 `n` / `ms` / `skipped`。
3. 某腿 `skipped` 就按原因修依赖。全跑了但零命中，查 query 与库范围。
4. 点数与文档数不符，`GET /admin/consistency` 分腿看缺/多。
5. 文档一直处理中，`GET /jobs?doc_id=` 查任务终态，巡检查「卡住的文档」。

**「看到了不该看的」**：

1. `GET /kb` 是否列出该库——列表用 `visible_kb_clause`。
2. 检索结果里是否出现——Qdrant 过滤只按 `kb_id`，范围来自 `readable_kb_ids`。
3. 是否有人用 payload 的 `visibility` / `workspace_id` 做过滤（该字段是摄取时写死的陈旧值）。
4. 工作区软删的 `EXISTS` 是否被写成独立 `or` 分支、是否 `correlate` 到外层行。

**「改了没生效」**：

1. 后端改动重启了吗（`dev.sh restart`），有没有残留 worker 在抢任务。
2. 切分策略、PII 开关只对之后摄取的文档生效，旧文档要 `reparse`。
3. 新增 payload 字段有重摄取欠账，旧点没有该字段。
4. 别名模式下确认当前别名指向哪一个物理集合。

`dev.sh` 没有 `status` / `logs` 子命令。进程状态用 `/health` 与三个日志文件看：

```bash
tail -20 /tmp/pkh_api.log /tmp/pkh_worker.log /tmp/pkh_visual.log
```

磁盘写满时上传仍返回 202，blob 写失败发生在 handler 里，用户看到的是「文档一直 pending」。巡检的磁盘项是能把这类故障前置发现的地方。
