# 架构与进程

> **阅读目标**: 知道有哪几个进程、它们各自背多少内存、哪份数据是真相、模型在哪里加载，以及七个绕不开的设计决策各自的替代方案。

---

## 1. 三个进程的边界

| 进程 | 启动 | 端口 | 常驻内容 | 职责 |
|---|---|---|---|---|
| API | `uv run uvicorn services.api.main:app` | 8010（`PKH_API_PORT`） | bge-small | REST / SSE、MCP、A2A、托管 `web/dist` |
| worker | `uv run python -u -m services.worker.main` | 无 | colSmol（可关） | 轮询 `jobs`、摄取、清理、定期对账 |
| visual_service | `uv run uvicorn services.visual_service.main:app` | 8020（`PKH_VISUAL_PORT`） | colSmol | 只把文本或图片编码成 multi-vectors |

体积与加载耗时见 §4。

`deploy/dev.sh start` 依次拉起三个进程，日志分别落在 `/tmp/pkh_api.log`、`/tmp/pkh_worker.log`、`/tmp/pkh_visual.log`。视觉服务的生命周期单独交给 `deploy/visual.sh`，`dev.sh` 只负责编排，共用同一份实现。

worker 独立的直接原因是单页图片编码的耗时：colSmol 前向一次十几秒，6 路并发时吃掉 8.7 个核。与 API 同进程时，用户提问会排在这些编码后面。

visual_service 独立的原因在内存：它常驻一整份 colSmol，放进 API 意味着每个 API 进程都要背这份内存，2C4G 的机器直接 OOM。它没有鉴权，所以只绑 `127.0.0.1`（安全边界见《运维与验收》§4）；`deploy/visual.sh` 负责起停与扫残留。

三个进程对视觉腿的分工不同：

| 进程 | 编码查询文本 | 构造租户过滤 | 查询 Qdrant |
|---|---|---|---|
| API | 走远端 HTTP | ✅ 本地 | ✅ 本地 |
| worker | 本地（写侧图片编码） | — | 写侧 upsert |
| visual_service | 本地 | ❌ | ❌ |

后两列留在 API 侧不是省事。`build_qdrant_filter` 是租户过滤的入口之一，复制到新进程就多一份会漂的逻辑，而漂移的方向是越权。

## 2. 模块依赖方向

```
services/api      services/mcp      services/worker
      │                │                  │
      ├────────────────┴──────────────────┤
      ▼                                   ▼
services/ingest  ───────────────▶  services/retrieval
      │                                   │
      └──────────────┬────────────────────┘
                     ▼
              services/common
```

| 层 | 允许依赖 | 不允许 |
|---|---|---|
| `common` | 无（只依赖第三方库） | `ingest`、`retrieval`、`api` |
| `retrieval` | `common` | `ingest`、`api` |
| `ingest` | `common`、`retrieval` | `api` |
| `worker` | `common`、`ingest`、`retrieval` | `api` |
| `api` | `common`、`ingest`、`retrieval`、`mcp` | `worker` |
| `mcp` | `common`、`retrieval` | `api` |

`common/jobs.py` 判断异常是否可重试时用 `getattr(exc, "retryable", True)`，没有 `isinstance(IngestError)`。这里就是依赖方向在约束写法：`common` 不能 import `ingest`，否则成环。

`services/api/main.py` 按顺序挂载 19 个路由模块。MCP 与 A2A 挂在根路径（`/mcp`、`/.well-known/agent-card.json`、`/a2a/tasks`），不走 `/api/v1`：MCP 客户端按固定路径找端点，A2A 的 Agent Card 是规范写死的发现路径。前端静态产物最后挂载，否则 `StaticFiles` 会把 `/api/v1/*` 全吃掉。

`routers/` 下 19 个路由模块共用一个请求级会话（`common/deps.py::get_session`）：正常返回时提交，异常时回滚。认证也从这里进，`get_current_user` 解析 `Authorization: Bearer sk-pkh_...` 后调 `load_user_context`，路由里不碰授权头。

## 3. 数据平面：真相与派生

| 存储 | 内容 | 是否真相 | 丢了怎么办 |
|---|---|---|---|
| Postgres | 18 张表：账号、库、文档、块、任务、审计、词表、会话 | 是 | 从备份恢复 |
| Qdrant | `kb_dense`、`kb_sparse`、`kb_visual` 三个 collection | 否，可重建 | 文本两腿 `reindex`；视觉腿重新摄取 |
| 本地盘 `data/blobs/` | 原始文件、Office 转换预览、缩略图 | 原件 | 从备份恢复 |

blob 按内容寻址，路径由 sha256 决定：

```
data/blobs/{sha[:2]}/{sha}/original
data/blobs/{sha[:2]}/{sha}/preview.pdf
data/blobs/{sha[:2]}/{sha}/thumbs/{page}.jpg
```

前两位十六进制分成 256 个子目录，避免单目录堆几十万文件后 ext4 目录项退化。同一份内容被多个文档版本引用时只存一份，`blobs.ref_count` 记引用数，减到 0 才删目录。

Qdrant 的点 ID 由三元组算出来，不用自增序号：

```python
point_id(kb_id, doc_id, chunk_index)          # blake2b-64 后右移一位
point_id_for_page(kb_id, doc_id, page_no)     # chunk_index 传 -(page_no + 1)
```

四点说明：

- **为什么哈希而不是自增**：自增号是存储状态的一部分，重建索引就会变，缓存、反馈、标注这些外部引用全部错位；哈希是三元组的纯函数，同一个 chunk 在任何机器、任何时刻都算出同一个号。
- **为什么右移一位**：Qdrant 的 id 是 uint64，而客户端链路里它常被当有符号 64 位或更窄的数处理（JSON、protobuf `int64`、Java 没有 `unsigned long`、JS `Number` 只有 53 位精度）。右移一位把结果压进 `[0, 2^63)`，牺牲 1 bit 熵换跨语言序列化安全。
- **为什么页用 `-(page_no + 1)` 而不是 `-page_no`**：`page_no` 从 0 开始，直接用 `-page_no` 会让第 0 页和 `chunk_index=0` 算出同一个号；加一之后页级点永远是负数，块级点永远非负，`kb_visual` 里不会混进 chunk 级点。
- **代价**：有效空间从 64 位降到 63 位，碰撞概率翻倍，百万级点下仍在 10^-7 量级。

三条腿共用同一套算法，所以同一个 chunk 在三个 collection 里 id 相同，RRF 融合直接靠它对齐，不需要映射表。重算的前提是 `chunks` 上的 `UNIQUE (doc_id, chunk_index)`（见《数据与一致性》§3）：块序号必须稳定，否则同一个块会算出两个号。

| collection | 向量 | 距离 | 一条点对应 |
|---|---|---|---|
| `kb_dense` | 512 维，匿名向量 | Cosine | 一个 chunk |
| `kb_sparse` | BM25 稀疏，顶层 `sparse_vectors.bm25` | 稀疏（内积语义） | 一个 chunk |
| `kb_visual` | 128 维 multi-vector，命名向量 `text` | Cosine + `max_sim` 比较器 | 一页扫描件或一张照片 |

`data/` 是运行时目录，不进 git。测试、账本、轨迹都按需重建。

## 4. 模型加载边界

三个模型各占链路里的一格，不能互相替代：`bge-small` 做文本语义召回，colSmol 做页级视觉召回，`bge-reranker` 只对已召回的候选做精排。

| 模型 | 在链路里的位置 | 体积 | 加载时机 | 谁加载 | 实测成本 |
|---|---|---|---|---|---|
| `BAAI/bge-small-zh-v1.5` | dense 召回：query 与 chunk 各编一次 | 约 100MB | 进程启动时 `preload_core()` | API、worker | 88ms/chunk，上限 512 token |
| `vidore/colSmol-500M` | 视觉召回：一页图编成一组向量 | 约 2.65GB | 首个视觉任务或首次编码 | worker、visual_service | 加载 13s，编码 15s/图 |
| `BAAI/bge-reranker-v2-m3` | 精排：只重排候选，不参与召回 | — | 首次精排 | API | 114ms/对 |

这三个数字直接决定参数，推导见 §5。精排之所以选 m3 而不是 base：base 单对 53ms 更快，但成对判别只有 2/4，m3 是 4/4。

API 进程恒不加载 colSmol。`services/api/main.py` 的 lifespan 只调 `preload_core()`，异常不阻止启动，只写进 `app.state.model_warmup_error`。

worker 的加载开关有三个分支，启动日志会写明走哪一支：

```bash
VDR_ENABLED=false              # 不加载 colSmol；扫描件/照片不建视觉索引
VISUAL_WRITE_VIA_SERVICE=true  # 写侧走 8020，本进程不加载 colSmol（多 worker 前提）
（都不设）                      # 本地加载 colSmol
```

`VISUAL_WRITE_VIA_SERVICE=true` 之后，摄取依赖视觉服务：它挂了，照片与扫描件的任务会失败并重试。`PKH_WORKERS=4` 必须配这一项，否则 4 个 worker 各背一份视觉模型的常驻内存（体积见上表）。

`HF_HUB_OFFLINE=1` 与 `TRANSFORMERS_OFFLINE=1` 由 `deploy/dev.sh` 导出。换机器前先准备模型缓存，否则加载会失败或慢到几十分钟。

## 5. 实测成本与并发预算

§4 那三个数字决定了下表的每一行。

- **88ms/chunk**：一个 worker 串行编码约 11 chunk/s，`PKH_WORKERS=4` 才到约 45 chunk/s。这是切分大小与 worker 数的调参依据。
- **15s/图**：视觉摄取的真实瓶颈，所以视觉并发压到 4、单次查询超时 2s（见下表）。
- **114ms/对**：精排只对候选集做，候选数涨几倍它就涨几倍，所以候选上限要小（见《检索与问答》§5）。

一次 `hybrid` 检索最多占 4 条 Postgres 连接：请求自己的会话，加上三条 DB 腿各自从会话工厂拿的会话。`trgm` 腿跑在 Postgres 上，`dense` 与 `sparse` 要查词表和索引模型记录。

| 项 | 默认值 | 依据 |
|---|---|---|
| `pg_pool_size` + `pg_max_overflow` | 5 + 5 | 按并发检索数 × 4 估 |
| 视觉查询并发 | 4 | colSmol 在 CPU 上并行度 8.7x，再堆只让每条更慢 |
| 视觉查询超时 | 2.0s | 6 路并发单条 p95 905ms 的两倍余量，含排队 |
| 视觉探活缓存 | 5.0s | 每次检索都探活会多一次 RTT，服务挂掉时那次是连接超时 |
| trgm 语句超时 | 800ms | `word_similarity` 只能 seq scan，10 万 chunk 约 1.4s |

连接池不够时请求排队，延迟变差但不会算错。单机个人库 5+5 够用；并发检索上来要调大。

## 6. 关键设计决策

八个绕不开的选择，各自都有更常见的做法。这一节只给对照，实现在对应章节。

| 决策 | 更常见的替代 | 为什么不选替代 |
|---|---|---|
| 任务用 Postgres 一张表 | Redis 队列 / Celery | 任务与业务同库，`ON DELETE CASCADE` 能随文档一起清掉待办；规模是几个人的团队，峰值几百条任务 |
| 三个进程分开 | 全部塞进 API 进程 | 视觉编码单页以十秒计、6 路并发吃 8.7 个核，同进程时用户提问排在编码后面；一整套视觉模型常驻进 API 会让 2C4G 直接 OOM |
| 点 ID 用三元组哈希 | 自增序号 | 自增号随重建漂移，外部引用错位，三腿还要维护映射表（§3） |
| 融合用 RRF | 分数加权求和 | 四条腿分数量纲不同，加权等于让数值天生大的那条腿说了算（《检索与问答》§3） |
| dense 用小模型常驻 | 更大维度的 embedding | 体积小到能在 API 与 worker 启动时就 `preload_core()`；它每次请求、每个 chunk 都要用，懒加载的首次延迟会打到用户请求上 |
| 精排按库启用 | 全局默认开精排 | 跨库检索时排序取决于「哪些库碰巧配了模型」，结果不可解释（《检索与问答》§5） |
| 向量进 Qdrant，pgvector 装了不用 | 全部留在 Postgres | colSmol 的 late-interaction 是多向量 + MaxSim，不是 pgvector 的形状（《数据与一致性》§1） |
| 生成层默认抽取式 | 默认接外部 LLM | 原文不出本机；接外部模型要显式配置，失败降级并写明原因（《检索与问答》§7） |
