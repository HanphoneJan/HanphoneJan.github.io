# 项目深度拆解

本文面向后端工程师，目标是读完能理解这套系统每个关键设计背后的原因，并能把其中一些做法迁移到自己的项目里。

项目本身是一个多租户知识库加 RAG 检索服务，单机自部署，由三个进程和两个存储组成。

## 1. 项目要解决的问题

个人或小团队手里的资料通常有三类：

- 办公文档：PDF、DOCX、XLSX、PPTX、Markdown；
- 聊天导出：几万条消息，按天分布；
- 照片和扫描件：没有文本层，OCR 识别又经常不可靠。

要做到“问一句话就能定位到原文的那一页、那一句”，有三个真实的难点：

| 难点 | 常见的失败方式 | 这个项目的做法 |
|---|---|---|
| 资料格式杂、质量参差 | 解析出空文档、乱码、表格错位 | 解析器派发表、三层校验、失败降级 |
| 问题形态多样 | 问语义、问编号、问日期、找照片 | 四路召回、查询类型路由、RRF 融合 |
| 引用不可信 | 只给出“相关文档”，点开还要自己找 | 块级坐标引用：页图加命中框，表格按行列画网格 |

更重要的是，这个项目不是演示程序。它有任务队列、进度上报、索引对账、备份、恢复演练、契约检查和巡检。这些不显眼的部分，才决定它能不能长期自部署。

## 2. 预备知识

在理解后面的设计之前，需要先补齐四个技术点，并说明它们在项目里的落点。

### 2.1 PostgreSQL 与 Qdrant：真相源与派生索引

系统同时使用 PostgreSQL 和 Qdrant，但分工并不是“关系数据放 PostgreSQL、向量放 Qdrant”这么简单：

- PostgreSQL 是唯一真相源：用户、工作区、知识库、文档元数据、chunk 文本、任务队列和审计都在这里；
- Qdrant 是可重建的派生索引：`kb_dense` 存稠密向量，`kb_sparse` 存 BM25 稀疏向量，`kb_visual` 存视觉多向量。

由此得到一条贯穿全系统的原则：

> 允许 Qdrant 短暂不一致，绝不允许“PostgreSQL 里有而 Qdrant 里没有”。

删除文档时先修改 PostgreSQL（写入 `deleted_at`，把 `is_current` 置为 `FALSE`），立即生效；然后异步删除索引点。检索时还会用 `is_current` 做一次过滤，所以即使清理任务没跑完，被删的文档也不会被召回。

项目装了 pgvector 却没有用它存向量。原因是镜像自带 `pg_trgm`，子串检索需要它，于是顺带装上了 pgvector；但 pgvector 不支持 late-interaction 多向量，与视觉检索冲突，而且 Qdrant 已经是既有选型。PostgreSQL 只承担真相源、子串检索、任务队列和审计。

### 2.2 BM25 与 pg_trgm：两种字面匹配

- BM25 是词元级算法，擅长人名、术语和关键词。项目用 jieba 分词加自实现 BM25，把稀疏向量存进 Qdrant。
- pg_trgm 是字符级三元组匹配，擅长非词字符串：编号、错误码、文件名片段、手机号。

两者不能互相替代。这里还有一个实测结论：PostgreSQL 内置的 `to_tsvector` 对中文完全无效，整行会被当成一个 token，而镜像里也没有中文分词扩展。所以 BM25 留在 Qdrant 里用 jieba 实现，PostgreSQL 只做字符级子串搜索。

### 2.3 Late-interaction 与 MaxSim：视觉检索

扫描件和照片没有文本层，传统 OCR 又慢又容易出错。项目用 `colSmol-500M` 做多向量 late-interaction：一张图片编码成一组 token 向量，查询文本也编码成一组，用 MaxSim 计算相似度。

代价很具体：

- 模型常驻内存 2.64 GB；
- 单张图片编码约 15 秒，而且与分辨率无关，因为模型内部固定切成 13 个 512×512 的图块；
- 6 路并发时实际耗时 0.96 秒、消耗 CPU 8.36 秒，并行度 8.7 倍，会把整机 CPU 占满。

所以它必须跑在独立进程里，不能和 API 同进程。

### 2.4 RRF：只比较排名

四路检索的分数不在同一个量纲上：

| 通道 | 分数含义 | 实际范围 |
|---|---|---|
| dense | 余弦相似度 | 0.2 到 0.9（有界） |
| sparse | BM25 | 0 到 40 以上（无界） |
| trgm | `word_similarity` | 0.25 到 0.40（窄带） |
| visual | MaxSim | 0 到 1 |

如果要加权求和，就得先把分数归一化，而 min/max 归一化对单次查询的候选集很敏感，z-score 又会被离群值带偏。RRF（Reciprocal Rank Fusion）只看排名，避开了这个问题：

```
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))        k = 60
```

取 `k = 60` 的作用可以从数值上看出来：排名第 1 和第 2 的贡献分别是 `1/61` 和 `1/62`，只差约 0.26%。也就是说，头部名次的微小优势不会压倒第二条通道的共识。“多路都认为相关”要优于“只有一路排第一”，这正是 RRF 想表达的性质。

## 3. 总体架构

```
                      ┌──────────────────────────────────────┐
   浏览器 / 客户端 ──→│ api（FastAPI） :8010                 │──→ Qdrant   :6333
                      │  · 检索编排（四条通道）               │──→ PostgreSQL :5432
                      │  · 托管前端静态产物                   │
                      │  · MCP /mcp · A2A /a2a               │
                      └───────┬──────────────────────────────┘
                              │ 入队任务 / 查询进度
                              ▼
                      ┌──────────────────────────────────────┐
                      │ worker（无监听端口）                  │
                      │  · 轮询任务队列 · 摄取 · 清理         │
                      └──────────────────────────────────────┘

                      ┌──────────────────────────────────────┐
                      │ visual_service :8020                 │
                      │  · 常驻视觉编码模型，启动即预热        │
                      │  · 只做“文本/图片 → 向量”             │
                      │  · 不查 Qdrant，不做租户过滤           │
                      └──────────────────────────────────────┘
```

三个进程的边界不是微服务式拆分，而是被资源特性逼出来的：

| 进程 | 常驻内存 | 为什么单独存在 |
|---|---|---|
| api | 约 400 MB（峰值约 600 MB） | 轻量、常驻，直接服务用户 |
| worker | 约 200 MB（加载视觉模型时峰值约 2.8 GB） | 摄取是 CPU 密集型工作，不能拖慢 API |
| visual_service | 2.71 GB（启动预热约 13 秒） | 视觉编码会占满整机 CPU |

`visual_service` 的边界切得很干净：它只做编码，不连接 Qdrant，也不判断租户。因为租户过滤的唯一入口在 `services/common/auth.py`，复制进第三个进程就会多出一份迟早会漂移的实现，而漂移的方向是越权。视觉检索因此拆成三步：

1. 查询文本编码为多向量，可以在本进程或远端服务完成；
2. 构造租户过滤条件，始终在 API 进程完成；
3. 在 Qdrant 上做 MaxSim 查询，始终在 API 进程完成。

## 4. 摄取链路

从文件上传到可以检索，要经过八个阶段：

```
文件
  → ① 上传（扩展名白名单、大小不超过 50MB、文件头嗅探）
  → ② 按内容寻址写入 blob，插入 documents 行（pending），入队 ingest
  → ③ worker 领取任务（FOR UPDATE SKIP LOCKED）
  → ④ 解析（PDF、Office、文本、图片）
  → ⑤ 执行切分策略（六选一，默认 recursive）
  → ⑥ 分层校验，并做 PII 检出与掩码
  → ⑦ 嵌入并写入索引（文本通道和视觉通道）
  → ⑧ 终态结算（任务状态加索引点数）
```

### 4.1 内容寻址带来的约束：扩展名存在数据库里

blob 按 sha256 存放：

```
data/blobs/<sha[:2]>/<完整 sha>/original
```

同一份文件上传两次只存一份。代价是 blob 路径没有扩展名，所以解析器不能从路径猜格式：

```python
# ❌ 每个 blob 都没有扩展名，解析器会一律报 UnsupportedFormat
suffix = blob_path(doc.blob_sha).suffix

# ✅ 扩展名和 mime 的真相在数据库行里
parse_to_chunks(path, file_name=doc.file_name, ...)
```

这个错误会同时影响两处：解析器和页图渲染端点。因此解析入口强制要求传入 `file_name`。

### 4.2 解析器派发表

`PARSERS` 是一张“后缀到处理器”的映射表，增加一种格式就是增加一条记录。上传白名单也从它派生：

```python
SUPPORTED_SUFFIXES, IMAGE_SUFFIXES = _derive_suffix_sets(PARSERS)
```

这样做的好处是可以测试：测试断言“白名单常量确实等于派发表推导出的结果”，从而抓住“有人又手写了一份白名单”的漂移。历史上真实出现过的漂移就是“白名单里有、实现里没有”。

### 4.3 六种切分策略

切分是知识库级单选，默认使用 `recursive`。没有一种策略能通吃所有文档：

| 策略 | 边界怎么定 | 代价或前提 |
|---|---|---|
| `fixed` | 固定长度加 overlap 硬切 | 会切断句子，语义上最差；主要作为评测基线 |
| `recursive` | 标题、段落、硬切逐级降级 | 默认值，也是向后兼容契约 |
| `semantic` | 句子向量相似度低于阈值就断开 | 需要句向量编码器；PDF 不执行 |
| `parent_child` | 子块进向量库，父块（章节或整页）进上下文 | 父块文本不进向量库 |
| `late` | 整篇经过 Transformer 后按 span 池化 | 受 512 token 上限约束 |
| `contextual` | 每块前置一段 LLM 生成的上下文 | 需要显式配置外部 LLM |

有两个顺序约束容易踩错：

- 策略在解析之后、PII 掩码之前执行：策略作用于“内容”，而 PII 掩码必须作用在最终入库的文本上；
- PII 先检出再掩码：计数必须记录掩码前的数量，否则报告永远显示“0 处 PII”。

策略失败一律降级：未知策略、策略抛异常、依赖缺失，都退回 `recursive`，并把原因写进 `documents.quality.strategy_notes`。不能让“想用新切法”导致摄取失败。

## 5. 检索链路

一次 `hybrid` 检索的流程是：

```
auth：API Key → UserContext(readable_kb_ids)
  → routing：判断查询意图（photo / scan / table / chat / date / general）
  → engine：并行执行四条通道
       dense   编码查询 → Qdrant
       sparse  查 PostgreSQL 词表算 BM25 权重 → Qdrant
       trgm    在 PostgreSQL 里做 word_similarity
       visual  编码 → 构造过滤条件 → MaxSim 查询
  → fusion：RRF 融合，得到候选池
  → 软删除二次过滤
  → routing.prefer：按意图做软偏好过滤
  → rerank：仅当知识库配置了精排模型时执行
  → ask：组装证据 → 生成 → 校验引用
```

### 5.1 四条通道真并发，但每条数据库通道持有自己的会话

项目早期文档写的是“四条通道并发”，而代码里踩过一个更深的问题：

- dense、sparse、trgm 都要访问数据库，如果共用一个 `AsyncSession`，SQLAlchemy 不允许并发 `execute`；
- 并发会让 sparse 和 trgm 被记成 `skipped`，`hybrid` 静默退化成 dense 单通道，接口仍然返回 200；
- 第一版修法是加锁串行执行，结果正确（56 + 153 + 45 约 254 毫秒），但丢掉了并发的收益；
- 现在的做法是每条数据库通道各拿一个会话，也就是各自占一条连接，四条通道真正并发；视觉通道不访问数据库，同样并发。

代价从延迟变成了连接数：一次 `hybrid` 最多占用请求会话加三条通道，共 4 条连接，连接池要按“并发检索数 × 4”估算。连接不够时请求会排队，结果仍然正确，只是延迟退化。

这是一个典型的“看起来正常、实际能力已经退化”的问题，也是后面反复强调“降级必须如实报告”的原因。

### 5.2 查询路由：拿不准就不路由

路由只做两件事：调整通道权重，以及增加软偏好。它不改变 `mode`，也不改变 RRF 的 `k`。

| 意图 | 通道权重 | 偏好 |
|---|---|---|
| `photo` | `visual 3.0` | 照片库 |
| `scan` | `visual 2.0` 加 `sparse 1.2` | 整页或表格块 |
| `table` | `sparse 1.3` 加 `trgm 1.2` | 表格块 |
| `chat` | `sparse 1.6` | 聊天块与聊天库 |
| `date` | `sparse 2.5` | 无 |
| `general` | 全部为 1.0 | 无 |

置信度低于 0.35 时返回等权结果且不做偏好过滤，行为与引入路由之前完全一致。偏好过滤后如果为空，会自动退回全部结果，并如实说明原因。宁可少优化一点，也不要用一个猜错的意图把结果过滤空。

`photo` 对应的 `visual 3.0` 是实测出来的：3.0 是能让照片点把融合池装满的最小值，再往上没有收益。

### 5.3 降级：只降级，不返回 500

核心纪律是：检索通道属于增强项。任何一条通道不可用，都返回 `skipped` 和可操作的原因，其它通道照常返回结果。

| 通道 | 什么情况下标记 `skipped` | 原因文案的要求 |
|---|---|---|
| `visual` | 远端编码服务不可达、超时或返回 503 | 说清怎么修 |
| `dense` | 索引和查询使用的嵌入模型不一致 | 说清“索引用的是哪个、现在配的是哪个、怎么修” |
| `rerank` | 未配置或模型不可用 | 区分“未配置”和“不可用” |
| 任意通道 | 抛出异常 | `ok=false` 加原因 |

`skipped` 是字符串或 `null`，不是布尔值，因为前端要显示原因。一个没有内容的 `skipped: false` 会让人查错方向。

## 6. 多租户：过滤只有一个来源

### 6.1 租户来自 API Key

系统从 API Key 推导出 `UserContext`，其中的 `readable_kb_ids` 表示这个用户可以读取的知识库集合。请求体里不接受 `user_id`，也不接受“我是管理员”这类字段。跨库搜索可以传 `kb_ids` 子集，但它只用于求交：实际范围等于可读集合与请求子集的交集，只会更小。

### 6.2 三档可见性必须写成三个独立分支

```python
# ❌ 这样写有两个独立漏洞
or_(visibility.in_(("workspace", "global")), created_by == me)

# ✅ 三个档位各有各的限定条件
global    → 所有用户可见
workspace → visibility == 'workspace' AND workspace_id IN (我的工作区)
private   → created_by == 我
```

`IN` 表达的是“任一条件成立即可”，而可见性要表达的是“不同档位有不同的限定条件”，两者语义不匹配。

修复时还有一个常见的二次错误：保留裸的 `workspace` 分支，把带成员资格限定的分支追加成另一个 `or`，等于没有修改。两个条件必须写在同一个 `and_` 里。

由此得到一条推论：任何附加的限定条件，都要先问它是 `or` 的一项还是 `and` 的一项。拿不准就写成 `and_(or_(可见性...), 额外限定)`，让结构本身表达意图。

### 6.3 无权限等于不存在

没有权限访问某个知识库时，返回的错误和“这个资源真的不存在”完全相同（`KB_NOT_FOUND` 加 403）。如果分成两种错误码，攻击者就能通过差异探测资源是否存在。

过滤条件有两个构造入口，但都只读同一份 `readable_kb_ids`：

| 函数 | 服务的存储 |
|---|---|
| `build_qdrant_filter` | Qdrant（dense、sparse、visual） |
| `build_kb_scope_sql` | PostgreSQL（trgm 通道） |
| `visible_kb_clause` / `writable_kb_clause` | PostgreSQL 的知识库列表与回收站 |

之所以不是一个函数，是因为有一条通道运行在 PostgreSQL 里，拿不到 Qdrant 的过滤字典。但这两个函数都不各自重新计算可见性。历史上唯一一次真实越权，正是因为两处各自复刻了可见性逻辑。

## 7. 可以迁移的可靠性做法

这一节是整套系统里最值得迁移的部分。

### 7.1 真相源与派生索引分离

- PostgreSQL 写入立即生效，Qdrant 异步清理；
- 检索时用 PostgreSQL 的 `is_current` 做二次过滤；
- 对账任务按通道分别报告“PostgreSQL 有而这条通道缺”和“这条通道有而 PostgreSQL 缺”，只报告，不自动修。

设计立场很明确：没有被对账覆盖的检索通道，等于不存在。增加一条通道，就要增加一条对账。

### 7.2 文档终态要同时看两件事

`jobs.status` 和 `documents.status` 是两套状态：

- 只看任务状态，部分失败会被报成 `ready`；
- 只看索引点数，全部失败时文档会永远停在 `pending`。

所以终态判定要同时看“任务是否全部进入终态”和“索引里实际有多少点”。此外，结算必须发生在任务收尾事务之外，并且不抛异常，否则一次状态写入失败会把 15 秒的模型前向计算一起回滚。

### 7.3 降级要如实记录

视觉通道不可用、嵌入模型不一致、精排不可用、Contextual 切分缺少 LLM，这些情况的统一做法是记录 `skipped`、note 或 `degraded`，让用户看得见。静默降级的代价是用户以为自己正在使用某个能力，实际并没有。

### 7.4 巡检要有三态

`deploy/monitor.py` 有十四项检查，其中“跳过”不算健康。跳过通常意味着这项检查没法验证，例如没有配置巡检 Key。巡检一半没跑成却报告“一切正常”，是监控工具最糟糕的失败。

退出码 0 和 1 要能被 cron 使用，否则“报警”就无从谈起。

### 7.5 备份必须恢复过

备份包含 PostgreSQL 和 `data/blobs/`，不备份 Qdrant，因为索引可以重建。但备份目录里有 `manifest.json`，记录各表的精确行数、每个 blob 的 sha256，以及 Qdrant 的期望点数。恢复演练会建一个临时库，逐表对账，逐个校验 blob，然后删掉临时库。

> 没有恢复过的备份只是一堆文件。

### 7.6 用测试固定架构约束

- 端点契约由 `eval/contract_check.py` 对账路径、方法和参数面；
- 关键架构约束用 AST 扫描固定：租户过滤不得出现在别处、检索实现只能有一份、不得有未 await 的协程；
- 已跟踪文件不得包含真实数据，由 denylist 守卫；
- 文档里的路径、命令和端口也有守卫。

这比“写在文档里希望大家遵守”可靠得多。

## 8. 隐私设计：默认不外传

隐私是项目的第一个卖点，不是事后补的合规声明。

| 设计 | 做法 | 代价 |
|---|---|---|
| 默认抽取式生成 | 答案句子全部摘自原文 | 不做归纳；需要归纳要显式接外部 LLM |
| 外部 LLM 显式配置 | 全局单例配置，`enabled` 加用途开关 | 打开就意味着原文会离开本机 |
| PII 掩码按库开关 | 只掩索引侧，原件、预览和下载仍是原文 | 打开后就搜不到自己的号码 |
| 视觉编码只在专用进程 | API 进程恒不加载 colSmol | 多一个进程和 2.65 GB 内存 |
| 外部生成器失败时降级 | 401、超时或 5xx 时退回抽取式并写 `degraded` | 这一轮没有归纳，但不会返回 500 |

PII 检出报告只回答“哪里有、有多少”，不返回原文片段，否则报告本身就成了新的泄露面。掩码默认关闭，因为个人知识库的核心用途之一恰恰是“搜我自己的证件号”。

## 9. 性能数据与测量条件

| 指标 | 实测值 | 测量条件 |
|---|---|---|
| dense 单通道 | 56 毫秒 | 同一评测集 |
| sparse 单通道 | 153 毫秒 | 同上，四路里召回最强 |
| trgm 单通道 | 约 45 毫秒 | 同上 |
| 检索段 | 约 312 毫秒 | 单库 hybrid，包含融合 |
| 视觉查询编码 | 每条 119 到 128 毫秒 | p95 为 157 毫秒 |
| 视觉单图编码 | 约 15 秒 | float32，与分辨率无关 |
| 视觉模型常驻内存 | 2.64 GB | 启动预热约 13 秒 |
| 6 路视觉并发 | 实际 0.96 秒，消耗 CPU 8.36 秒 | 并行度 8.7 倍 |
| 内存峰值 | api 约 0.6 GB、worker 约 2.8 GB、visual 约 2.7 GB | 单机 15 GB |

问答的目标是首 token 小于 2 秒，检索段小于 500 毫秒。生成段靠 SSE 逐字输出掩盖慢速：本机抽取式是毫秒级，接外部 LLM 时可能是每秒 3 到 8 个 token。

单个数字脱离测量条件没有意义。例如把四类语料混在一起算出的 overall R@10，就不能用来做取舍；视觉通道只索引扫描页和照片，把文本提问混进去算总平均，只会得到无法解释的数字。

## 10. 边界与取舍

| 边界 | 现状 | 理由 |
|---|---|---|
| 文件存储 | 只有本地磁盘和内容寻址 blob，没有对象存储 | 单机自部署是目标形态；真要上第二台机器时，先做只读远端副本 |
| 不做归纳 | 默认抽取式 | 引用 100% 可核验，且不外传 |
| 精排默认关闭 | 按知识库开启 | 只能重排候选，不能扩大召回；CPU 上处理 20 个候选需要 0.6 到 1.2 秒 |
| 不引入多节点 | 没有分片，没有副本 | 这个规模下复杂度换不来收益 |
| 不做 OCR | 扫描件交给视觉检索 | 不引入 tesseract 这条独立链路 |
| 表格结构化只覆盖 PDF、CSV、XLSX | DOCX、HTML、PPTX 里的表格仍按纯文本处理 | 工程量与收益的取舍 |
| 文档没有可信的撰写日期 | 文件名是编号或修订年份，mtime 是拷贝日期 | 不猜 |
| 前端没有超时保护 | Python 死循环会卡死标签页 | 需要 COOP/COEP 加 Web Worker，先记为限制 |

## 11. 从零实现的顺序

如果重新实现一遍，建议按下面的顺序推进：

1. 先做真相源：PostgreSQL 表、内容寻址 blob 和任务队列，确保上传后能查到元数据。
2. 接一条文本通道：解析、切分、dense 嵌入、写入 Qdrant，先让语义相似可用。
3. 补字面通道：BM25（jieba）和 trgm。很多“搜不到”其实是缺少字面匹配，而不是语义模型不行。
4. 加 RRF：先只比较排名，把多路融合跑通，再考虑权重。
5. 加引用坐标：解析期保存归一化 bbox，前端乘回页图尺寸后画框。没有坐标的引用只是装饰。
6. 加租户隔离：从登录态推导可读集合，过滤条件只在一处构造，无权限与不存在返回同一个错误码。
7. 加视觉通道：拆成独立进程，接入远端编码服务，失败时降级为 `skipped`。
8. 加运维闭环：巡检、对账、备份、恢复演练、契约检查。
9. 最后再调质量：查询路由、精排、改写、拒答、时间过滤。每一项都必须能关掉，默认路径保持不变。

这条顺序的核心是：先让系统可信，再让它聪明。引用、隔离、降级和对账，都是“可信”的组成部分。
