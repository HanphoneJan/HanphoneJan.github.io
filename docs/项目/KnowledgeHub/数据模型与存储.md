# 数据模型与存储

本文只描述当前实现，不讨论设计理由。想看“为什么这样设计”，请读[架构总览](./架构总览.md)和[项目深度拆解](./项目深度拆解.md)。

## 1. 存储拓扑

```
PostgreSQL 16（pgvector/pgvector:pg16）
  真相源：用户、工作区、知识库、文档、chunk 元数据、
          任务队列、审计日志、全文子串索引（trgm）、会话与消息

Qdrant 1.15.1（standalone 二进制）
  kb_dense   dense 512 维      bge-small-zh-v1.5
  kb_sparse  sparse           jieba + BM25
  kb_visual  multi 128 维     colSmol-500M（max_sim）

本地文件系统
  data/blobs/{sha[:2]}/{sha}/original|preview.pdf|thumbs/
```

项目装了 pgvector 却没有用它存向量，原因有两条：全局只用一个嵌入模型，而且 Qdrant 已经是既有选型；pgvector 不支持 late-interaction 多向量。装 pgvector 只是为了顺带拿到镜像里的 `pg_trgm`。

## 2. PostgreSQL 表结构

### 2.1 身份与工作区

```sql
CREATE TABLE users (
    id            BIGSERIAL PRIMARY KEY,
    email         CITEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,              -- argon2
    display_name  TEXT NOT NULL,
    role          TEXT NOT NULL DEFAULT 'user'
                  CHECK (role IN ('user','superadmin')),  -- 全局角色
    nickname      TEXT UNIQUE,                -- 唯一昵称，可作登录名
    is_active     BOOLEAN NOT NULL DEFAULT TRUE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE workspaces (
    id BIGSERIAL PRIMARY KEY, name TEXT NOT NULL, description TEXT,
    owner_id BIGINT NOT NULL REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(), deleted_at TIMESTAMPTZ
);

CREATE TABLE workspace_members (
    workspace_id BIGINT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id      BIGINT NOT NULL REFERENCES users(id)      ON DELETE CASCADE,
    role         TEXT NOT NULL CHECK (role IN ('owner','member')),
    invited_by   BIGINT REFERENCES users(id),
    joined_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (workspace_id, user_id)
);
```

角色只有两档，暂不做完整的 RBAC。`users.role` 是全局角色，`workspace_members.role` 是工作区内的 owner 或 member，两者不是一回事。

邀请码表 `workspace_invites` 只保存 HMAC-SHA256 哈希和前 4 位，不保存明文。默认有效期 7 天、可用 1 次，`used <= max_uses` 由数据库 CHECK 约束保证。

### 2.2 知识库

```sql
CREATE TYPE kb_visibility AS ENUM ('private', 'workspace', 'global');
CREATE TYPE kb_source_kind AS ENUM ('file', 'chat', 'photo');

CREATE TABLE knowledge_bases (
    id BIGSERIAL PRIMARY KEY,
    workspace_id BIGINT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    name TEXT NOT NULL, description TEXT,
    visibility   kb_visibility  NOT NULL DEFAULT 'private',
    source_kind  kb_source_kind NOT NULL DEFAULT 'file',
    embed_model  TEXT NOT NULL DEFAULT 'BAAI/bge-small-zh-v1.5',  -- 全局统一
    chunk_size   INT  NOT NULL DEFAULT 500,
    chunk_overlap INT NOT NULL DEFAULT 50,
    chunk_strategy TEXT NOT NULL DEFAULT 'recursive',
    generate_image_desc BOOLEAN NOT NULL DEFAULT FALSE,
    rerank_model TEXT,                    -- 空表示不启用精排
    pii_mask     BOOLEAN NOT NULL DEFAULT FALSE,
    created_by   BIGINT NOT NULL REFERENCES users(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at   TIMESTAMPTZ
);
CREATE INDEX ON knowledge_bases (workspace_id) WHERE deleted_at IS NULL;
```

### 2.3 文档

```sql
CREATE TYPE doc_status AS ENUM
  ('pending','parsing','chunking','embedding','ready','failed','deleted');
CREATE TYPE doc_source AS ENUM ('upload','chat_import','photo_dir');

CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    kb_id BIGINT NOT NULL REFERENCES knowledge_bases(id) ON DELETE CASCADE,
    file_name    TEXT NOT NULL,           -- 覆盖式更新，同一 (kb_id, file_name) 可有多个版本
    source_path  TEXT,                    -- 聊天知识库专用，例如 chat-2025-02-14
    content_hash TEXT NOT NULL,           -- sha256，用于判重
    blob_sha     TEXT NOT NULL REFERENCES blobs(sha256),
    mime_type    TEXT, size_bytes BIGINT,
    doc_source   doc_source NOT NULL DEFAULT 'upload',
    status       doc_status NOT NULL DEFAULT 'pending',
    status_msg   TEXT,                    -- 失败原因
    quality      JSONB,                   -- 三层校验报告
    is_current   BOOLEAN NOT NULL DEFAULT TRUE,
    version_id   INT NOT NULL DEFAULT 1,
    page_count   INT, chunk_count INT DEFAULT 0,
    scan_pages   INT[],                   -- 页级索引的 PostgreSQL 真相来源，NULL 表示未知
    pii_hits     JSONB,                   -- 摄取时掩码前记录
    taken_at     TIMESTAMPTZ,             -- 照片拍摄日期，来自 EXIF 或文件名，不猜
    uploaded_by  BIGINT NOT NULL REFERENCES users(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at   TIMESTAMPTZ
);
CREATE INDEX ON documents (kb_id) WHERE is_current AND deleted_at IS NULL;
CREATE INDEX ON documents (status) WHERE deleted_at IS NULL;
```

有几个字段的语义容易记错：

| 字段 | 含义 | 常见误解 |
|---|---|---|
| `id` | 文档主键 | 不是 `doc_id`。`DocumentOut` 上有一个 `doc_id` property，但 pydantic 不会序列化普通 property |
| `version_id` | 同一 `(kb_id, file_name)` 的版本号 | 覆盖式更新时加 1，不保留完整版本历史 |
| `is_current` | 是否是当前版本 | 检索只返回 `is_current` 为真的文档 |
| `quality` | 三层校验报告加 `strategy_notes` | 扫描件的 `parse` 是 `skipped`，不是 `passed` |
| `scan_pages` | 哪些页走视觉通道 | 视觉通道对账时以这里为 PostgreSQL 侧的真相 |
| `pii_hits` | 掩码前的检出数量 | 开启掩码后仍然能回答“原文里有多少” |

### 2.4 Blob（内容寻址存储）

```sql
CREATE TABLE blobs (
    sha256 TEXT PRIMARY KEY, size_bytes BIGINT NOT NULL, mime_type TEXT,
    storage_path TEXT NOT NULL, ref_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

这里不使用 `ON DELETE CASCADE` 直接删文件，因为同一份文件可能被多个文档版本引用，覆盖式更新后旧版本仍然在回收站里。只有引用计数归零时才物理删除。

需要特别注意，`storage_path` 这一列不是存储抽象。写入时它保存的是 `str(blob_path(sha256))`，没有任何代码读取它来做分发。将来要上对象存储时，先做只读的远端副本。

### 2.5 Chunk 元数据

```sql
CREATE TABLE chunks (
    id BIGSERIAL PRIMARY KEY,
    doc_id BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index INT NOT NULL,
    content_norm TEXT NOT NULL,          -- 归一化文本，用于嵌入
    char_start INT, char_end INT,        -- 在原文中的偏移
    locations JSONB,                     -- 引用坐标矩形数组，归一化到 0 到 1
    token_count INT,
    kind TEXT NOT NULL DEFAULT 'text',   -- text | table | page | chat
    table_index INT, row_count INT, col_count INT,
    table_json  JSONB,                   -- 表格结构化网格 {header,rows,row_count,col_count}
    parent_text TEXT,                    -- 父块上下文，不进向量库
    section_path TEXT,                   -- 章节路径 H1 > H2 > H3
    CONSTRAINT ck_chunk_kind CHECK (kind IN ('text','table','page','chat')),
    UNIQUE (doc_id, chunk_index)
);
CREATE INDEX ON chunks (doc_id);
CREATE INDEX chunks_trgm ON chunks USING gin (content_norm gin_trgm_ops);
```

实测依据如下：bbox 归一化后的往返误差是 0.00e+00 point，与 DPI 无关；正文 chunk 恰好有一个框；表格 chunk 每个非空单元格一个框，实测最多 40 个，带 `row` 和 `col`；坐标提取成本约为每页 8 到 9 毫秒。

画框时必须先把归一化坐标乘回 PDF point。表格框要取自 `tbl.rows[i].cells`，不是扁平的 `tbl.cells`。

### 2.6 任务队列

```sql
CREATE TABLE jobs (
    id BIGSERIAL PRIMARY KEY,
    kind TEXT NOT NULL,                  -- ingest / embed_visual / thumbnail / pdf_preview
                                         -- cleanup / import_chat / import_dir / reindex
    doc_id BIGINT REFERENCES documents(id) ON DELETE CASCADE,
    kb_id  BIGINT REFERENCES knowledge_bases(id) ON DELETE CASCADE,
    status TEXT NOT NULL DEFAULT 'pending'
           CHECK (status IN ('pending','running','done','failed','cancelled')),
    progress REAL NOT NULL DEFAULT 0,
    attempts INT NOT NULL DEFAULT 0,
    max_attempts INT NOT NULL DEFAULT 3,
    error TEXT, payload JSONB,
    locked_at TIMESTAMPTZ, locked_by TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX jobs_poll ON jobs (status, created_at) WHERE status = 'pending';
CREATE INDEX jobs_doc ON jobs (doc_id);
```

worker 领取任务的协议如下，用来防止重复消费：

```sql
UPDATE jobs SET status='running', ...
WHERE id = (
  SELECT id FROM jobs
  WHERE status='pending'
    AND (locked_at IS NULL OR locked_at < now() - interval '5 min')
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
) RETURNING *;
```

这里刻意不用 ENUM，因为 alembic 的 autogenerate 不会检测 ENUM 或 CHECK 的值变更，用 TEXT 加 CHECK 至少能让人看见差异。修改任何 kind 都要在三处登记：`common/jobs.py` 的 `ALL_KINDS`、`worker/handlers/__init__.py` 的 `HANDLERS`、`models.py` 的 CHECK 约束，另外还要一条手写迁移。

### 2.7 认证与审计

```sql
CREATE TABLE api_keys (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    key_hash TEXT NOT NULL UNIQUE,        -- 完整的 sha256(明文)，不存明文
    key_prefix TEXT NOT NULL,             -- 前若干位，用于界面展示
    scopes TEXT[] NOT NULL DEFAULT '{kb:read,chat:read}',
    last_used_at TIMESTAMPTZ, expires_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE audit_log (
    id BIGSERIAL PRIMARY KEY,
    api_key_id BIGINT REFERENCES api_keys(id), user_id BIGINT REFERENCES users(id),
    action TEXT NOT NULL,       -- search | ask | mcp_call | a2a_call | upload ...
    kb_ids BIGINT[],            -- 审计三元组：key、user、kb
    detail JSONB,               -- query 摘要、结果数、耗时
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX audit_user_time ON audit_log (user_id, created_at DESC);
CREATE INDEX audit_time ON audit_log (created_at DESC);
```

明文 API Key 只在创建时返回一次。吊销的方式是删除数据行，没有 `revoked_at` 列。

### 2.8 外部 LLM 配置

```sql
CREATE TABLE llm_settings (
    id INT PRIMARY KEY DEFAULT 1,        -- 全局单例
    provider TEXT NOT NULL DEFAULT 'extractive'
             CHECK (provider IN ('extractive','openai_compat')),
    base_url TEXT, model TEXT,
    api_key TEXT,                        -- 明文，必须能发给上游；读端点只回掩码
    extra_headers JSONB NOT NULL DEFAULT '{}'::jsonb,
    temperature REAL NOT NULL DEFAULT 0.3,
    enabled BOOLEAN NOT NULL DEFAULT FALSE,
    use_for_ask BOOLEAN NOT NULL DEFAULT TRUE,
    use_for_contextual BOOLEAN NOT NULL DEFAULT TRUE,
    updated_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

没有数据行就表示使用抽取式，原文零外传，这正是隐私默认。迁移不会插入默认行。只有 `provider='openai_compat'`、`enabled` 为真，并且 base_url、model、api_key 齐全时，生成层才真的会把原文发出去。

`extra_headers` 是接特殊网关的硬需求。某些 OpenAI 兼容网关要求自定义请求头，缺少它会直接返回 400。

### 2.9 索引模型记录

```sql
CREATE TABLE index_models (
    collection    TEXT PRIMARY KEY,     -- kb_dense / kb_visual
    model         TEXT NOT NULL,
    dim           INT  NOT NULL,
    model_version TEXT,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

需要这张表，是因为索引和查询必须使用同一个模型。否则就是在两个向量空间里计算相似度，排序基础整个失效，而且不会报错。入库或重建时写入，dense 通道查询前校验，不一致就标记 `skipped`，`/health` 的 `index_models` 如实汇报。稀疏通道是词法算法，不记录。

### 2.10 会话、聊天与语料统计

| 表 | 用途 | 关键点 |
|---|---|---|
| `chat_sessions` | 多轮会话 | 新增 `kb_ids` 表示检索范围，`null` 表示全部有权限的库；`kb_id` 可以为空 |
| `chat_messages` | 消息历史 | 只保存引用编号，不保存来源身份，所以历史里的 `[n]` 点不出原文 |
| `chat_day_stats` | 聊天时间线的按天汇总 | 聊天知识库的时间线视图 |
| `terms` / `corpus_stats` | BM25 词表与语料统计 | 全局量；入库时增加，删除时减少，必须有统一的减法入口 |

## 3. Qdrant 索引布局

### 3.1 三个集合而不是一个

Qdrant 的单个集合不支持把匿名向量和命名多向量混在一起，而 `kb_visual` 使用的是命名向量 `text` 加 `multivector_config`。

| 集合 | 向量类型 | 模型 | 承载 |
|---|---|---|---|
| `kb_dense` | dense 512 维 | bge-small-zh-v1.5 | 所有文本 chunk |
| `kb_sparse` | sparse | jieba BM25 | 同上，提供词元级精确匹配 |
| `kb_visual` | multi 128 维 max_sim | colSmol-500M | 扫描件页和照片 |

三个集合的点 ID 完全一致，同一个 chunk 同时有 dense 和 sparse 两个点。检索时并行查询，再用 RRF 融合。一致性靠的就是“点 ID 由业务键算出来”；如果退化成全局连续序号，三条通道就对不上了。

### 3.2 稳定点 ID

```python
def point_id(kb_id: int, doc_id: int, chunk_index: int) -> int:
    """blake2b-64 哈希，稳定可复算，删除后重建不会冲突"""
    h = hashlib.blake2b(f"{kb_id}\x00{doc_id}\x00{chunk_index}".encode(), digest_size=8)
    return int.from_bytes(h.digest(), "big") >> 1   # 留出符号位
```

页级点另有 `point_id_for_page(kb_id, doc_id, page_no)`，`kb_visual` 用的就是它，其中 `chunk_index = -(page_no + 1)`。实测 10 万个 chunk 没有冲突。

由此得到一个推论：重建索引后，同一文档同一 chunk 的 ID 不变，所以可以“临时删掉索引，再用同一个脚本重建”。

### 3.3 Payload schema

三个集合使用统一的 payload，方便 RRF 融合时对齐：

`kb_id`、`doc_id`、`chunk_index`、`source_kind`、`owner_id`、`workspace_id`、`visibility`、`kind`、`page`、`embed_model`、`text_norm`、`text_raw`、`file_name`、`mime`、`locations`，以及可选的 `table_index`、`parent_text`、`section_path`、`updated_at`。

每个集合都要建以下 payload 索引，共 6 个：

- `kb_id`（keyword，最高优先级）
- `workspace_id`（keyword）
- `doc_id`（integer）
- `source_kind`（keyword）
- `visibility`（keyword）
- `updated_at`（datetime，用于时间过滤）

建索引时要带 `?wait=true`。另外，`payload_schema` 在 GET 响应的顶层。

### 3.4 别名模式与蓝绿重建

逻辑名（`kb_dense`、`kb_sparse`、`kb_visual`）在别名模式下是别名，真正存数据的是带代次后缀的物理集合。

| 模式 | 开关 | `kb_dense` 是什么 | 是否支持蓝绿重建 |
|---|---|---|---|
| 默认 | `QDRANT_ALIASES=false` | 真实集合，与历史行为逐字一致 | 否 |
| 别名 | `QDRANT_ALIASES=true` | 指向 `kb_dense__<gen>` 的别名 | 是 |

```bash
# 一次性迁移：把现有真实集合复制成物理集合，再建立别名
uv run python deploy/bootstrap_index_aliases.py --yes

# 蓝绿重建（需要超管权限）：建影子集合 → 验证 → 原子切换别名 → 保留旧集合以便回滚
curl -XPOST '/api/v1/admin/reindex?swap=true' -H "Authorization: Bearer <超管 key>"
```

有几点需要注意：

- 别名不会出现在 `GET /collections` 里（实测），所以巡检和 `/health` 列出的是物理集合名；对账使用逻辑名经别名查询，照常工作。
- 迁移和切换都有毫秒级窗口（删除原集合、建立别名之间），期间该通道读取会得到 404，检索降级为 `skipped`，不会返回 500。
- 视觉通道不参与重建。它需要重新读取原件并跑 colSmol 前向计算，那属于“重新摄取”。影子重建只覆盖 dense 和 sparse。

## 4. 级联删除与一致性

一致性原则是：PostgreSQL 是真相源，Qdrant 是可重建的派生索引。

```
删除文档：
  1. PostgreSQL：documents.deleted_at = now()，is_current = FALSE   ← 真相源，此刻生效
  2. 删除 blob，仅在 ref_count 归零时执行
  3. 入队 cleanup 任务，删除 Qdrant 三个集合里对应的点
  4. 30 天后由 cleanup 物理清理文档行和 chunk 行
```

允许 Qdrant 短暂不一致，检索时会用 PostgreSQL 的 `is_current` 做二次过滤。绝不允许“PostgreSQL 有而 Qdrant 没有”，那才是真正的数据丢失。

索引对账任务在 worker 空闲时定期运行（`common/consistency.py`），只报告，不自动修。另外还有两个入口：`GET /admin/consistency` 按需查询，`deploy/monitor.py` 由人执行。

对账按通道分别报告：

| 报告项 | 含义 | 该怎么处理 |
|---|---|---|
| `legs.*.missing` | PostgreSQL 有，这条通道没有 | 漏索引。文本通道可以用 `KIND_REINDEX` 修；视觉通道要重新解析 |
| `legs.*.dangling` | 这条通道有，PostgreSQL 没有 | 残留点。reindex 修不了，要重跑摄取或软删 |

顶层的汇总口径会掩盖“只有一条通道坏了”的情况，所以不要只看顶层。

## 5. 迁移与真实数据

迁移原则是保留原始数据源，向量全部重建。原始文件放在 `data/` 下，可以重新跑：

- `data/chat_messages_clean.jsonl` 导入“聊天记录”知识库（`source_kind=chat`）；
- `data/docs_light/*.md` 导入“我的文档”知识库，需要重跑隐私判定；
- `photos_original/*.jpg` 导入“我的照片”知识库。

隐私复检是必须的。迁移时要重跑 `owner_classifier`，不能信任旧结果，因为判定规则在后续修复中改动过多次。

`data/` 不进 git，已跟踪的文件里不允许出现真实信息。守卫在 `tests/test_no_real_data.py`：真实数据只能从不被追踪的文件读取，例如 `eval/_qset.py`、`eval/_local_data.py`、本地 denylist 和 `reports/`。
