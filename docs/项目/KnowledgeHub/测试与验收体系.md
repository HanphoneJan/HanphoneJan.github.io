# 测试与验收体系

项目的验收分成五层，层与层之间不能互相替代。CI 只运行不需要基础设施和模型的那部分，全量基线留在本机。

## 1. 分层总览

```
+-----------------------------------------------------------------+
|  第 5 层  恢复演练   deploy/restore.sh                             |
|  业务视角：备份真的能恢复吗                                        |
+-----------------------------------------------------------------+
|  第 4 层  巡检       deploy/monitor.py（十四项，跳过不算健康）        |
|  运维视角：这个部署现在健康吗                                      |
+-----------------------------------------------------------------+
|  第 3 层  验收脚本   eval/（契约 81/82、1b 138、1c 218、1d 199）    |
|  真实链路视角：接口与端到端行为对不对                               |
+-----------------------------------------------------------------+
|  第 2 层  前端       vitest 316、typecheck、build                  |
|  前端纯逻辑与构建                                                  |
+-----------------------------------------------------------------+
|  第 1 层  pytest 1335 与 CI 门禁 deploy/ci.sh                      |
|  代码质量视角：单元测试、集成测试与结构守卫                          |
+-----------------------------------------------------------------+
```

| 层 | 跑什么 | 需要什么 | 谁跑 |
|---|---|---|---|
| 1 | `uv run pytest`（1335 项） | PostgreSQL、Qdrant、本地模型 | 本机 |
| 1 | `bash deploy/ci.sh` | 什么都不需要 | CI 和本机 |
| 2 | `npm test`、`typecheck`、`build` | Node | 本机和 CI |
| 3 | `eval/*.py` 加 `contract_check.py` | 真库、模型、正在运行的服务 | 本机 |
| 4 | `deploy/monitor.py` | 真库和真服务 | 本机或 cron |
| 5 | `deploy/restore.sh --scratch` | 一份备份 | 本机，建议每月一次 |

## 2. 第 1 层：pytest 与 CI 门禁

### 2.1 全量 pytest

```bash
uv run pytest                  # 1335 项
```

全量测试需要真实的 PostgreSQL（带 pgvector）、Qdrant 和本地缓存的模型。文本模型 `bge-small` 约 100 MB，视觉模型 colSmol 约 2.65 GB。

模型必须离线加载，这是一条硬约束：`tests/conftest.py` 和 `eval/*` 都通过 `setdefault` 设置了 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`。如果不设置，每次加载模型都会联网重试 5 次，约 23 秒，整套 pytest 会从 50 秒涨到约 28 分钟。

三个 eval 脚本都会清数据（通过 `eval/_reset.py`），必须串行运行，不能并发。

### 2.2 CI 门禁

```bash
bash deploy/ci.sh            # 全部
bash deploy/ci.sh web        # 只跑前端
bash deploy/ci.sh py         # 只跑后端不需要基础设施的部分
```

CI 只运行不需要数据库、模型和运行中服务的部分：

- 前端 `typecheck`、`vitest` 和 `build`；
- 契约覆盖率 `eval/contract_check.py`；
- 443 项免基础设施单测，由 `PURE_TESTS` 白名单指定，约 30 个文件。

为什么不把全量测试塞进 CI：模型要么进 CI 缓存，要么每次下载几百 MB，而离线加载是硬约束；视觉通道在 CI 里必然被标记 `skipped`，于是“跑过了”反而是假绿灯。

判定一个测试是否真的“免基础设施”，要验证三个维度，前两个各踩过一次：

1. 数据库不可达：把 `DATABASE_URL` 指向不存在的库，测试仍然全部通过；
2. 服务不可达：确认该文件不会发送真实 HTTP 请求。本机恰好运行着 API 时，这种写法会变红，并连累同模块的纯单测；
3. locale：CI 使用 `LANG=C`，本机通常是 `zh_CN`。任何 `localeCompare` 或 `toLocaleString` 的排序和格式断言，都可能只在本机通过。验证方法是 `LANG=C LC_ALL=C npm test`。

`ci.sh` 与本地运行的是同一份命令，workflow 只是调用它。修改“哪些测试进 CI”时，先在本地按上面的三个维度验证一遍。

## 3. 第 2 层：前端

```bash
cd web && npm run typecheck && npm test && npm run build
```

- `vitest` 共 316 项，覆盖核心纯逻辑（`src/lib/*` 各自带单测）、主题首绘守卫、切分策略和 locale 守卫；
- `typecheck` 和 `build` 必须通过；
- 接口对齐由 `src/types/api.ts` 与契约保持一致，后端用 `eval/contract_check.py` 守路径、方法和参数面；
- 逐页浅色和深色目测使用 `web/scripts/screenshot.mjs`，`web/scripts/smoke.mjs` 用来检查是否有 console error 和 4xx/5xx。这些是开发工具，不是 e2e 契约，不要往 smoke 里加选择器断言。

## 4. 第 3 层：eval 验收脚本

| 脚本 | 项数 | 覆盖范围 |
|---|---|---|
| `eval/contract_check.py` | 81/82 | 端点路径、方法和参数面 |
| `eval/api_1b_check.py` | 138 | 认证、权限、邀请码、PII 掩码、回收站、统计、限流、对外加固 |
| `eval/api_1c_check.py` | 218 | 摄取全链路、预览、时间线、导入、坐标 |
| `eval/api_1d_check.py` | 199 | 检索、问答 SSE、MCP、A2A、审计、运维审计 |

```bash
uv run python eval/contract_check.py
uv run python eval/api_1b_check.py   # 串行
uv run python eval/api_1c_check.py   # 串行
uv run python eval/api_1d_check.py   # 串行
```

三个脚本都通过 `eval/_reset.py` 清场，必须串行执行。项数可以用 `grep -cP '^\x1b\[32m✓'` 复核。`_fixtures.py` 负责造数据，照片 keeper 库就是靠它。

真实数据不能进仓库。`_qset.py`（问题集）、`_local_data.py`（探针 PDF、问题和标记）和 `reports/` 都只留在本地，仓库里只有 `*.example.py` 模板。守卫 `tests/test_no_real_data.py` 会按本地 denylist 扫描已跟踪文件。

### 4.1 检索质量回放

`eval/retrieval_eval.py` 和 `retrieval_metrics.py` 是修改检索时的核心工具。它第一次运行就抓到了“hybrid 静默降级成 dense 单通道”的问题，原因是三条数据库通道共用一个 `AsyncSession` 并发执行。路由 `date` 权重的方向性错误也是它发现的。

后续修改检索要先跑回放，不能只看“调用返回 200”。

## 5. 第 4 层：巡检

```bash
uv run python deploy/monitor.py          # 十四项，给人看
uv run python deploy/monitor.py --json   # 机器可读
uv run python deploy/monitor.py --quiet  # 只输出问题
uv run python deploy/monitor.py --only df index
```

退出码 0 表示一切正常，1 表示有问题，跳过也算有问题。详细检查项见[部署与运维](./部署与运维.md)。

## 6. 第 5 层：备份与恢复演练

```bash
bash deploy/backup.sh                              # 备份，含自检
bash deploy/backup.sh --list                       # 列出已有备份，含自检结果
bash deploy/backup.sh --verify DIR                 # 只校验
bash deploy/restore.sh --scratch data/backups/<ts> # 演练，推荐每月一次
```

演练会依次执行：校验备份完整性、创建临时库并执行 `pg_restore`、逐表核对行数、逐个校验 blob 的 sha256、删除临时库，最后提示“重建索引后按 `qdrant_expect` 对账”。

已经实测过一次：18 张表的行数全部正确，126 个 blob 的 sha256 全部正确，临时库自动删除。

> 没有恢复过的备份只是一堆文件。

## 7. 结构守卫

| 守卫 | 固定住什么 |
|---|---|
| `test_retrieval_filters.py` | 租户过滤只有统一入口；检索实现只有一份；运行时只有一棵依赖树 |
| `test_permissions.py` | 三档可见性写成三个独立分支，SQL 里不出现 `visibility IN` |
| `test_container_trash.py` | 回收站使用写判据，用真值表逐格比对 |
| `test_audit_coverage.py` | 新增检索端点必须接上审计 |
| `test_unawaited_coroutines.py` | 调用了协程函数却没有 await |
| `test_visual_service.py` | 视觉服务不得访问 Qdrant 或鉴权模块 |
| `test_strategies.py` | 切分策略注册表与对外 schema 的枚举相等 |
| `test_index_models.py` | 嵌入模型一致性 |
| `test_no_real_data.py` | 已跟踪文件里没有真实数据 |
| `test_docs_pointers.py` | 入口文档的路径、命令、端口和基线数字对得上 |
| `test_contract_parser.py` | 固定住契约解析器本身 |

### 7.1 写这类断言的纪律

- AST 类断言必须做变异验证。故意改坏一处，确认测试真的会变红，并单独判断 pytest 的 `exit 5`，它表示没有收集到测试，不是通过。
- 判据要指向性质，而不是中间状态。如果判了某个中间状态或某行实现的字面量，改实现就会误报。
- 抽了 helper 必须接线。不接线的 helper 等于没有。
- “仍然全部通过”要分清是判据太弱、变异无效，还是 `-k` 指错了目标。

## 8. 基线数字怎么复核

```bash
uv run pytest                                  # 1335
uv run python eval/contract_check.py           # 81/82
uv run python eval/api_1b_check.py             # 138
uv run python eval/api_1c_check.py             # 218
uv run python eval/api_1d_check.py             # 199
cd web && npm test                             # 316
uv run python deploy/monitor.py                # 十四项
uv run alembic check                           # 应输出 No new upgrade operations
```

数字只能来自实际运行。改完任何一块都要重跑全量。改后端代码后先执行 `bash deploy/dev.sh restart`，原因见[任务队列与进程模型](./任务队列与进程模型.md)的“改代码之后先杀掉旧进程”一节。
