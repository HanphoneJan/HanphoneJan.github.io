# 评测体系总览

---

## 整体分层

```
+-----------------------------------------------------------------+
|  第5层: 上线验收  (acceptance/)                                    |
|  业务视角，决定能不能发布                                            |
+-----------------------------------------------------------------+
|  第4层: Agent 效果评测  (Langfuse + Golden Cases)                  |
|  AI 质量视角，评估 Agent 回答好不好                                  |
+-----------------------------------------------------------------+
|  第3层: E2E + Live Regression + [Locust 负载测试] + E2E 性能断言       |
|  真实链路视角，前端 + 后端全链路                                     |
+-----------------------------------------------------------------+
|  第2层: Benchmark  (benchmark/)                                    |
|  性能/能力基准，QueryAgent / Text2SQL 准确率 / Bundle / Lighthouse  |
+-----------------------------------------------------------------+
|  第1层: CI 质量门禁  (lint + 路由契约测试 + build + bundle-size-check)        |
|  代码质量视角，每次 push 自动跑                                      |
+-----------------------------------------------------------------+
```

各层之间互不替代：CI 通过不代表前端性能好，前端性能好不代表 Agent 效果好，Agent 效果好不代表业务可发布。每一层有独立的触发条件和判定标准。前端性能评测有独立方案，本文不展开。

## 第1层: CI 质量门禁

**触发方式**：GitHub push / PR 到 master 分支，自动执行
**配置文件**：`.github/workflows/ci.yml`

### 1.1 后端 Lint

| 项目 | 说明 |
|------|------|
| 位置 | `ruff check app worker --select=F,I,UP,W` |
| 工具 | ruff >= 0.15.0 |
| 触发 | GitHub push/PR 自动 |
| 失败处理 | 阻止合并 |

### 1.2 后端路由契约测试

| 项目 | 说明 |
|------|------|
| 位置 | `tests/unit/api/` |
| 工具 | FastAPI TestClient + pytest |
| 覆盖 | 422/404/405/CORS 通用契约（中间件层） |
| 配置 | `asyncio_mode = "auto"`，忽略 `tests/manual/` 和 `tests/benchmark/` |
| 触发 | GitHub push/PR 自动 |
| 设计 | 通过 `app.dependency_overrides` 绕过 JWT 中间件，仅验证 HTTP 中间件行为，不连接真实 DB。共 15 条用例，进程内运行，不需要外部服务。 |

> 中间件契约测试是 CI 中唯一的后端测试。端点 401/422 验证和 seed 数据回归由 `tests/api/` 黑盒测试（需要 server）承担。Agent 评测层（Langfuse + Golden Cases）独立验证 AI 回答质量。

### 1.3 前端 Lint

| 项目 | 说明 |
|------|------|
| 位置 | `web/` |
| 工具 | ESLint + eslint-plugin-playwright |
| 触发 | GitHub push/PR 自动 |

### 1.4 前端构建

| 项目 | 说明 |
|------|------|
| 位置 | `web/` |
| 命令 | `pnpm run build` (Vite) + `pnpm run size-check` (Bundle 体积预算) |
| 触发 | GitHub push/PR 自动 |

> Lighthouse CI 不在 CI 中运行（SPA static 预渲染为空白页），本地通过 `pnpm run lhci` 手动执行。

---

### 1.5 API 黑盒测试（`tests/api/`）

| 项目 | 说明 |
|------|------|
| 位置 | `tests/api/` |
| 工具 | pytest + httpx（复用 `tests/utils/api_client.py`） |
| 覆盖 | 全部 15 个模块 155 个端点，按 domain 分子目录（auth/dashboard/analysis/chat/config/infra） |
| 触发 | 手动执行，需要 `uv run server` |
| 设计 | Session 级 token 磁盘缓存，只登录一次。每条端点正确输入->200+seed数据断言 + 错误输入->401/422。 |

> API 黑盒测试定位在第3层（真实链路），替代原集成测试。当前 173 条用例（22 个文件），按 domain 分子目录。新增端点时在 `tests/api/{domain}/` 对应文件中添加 test method 即可。CI 暂不自动执行。

## 第2层: Benchmark

Benchmark 是离线执行的性能/能力基准测试，不阻塞 CI，按需手动运行。

### 2.1 QueryAgent Benchmark（主项目）

#### 文件结构

```
tests/benchmark/
  run_query_agent_benchmark.py   # 主执行脚本
  run_full_benchmark.py          # 统一入口（API + DuSQL）
  query_agent_benchmark_cases.yaml  # 17 条测试用例
  test_benchmark_utils.py        # 工具函数单元测试
```

#### 用例覆盖

17 条 benchmark case，覆盖 5 个类别：
- `login_detail` - 登录明细查询
- `order_detail` - 订单明细查询
- `sql` - SQL 生成与执行
- `table_query` - 表查询
- `cross_project` - 跨项目查询

#### 执行命令

```powershell
cd server

# 仅跑 QueryAgent benchmark
uv run python tests/benchmark/run_query_agent_benchmark.py

# 跑完整 benchmark（API + DuSQL）
uv run python tests/benchmark/run_full_benchmark.py
```

#### 设计特点

- 对 `/api/v1/agent/query` 发送真实 HTTP 请求
- 有失败用例时 exit code 为非 0（可用于 CI 决策）
- 通过 pyproject.toml 从默认 pytest 收集中排除

### 2.2 BI 平台 Benchmark（Java 项目，独立体系）

#### 文件结构

```
bi-platform/benchmark/
  benchmark.py                   # 主执行脚本
  benchmark.md                   # 文档
  requirements.txt               # pandas, PyJWT, requests
  data/
    caiwu.csv                    # 财务类测试数据
    renli.csv                    # 人力类测试数据
```

#### 用途

对运行中的服务进行批量 Q&A 测试，使用 CSV 文件中的真实用户问题。

#### 执行命令

```bash
python benchmark.py -u <url> -a <agentId> -c <chatId> -f <filePath> -p <userName>
```

### 2.3 BI 平台 Evaluation（Text2SQL 准确率，独立体系）

#### 文件结构

```
bi-platform/evaluation/

  evaluation.sh                  # 一键执行脚本
```

跨模型 Text2SQL 准确率对比评测。将模型生成的 SQL 与 gold standard SQL 进行对比，输出准确率。

```bash

```

- 控制台输出准确率
- `error_case.json` - 错误案例明细

### Benchmark 层总结

| 评测 | 项目归属 | 测什么 | 何时跑 |

#### 关键设计模式

**API 登录注入** - 通过 `addInitScript` 将 token 写入 localStorage，跳过 UI 登录，加速测试执行：

```typescript
await page.addInitScript(
  ({ storedToken, storedUser }) => {
    window.localStorage.setItem('token', storedToken)
    window.localStorage.setItem('user', JSON.stringify(storedUser))
    window.localStorage.setItem('remember_me', '1')
  },
  { storedToken: token, storedUser: user },
)
```

**QualityProbe 质量探针** - 监听浏览器运行时事件，测试结束时统一断言：

```typescript
function installQualityProbe(page: Page) {
  const issues: string[] = []
  page.on('pageerror', (error) => { issues.push(`pageerror: ${error.message}`) })
  page.on('console', (msg) => { /* 过滤已知无害错误，其余记录 */ })
  page.on('requestfailed', (request) => { /* 记录非 abort 的失败请求 */ })
  page.on('response', (response) => { /* 记录 API 4xx/5xx */ })
  return {
    waitForApiIdle(timeoutMs) { /* 等待全部 API 完成 */ },
    assertClean(label) { expect(issues).toEqual([]) },
  }
}
```

**资源清理** - 所有种子数据测试使用 `try/finally` + `deleteResource()` 确保不污染数据库。

**重试机制** - 登录和认证操作内置 2-3 次重试，应对后端冷启动。

#### 三条执行 Lane

| Lane | 前置条件 | 说明 |
|------|----------|------|
| `http_api` | 后端 API 运行，`LIVE_API_*` 可登录 | 默认 lane，覆盖 HTTP 可执行的 supervisor/query/analyst/report/watcher HTTP/tool HTTP 样例 |
| `watcher_worker` | 后端 API + Worker 依赖可导入，账号有告警规则创建/删除权限 | Runner 通过 API 创建临时规则，调用 `watcher_check_single_rule` 或 `watcher_check_alerts` |
| `mcp_protocol` | MCP optional 依赖已安装，SSE 需要 `uv run mcp-sse` 运行中，至少一种有效认证 | stdio `tools/list`、stdio `tools/call`、SSE `/auth`、SSE `call_tool` |

#### 程序化分数（7 个确定性分数）

| 分数名 | 取值 | 判定逻辑 |
|--------|------|----------|
| `http_success` | 1/0 | HTTP 状态码 200-299 |
| `tool_success` | 1/0 | 无异常标记（Traceback, Internal Server Error 等） |
| `answer_contract` | 1/0 | must_include 全部包含 且 must_not_include 全部不包含 |
| `answer_contract_qem` | 1/0 | 准精确匹配（数字等价、列表等价、字符串语义等价） |
| `query_mode_match` | 1/0 | 返回的 query_mode 与 expected 一致 |
| `tool_call_ast_match` | 1/0 | 实际 tool.call span 与 expected tool_call 匹配 |
| `context_propagation` | 1/0 | 上下文（session_id / project_id）是否正确传播 |

#### LLM Evaluator 语义分数（9 个，0-10 分）

| 分数名 | 评估内容 | 注册方式 |
|--------|----------|----------|
| `query_capability` | 查询路径、工具选择、指标/时间/维度正确性、SQL 与项目范围安全 | Langfuse UI 手动注册 |
| `answer_correctness` | 回答是否正确、完整、符合 expected_output | Langfuse UI 手动注册 |
| `report_quality` | 报告结构、数据扎根、结论建议、缺数降级与安全输出质量 | Langfuse UI 手动注册 |
| `dashboard_quality` | 看板/自定义报表资源理解、组件设计、布局/筛选、权限与清理策略 | Langfuse UI 手动注册 |
| `tool_choice_quality` | 是否正确选择了 Agent、工具、查询模式或 MCP lane | Langfuse UI 手动注册 |
| `helpfulness` | 回答是否清晰、有帮助，并说明限制或下一步 | 计划中 |
| `instruction_following` | 是否遵循用户任务、硬门槛语义和输出约束 | 计划中 |
| `groundedness` | 最终回答是否扎根于工具/数据结果，是否避免编造 | 计划中 |
| `project_scope_safety` | 是否尊重项目范围、权限边界和 SQL 安全信号 | Langfuse UI 手动注册 |

> Langfuse 公开 API (`/api/public/evaluators`) 当前返回 404，因此 LLM Evaluator 通过 Langfuse UI 手动注册，不能通过 API 程序化创建。

### 4.4 Baseline / Current 对比工作流

```
1. 确认工作区干净，无无关改动
2. 修改 prompt 前 -> 跑 baseline
   run-name: native-agent-regression-baseline-<git_sha>
3. 修改 prompt（如 app/modules/agent/prompts/layers/_base.md）
4. 重启后端服务
5. 修改 prompt 后 -> 跑 current
   run-name: native-agent-regression-current-<git_sha>
   --baseline-run-name native-agent-regression-baseline-<git_sha>
6. 在 Langfuse UI Dataset Run 页面按 run name 打开两次结果对比
   - 优先关注低分 item
   - 对比确定性 score 和 LLM Evaluator 语义 score
```

### 4.5 低分复盘指南

#### 复盘优先级

优先复盘以下低分样本：
- `answer_contract=0`
- `tool_success=0`
- `http_success=0`
- `query_mode_match=0`
- `answer_correctness < 7`
- `query_capability < 7`
- `report_quality < 7`
- `dashboard_quality < 7`
- `tool_choice_quality < 7`
- `project_scope_safety < 9`

#### answer_contract=0 的处理

| 类型 | 判断方式 | 处理 |
|------|----------|------|
| 评估器误判 | HTTP/tool 成功，实际回答满足期望，但 `_response_text()` 没抽到正文 | 补单测并修正评估器或 expected，不改 Agent |
| 黄金集期望不合理 | 用户问题合理，但 `must_include/must_not_include` 太窄 | 调整黄金集 expected |
| 真实能力缺口 | 回答选择错误指标/工具/项目或缺少关键语义 | 进入 Agent 能力修复队列 |

#### 工具选择低分的处理

| 低分原因 | 判断方式 | 处理 |
|----------|----------|------|
| 工具说明边界不清 | `tool_choice_quality < 7`，相邻工具混淆 | 收紧工具说明和 Supervisor 路由表 |
| 参数缺失 | 工具正确但请求体缺项目、时间或指标 | 给工具 schema/prompt 补 required 参数说明 |
| 越权绕路 | `project_scope_safety < 9` | 修业务硬门槛，不用 prompt 兜底 |
| 不支持指标硬答 | `query_capability < 7` 且输出编造 | 加 `unsupported_metric` 反馈与受控拒答 |

### 4.6 运行时 Langfuse 观测（与评测独立）

评测体系之外，Agent 运行时还有一套 Langfuse **观测埋点**，遵循"只观测不拦截"原则--观测失败不影响业务。

#### 组件结构

| 组件 | 文件 | 作用 |
|------|------|------|
| 配置桥接 | `app/modules/agent/runtime/langfuse_config.py` | 将 Settings 同步到 SDK 环境变量 |
| Trace 写入 | `app/modules/agent/runtime/trace_writer.py` | `update_trace()`, `span()`, `score_current_trace()` |
| 字段定义 | `app/modules/agent/runtime/trace_schema.py` | 标准 trace/span/score 命名、脱敏规则 |

#### 标准 Trace 名称

`agent.chat`, `agent.chat.stream`, `agent.query`, `agent.analyze`, `agent.report.generate`, `agent.watcher.detect_all`, `agent.watcher.detect_rule`, `mcp.delegate_supervisor`, `mcp.call_tool`

#### 核心 Span 名称

`supervisor.llm_round`, `tool.call`, `permission.check`, `query.generate_sql`, `query.validate_sql`, `query.execute_sql`, `analyst.compute_attribution`, `report.plan`, `watcher.detect_rule`, `watcher.llm_confirm`

#### 运行时程序化 Score（硬门槛）

| Score | 含义 |
|-------|------|
| `permission_safety_pass` | 权限检查是否通过 |
| `sql_safety_pass` | NL2SQL/SQL 校验是否通过 |
| `data_scope_pass` | 项目范围、指标映射或数据 scope 是否可用 |
| `tool_success` | Tool 调用是否成功 |
| `trace_schema_pass` | Trace schema 完整性检查 |

#### 脱敏策略

- 敏感字段（api_key, secret, authorization, password, token, jwt）写入 `[REDACTED]`
- SQL 只记录脱敏摘要（operation, tables, limit, redacted_sql），不记录原始 SQL
- 报告 HTML 只记录长度、标题、状态，不记录正文
- metadata 统一包含 `environment`, `request_id`, `session_id`, `user_id`, `project_id`, `agent_type`, `entrypoint`, `intent`

| B | 集成合同 | 后端 API 黑盒测试、数据库/Worker 合同测试 | 后端/MCP/Worker P0/P1 required gate 至少达到 |
| C | 源码或文档合同 | 源码合同测试、单元测试、日志/文档证据 | 非前端 P2 required gate 至少达到 |
| D | 弱证据 | 人工说明、无有效证据、失败证据 | 不满足发布条件 |

### 5.5 发布条件

`release_gate.can_release = true` 必须同时满足：
- 所有 P0/P1/P2 required 场景均为 `passed`
- 所有 required 场景均有有效证据
- 所有 required 场景满足对应证据等级要求
- 不存在 open/blocker/high 级别未关闭缺陷
- P2 未通过项已进入延期或风险清单

### 5.6 常用命令

```powershell
cd server
```

### 5.7 首轮验收推荐顺序

1. `backend-runtime` - 健康检查、API 聚合、错误语义
2. `auth-session` + `permission` - 登录、会话、权限边界
3. `frontend-runtime` - 核心路由无白屏、无 Vue runtime 异常
4. `dashboard` + `dashboards` + `query` - 核心分析入口
5. `data-reports` + `event-analysis` + `user-segments` + `project-spaces` - 扩展分析与协作
6. `chat` + `report` + `workers` - AI、报告与后台任务
7. `mcp` - 外部集成入口
8. `data-consistency` + `observability` - 跨模块口径和证据归档
