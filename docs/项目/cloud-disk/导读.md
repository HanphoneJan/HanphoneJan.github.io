# 导读

这一栏是一套「S3 兼容对象存储服务」的设计文档。项目是 Java 21 + Spring Cloud Alibaba 的微服务：`gateway` 统一入口，`object-storage` 管对象字节，`object-metadata` 管 MySQL 里的索引，`admin-ui` 是 React 管理台；对象与索引之间用 Outbox + RabbitMQ 做最终一致。

规模：89 个 Java 文件，3 个业务服务，18 个 compose service（16 常驻 + 2 一次性），57 个 `@Test`，9 个 JMeter 场景。它能做的事与做不到的事都写在代码里，文档按代码写，与 README 冲突处以代码为准。

## 几条先知道的结论

- 下载默认返回 302，不是网关转发字节；本地与 OSS 后端不支持预签名时自动回退代理。
- 上传接口返回时，对象列表里不一定已经有这个对象；索引是异步补的。
- 回收站恢复只恢复 `object_info` 的状态，删除时字节已经被移除。
- 任何登录用户知道 Bucket 名就能读写；对象级授权没有实现。
- 业务服务没有 Actuator，健康检查只能看容器状态与登录接口。
- 分片状态只在 Redis，`multipart_upload` 表建了但没读写。

这些结论在对应篇目里有代码位置与边界条件；要改的话，[已知边界](./已知边界.md) 的最后一节按代价排了顺序。

项目仓库里已有 `docs/architecture.md`、`deployment.md`、`development.md`、`interview-prep.md`、`nacos-config.md`。这一栏没有搬运它们的章节，只把事实重新按代码核对了一遍；与代码冲突的地方以代码为准，冲突清单收在[已知边界](./已知边界.md)。

性能数字只有尖峰那一组能在提交的 JTL 里复算；其余场景的 JTL 是修复前的失败运行，不能当读数，[基准测试与性能](./基准测试与性能.md)里写明了原因。
