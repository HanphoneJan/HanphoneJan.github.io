这份笔记是为了「能和运营同事对话」写的：把 DAU、留存、LTV 这些词翻译成开发者熟悉的口径（事件、状态机、漏斗、归因），再讲清楚它们背后的数据是怎么采、怎么算的。

## 一、游戏运营是干什么的？

### 类比理解

```
传统软件开发:
  开发 → 上线 → 维护 → 偶尔更新

游戏运营:
  开发 → 上线 → 【持续运营】→ 不断迭代
                    ↑
               核心差异在这里
```

**游戏是"活的产品"**，上线只是开始。运营团队的工作就像是一个 24/7 运行的监控系统：

- **拉新**：获取新用户（类似市场推广）
- **留存**：让用户持续玩下去（类似产品优化）
- **付费**：让用户愿意花钱（类似商业变现）

### 运营的核心问题

每天运营人员都在问这些问题：

```
1. 今天来了多少人？（用户量）
2. 他们玩了多久？（活跃度）
3. 多少人明天还会来？（留存）
4. 多少人花钱了？花了多少？（付费）
5. 哪个渠道带来的用户最好？（渠道质量）
6. 数据突然下跌了，为什么？（异常归因）
```

**这个平台要解决的就是：自动回答这些问题。**

## 二、账号、角色、设备的区别

在游戏数据分析中，**账号、角色、设备是三个不同的统计口径**，必须区分清楚。

### 三者定义

```
设备 (Device)
├── 定义：物理设备，用 device_id 标识
├── 示例：一部手机 = 一个设备
└── 特点：设备可能被多人使用（如网吧电脑）

账号 (Account)
├── 定义：用户注册的账号，用 game_user_id 标识
├── 示例：玩家用手机号注册的账号
└── 特点：一个人可能有多个账号（大号、小号）

角色 (Role)
├── 定义：游戏内创建的角色，用 role_id 标识
├── 示例：《原神》里创建的"旅行者"
└── 特点：一个账号可能有多个角色（不同服务器）
```

### 层级关系

```
1台设备
  └── 可登录多个账号（换号登录）
        └── 每个账号可创建多个角色（多服务器）

示例：
  手机A (device_id: D001)
    ├── 账号1 (user_id: U001) - 主账号
    │     ├── 角色A (role_id: R001) - 1服
    │     └── 角色B (role_id: R002) - 2服
    └── 账号2 (user_id: U002) - 小号
          └── 角色C (role_id: R003) - 1服
```

### 为什么要区分？

**不同统计口径，结果差异很大：**

```
场景：统计今日付费情况

按设备统计：1台设备付费了 → 付费设备数 = 1
按账号统计：2个账号付费了 → 付费账号数 = 2
按角色统计：3个角色付费了 → 付费角色数 = 3

如果不区分口径，数据会对不上！
```

### 账号设备比

```
定义：账号数 / 设备数

正常值：1.0 - 1.2
  - 大部分用户一台设备一个账号

异常值：> 1.5
  - 可能存在刷号行为（工作室）
  - 可能有大量小号

技术实现：
  SELECT
    COUNT(DISTINCT game_user_id) / COUNT(DISTINCT device_id) AS account_device_ratio
  FROM player_login
  WHERE DATE(login_time) = '2026-01-20'
```

## 三、新增用户漏斗（激活→注册→创角）

新用户从下载到真正开始玩，要经过多个步骤，每一步都有流失。

### 漏斗阶段

```
激活设备 → 注册设备 → 创角设备
   ↓           ↓           ↓
  100%       55%         50%
   │           │           │
   │           │           └── 只有一半用户真正开始玩
   │           └── 45%的人安装后没注册
   └── 广告带来的初始流量
```

### 各阶段定义

| 阶段               | 定义                     | 作用                        |
| ------------------ | ------------------------ | --------------------------- |
| **激活设备** | 首次安装并打开游戏的设备 | 衡量广告/渠道带来的初始流量 |
| **注册设备** | 完成账号注册的设备       | 衡量注册流程的转化效果      |
| **创角设备** | 创建游戏角色的设备       | 衡量新手引导的吸引力        |

### 转化率指标

```
设备激活注册率 = 注册设备数 / 激活设备数

正常值：50-60%
低于40%：注册流程有问题
```

```
设备注册创角率 = 创角设备数 / 注册设备数

正常值：85-95%
低于80%：新手引导有问题
```

### 异常诊断

| 现象               | 可能原因                                   |
| ------------------ | ------------------------------------------ |
| 激活注册率低       | 注册流程太繁琐、需要实名认证、登录报错     |
| 注册创角率低       | 下载资源太大、新手引导劝退、服务器选择困难 |
| 某渠道转化率特别低 | 该渠道用户质量差、或存在作弊流量           |

### SQL 示例

```sql
-- 计算某日的新增用户漏斗
SELECT
  COUNT(DISTINCT CASE WHEN event_type = 'activate' THEN device_id END) AS 激活设备,
  COUNT(DISTINCT CASE WHEN event_type = 'register' THEN device_id END) AS 注册设备,
  COUNT(DISTINCT CASE WHEN event_type = 'create_role' THEN device_id END) AS 创角设备
FROM user_events
WHERE DATE(event_time) = '2026-01-20'
```

## 四、核心指标详解

### 4.1 用户量指标

#### DAU - 日活跃用户 (Daily Active Users)

```
定义：当天登录过游戏的用户数（去重）

示例：
  - 用户A 早上登录1次，晚上登录1次 → 算1个DAU
  - 用户B 今天登录3次 → 算1个DAU
  - 今天有1000个不同用户登录 → DAU = 1000

技术实现：
  SELECT COUNT(DISTINCT player_id)
  FROM player_login
  WHERE DATE(login_time) = '2026-01-20'
```

**为什么重要**：DAU 是游戏健康度的"心跳"，DAU 下降通常意味着出问题了。

#### MAU - 月活跃用户 (Monthly Active Users)

```
定义：过去30天内登录过游戏的用户数（去重）

DAU vs MAU 的关系：
  - DAU/MAU 比值叫"粘性"
  - 比值越高，说明用户越愿意每天来玩
  - 典型值：休闲游戏 10-20%，重度游戏 20-40%
```

#### PCU - 最高同时在线 (Peak Concurrent Users)

```
定义：某一时刻同时在线的用户数峰值

示例（某天数据）：
  10:00 → 500人在线
  12:00 → 800人在线
  20:00 → 2000人在线  ← 这就是PCU
  23:00 → 1200人在线

技术实现：服务器每分钟采样在线人数，取最大值
```

**为什么重要**：PCU 决定服务器容量规划，也反映游戏的"热度峰值"。

#### 日活跃付费老账号数

```
定义：当天登录的历史付费用户数

为什么单独统计：
  - 付费用户是高价值用户
  - 付费用户流失损失更大
  - 需要重点监控这群人的活跃情况

示例：
  今天DAU = 10000
  其中历史付费过的用户 = 3000 → 日活跃付费老账号数 = 3000
```

### 4.2 留存指标

#### 什么是留存？

```
留存 = 新用户在第N天还回来玩的比例

举例：
  1月1日：100个新用户注册
  1月2日：其中40人回来了 → 次日留存 = 40%
  1月8日：其中20人回来了 → 7日留存 = 20%
  1月31日：其中10人回来了 → 30日留存 = 10%
```

#### 留存率的计算

```sql
-- 计算2026-01-01注册用户的次日留存
WITH new_users AS (
  SELECT DISTINCT player_id
  FROM player_login
  WHERE DATE(login_time) = '2026-01-01'
    AND is_new = 1  -- 新用户标记
),
day2_users AS (
  SELECT DISTINCT player_id
  FROM player_login
  WHERE DATE(login_time) = '2026-01-02'
)
SELECT
  COUNT(day2_users.player_id) / COUNT(new_users.player_id) AS retention_d1
FROM new_users
LEFT JOIN day2_users ON new_users.player_id = day2_users.player_id
```

#### 留存率的行业标准

```
         次日留存    7日留存    30日留存
优秀      > 50%      > 25%      > 15%
良好      40-50%     15-25%     8-15%
及格      30-40%     10-15%     5-8%
危险      < 30%      < 10%      < 5%

不同类型游戏差异很大：
- 休闲游戏：次日留存 35-45% 就不错
- SLG策略：次日留存可能只有 20%，但长期留存高
```

**为什么重要**：留存是游戏能否长期赚钱的基础。留存差 = 用户来了就走 = 花钱买来的用户浪费了。

#### 留存矩阵

实际工作中，留存数据通常以矩阵形式展示：

```
日期        新增用户    当日    第1日   第3日   第7日   第14日
2025-12-21  6,612      100%    54.8%   38.1%   26.6%   17.3%
2025-12-22  162        100%    62.9%   40.1%   28.4%   14.2%
2025-12-23  502        100%    58.9%   47.4%   34.3%   19.5%
```

**如何解读**：

- 每一行是一批新用户（按注册日期分组）
- 每一列是该批用户在第 N 天的留存率
- 可以对比不同日期新增用户的留存差异

### 4.3 回流用户

#### 什么是回流？

```
回流 ≠ 留存

留存：用户从未流失，一直在玩
回流：用户曾经流失，后来又回来了

示例：
  用户A：1月1日注册，1月2日登录，1月3日登录... → 留存用户
  用户B：1月1日注册，1月2日没来，1月3日回来了 → 1日回流用户
```

#### 回流指标

| 指标              | 定义                          | 作用             |
| ----------------- | ----------------------------- | ---------------- |
| **1日回流** | 昨天没来、今天回来的用户数    | 短期召回效果     |
| **3日回流** | 连续3天没来、今天回来的用户数 | 中期召回效果     |
| **7日回流** | 连续7天没来、今天回来的用户数 | 长期流失用户召回 |

#### 回流的业务价值

```
场景：游戏做了一次召回活动（发短信/推送/邮件）

活动前：7日回流 = 100人/天
活动后：7日回流 = 500人/天

→ 活动效果 = 新增回流 400人
```

### 4.4 付费指标

#### 付费率的多种口径

| 指标                     | 公式                              | 典型值 | 用途         |
| ------------------------ | --------------------------------- | ------ | ------------ |
| **DAU付费率**      | 当日付费人数 / DAU                | 3-8%   | 日常监控     |
| **新增注册付费率** | 当日新增且付费人数 / 当日新增人数 | 1-2%   | 首日转化效果 |
| **新用户付费率**   | 新用户累计付费人数 / 新用户总数   | 5-15%  | 用户质量评估 |

#### ARPU & ARPPU

```
ARPU (Average Revenue Per User)
定义：平均每个用户贡献的收入（包括不付费的）
计算：总收入 / DAU
示例：今天充值30000元，DAU=10000 → ARPU = 3元

ARPPU (Average Revenue Per Paying User)
定义：平均每个付费用户的消费金额
计算：总收入 / 付费用户数
示例：今天充值30000元，付费人数=300 → ARPPU = 100元
```

#### ARPPU 的多种统计口径

```
账号付费ARPPU：按账号去重统计
  - 一个人多个角色付费，算一个账号

角色付费ARPPU：按角色统计
  - 一个人多个角色付费，算多个角色
  - 通常比账号ARPPU高
```

#### 三者的关系

```
ARPU = ARPPU × 付费率

验证：
  ARPU = 100元 × 3% = 3元 ✓

运营策略选择：
  - 提高付费率：让更多人愿意付费（降低付费门槛）
  - 提高ARPPU：让付费用户花更多钱（增加高价值商品）
```

#### 首次付费分析

```
首次付费金额：用户生命周期中第一笔付费的金额
首次付费账号数：当天首次付费的用户数

作用：
  - 衡量付费门槛设计是否合理
  - 首充礼包是否有吸引力
  - 新用户的付费转化效果

示例数据：
  首次付费金额均值 = 6元 → 说明首充6元档最受欢迎
  首次付费账号数 = 241人 → 今天有241人首次付费
```

### 4.5 LTV 时间维度详解

LTV（生命周期价值）是用户从注册到流失贡献的总收入，但实际工作中需要按时间维度拆分。

#### 不同时间点的 LTV

| 指标               | 定义                    | 用途             |
| ------------------ | ----------------------- | ---------------- |
| **1日LTV**   | 用户注册当天贡献的收入  | 衡量首日付费转化 |
| **7日LTV**   | 用户7天内累计贡献的收入 | 短期投放回收判断 |
| **14日LTV**  | 用户14天内累计收入      | 中期价值评估     |
| **30日LTV**  | 用户30天内累计收入      | 月度ROI计算基准  |
| **360日LTV** | 用户一年内累计收入      | 长期用户价值     |

#### LTV 预估方法

```
早期只有 1日LTV 数据时，可以用系数预估长期 LTV：

LTV(n日) ≈ 1日LTV × 系数

典型系数（不同游戏差异大）：
- 7日LTV ≈ 1日LTV × 1.5-2.0
- 30日LTV ≈ 1日LTV × 2.0-3.0
- 360日LTV ≈ 1日LTV × 3.0-5.0

示例：
  某渠道 1日LTV = 2元
  预估 7日LTV = 2 × 1.8 = 3.6元
  预估 30日LTV = 2 × 2.5 = 5元
```

#### LTV 与 ROI 的关系

```
n日ROI = n日LTV / CAC

示例：
  某渠道 CAC = 10元（获取一个用户花10元）
  7日LTV = 8元
  7日ROI = 8 / 10 = 80%（还没回本）

  30日LTV = 12元
  30日ROI = 12 / 10 = 120%（回本了）

→ 该渠道在30天内可以回本
```

#### 回本周期

```
定义：找到 n日ROI ≥ 100% 的最小 n

核心公式：
  n日ROI = n日LTV / CAC
  回本条件：n日LTV ≥ CAC

示例1（健康渠道）：
  CAC = 10元
  1日LTV = 2元  → 1日ROI = 20%
  7日LTV = 6元  → 7日ROI = 60%
  14日LTV = 9元 → 14日ROI = 90%
  30日LTV = 12元 → 30日ROI = 120% ← 第一次超过100%

  → 回本周期 = 30天（健康）
```

#### 回本周期计算模型

**方法一：直接追踪法**

```
持续追踪用户的累计付费，直到 n日LTV ≥ CAC

优点：最准确
缺点：需要等待很长时间才能得到结果
```

**方法二：LTV系数推算法**

```
当只有短期数据时，用 LTV 系数预估回本周期：

已知：1日LTV、CAC、LTV系数
求解：回本周期

计算步骤：
1. 求回本需要的 LTV 系数：目标系数 = CAC / 1日LTV
2. 根据系数对应表推算天数

LTV 系数参考（中重度游戏）：
  7日 ≈ 1.5-2.0 倍
  30日 ≈ 2.0-3.0 倍
  90日 ≈ 2.5-4.0 倍
  180日 ≈ 3.0-4.5 倍
  360日 ≈ 3.5-5.0 倍

示例：
  CAC = 15元，1日LTV = 3元
  目标系数 = 15 / 3 = 5.0（需要5倍才能回本）

  查系数表：5.0 倍对应约 360天 或更长
  → 回本周期 ≈ 300-400天（偏长，需要评估渠道质量）
```

**方法三：线性外推法（粗略估计）**

```
假设 LTV 增长近似线性（实际是递减的）：

回本天数 ≈ CAC / 日均 LTV 增量

示例：
  CAC = 15元，1日LTV = 3元
  假设 7日LTV = 5元
  日均增量 = (5-3) / 6 = 0.33元/天

  剩余需要：15 - 3 = 12元
  估算天数：12 / 0.33 ≈ 36天

  但实际 LTV 增长会递减，所以真实回本周期更长
```

#### 回本周期的判断标准

```
游戏类型不同，可接受的回本周期差异很大：

| 游戏类型 | 健康回本周期 | 可接受上限 | 警戒线 |
|---------|-------------|-----------|--------|
| 休闲游戏 | 7-14天 | 30天 | 60天 |
| 中度游戏 | 30-60天 | 90天 | 180天 |
| 重度游戏 | 60-120天 | 180天 | 365天 |
| SLG/MMO | 90-180天 | 365天 | 540天 |

判断渠道质量：
  回本周期 < 健康值 → 优质渠道，可加大投放
  回本周期 < 可接受值 → 正常渠道，维持投放
  回本周期 > 警戒线 → 问题渠道，考虑停投
```

#### 回本周期过长的诊断

```
如果某渠道回本周期过长，可能原因：

1. CAC 过高
   - 竞价太激烈
   - 素材吸引了低质量用户
   → 优化素材，调整出价

2. LTV 过低
   - 用户付费意愿弱
   - 用户流失太快
   → 分析该渠道用户画像

3. 渠道属性问题
   - 某些渠道天然用户质量低
   - 买量成本与用户价值不匹配
   → 考虑停止该渠道投放
```

### 4.6 渠道与投放指标

#### 什么是渠道？

```
渠道 = 用户从哪里来的

常见渠道类型：
  - 应用商店：App Store、Google Play、华为应用市场等
  - 广告平台：抖音、Facebook、Google Ads 等
  - 小程序：微信小程序(微小)、抖音小程序(抖小) 等
  - 自然流量：用户自己搜索下载
  - 社交分享：朋友推荐

技术实现：
  用户安装时带上渠道标识（channel_id），全生命周期追踪
```

#### CAC - 用户获取成本

```
定义：获取一个新用户花的钱
计算：广告花费 / 新增用户数

示例：
  在抖音投了10000元广告
  带来了500个新用户
  CAC = 10000 / 500 = 20元/人
```

#### ROI - 投资回报率

```
定义：投入的钱赚回来多少
计算：收入 / 成本

示例：
  某渠道投入10000元，用户充值了15000元
  ROI = 15000 / 10000 = 150%（赚了）

判断标准：
  ROI > 100% → 赚钱
  ROI < 100% → 亏钱
```

#### 渠道质量评估

```
不同渠道的用户质量差异很大：

渠道A（便宜渠道）：
  - CAC = 5元
  - 次日留存 = 20%
  - 7日ROI = 50%

渠道B（优质渠道）：
  - CAC = 30元
  - 次日留存 = 45%
  - 7日ROI = 120%

表面看A便宜，实际B更值得投！

这就是为什么需要按渠道维度分析数据。
```

## 五、支付渠道与退款

### 支付渠道 (charge_channel)

```
定义：用户使用的支付方式

常见支付渠道：
  - 101：微信支付
  - 105：支付宝
  - 108：Apple Pay
  - 110：Google Pay
  - ...

为什么要区分：
  - 不同渠道手续费率不同（Apple 抽成30%）
  - 支付故障需要定位到具体渠道
  - 用户付费习惯分析
```

### 支付来源 (sub_channel_id)

```
定义：更细粒度的支付来源

示例（微信支付下的细分）：
  - 微信小程序支付
  - 微信H5支付
  - 微信APP支付

作用：
  - 定位支付问题更精准
  - 分析不同入口的付费转化
```

### 支付监控指标

| 指标                   | 定义                    | 作用         |
| ---------------------- | ----------------------- | ------------ |
| **充值账号数**   | 进行充值的唯一账号数    | 付费用户规模 |
| **充值次数**     | 充值交易笔数            | 付费频次     |
| **总充值金额**   | 所有充值的总金额        | 营收规模     |
| **ARPPU**        | 总充值金额 / 充值账号数 | 人均消费     |
| **付费金额占比** | 该渠道金额 / 总金额     | 渠道重要性   |

### 退款监控

| 指标                 | 定义                        | 警戒值      |
| -------------------- | --------------------------- | ----------- |
| **退款订单数** | 发起退款的订单数量          | -           |
| **退款金额**   | 退款总金额                  | -           |
| **退款率**     | 退款订单数 / 支付成功订单数 | > 1% 需关注 |

#### 退款率高的常见原因

```
1. 支付BUG
   - 重复扣款
   - 支付成功但未发货

2. 用户投诉
   - 外挂检测后封号
   - 对游戏不满要求退款

3. 平台政策
   - Apple/Google 无条件退款政策
   - 用户利用政策薅羊毛

4. 恶意退款
   - 黑产工作室
   - 利用退款漏洞
```

## 八、实时监控的时间粒度

### 不同时间粒度的用途

| 粒度                        | 指标示例                           | 用途                   |
| --------------------------- | ---------------------------------- | ---------------------- |
| **byminute (按分钟)** | 注册创角byminute、付费金额byminute | 实时监控异常，发现问题 |
| **byhour (按小时)**   | 活跃byhour、付费人数byhour         | 日内趋势分析，峰值定位 |
| **按天**              | DAU、日充值                        | 日常运营报告           |
| **按周/月**           | WAU、MAU、月流水                   | 长期趋势分析           |

### 环比与同比

| 指标               | 定义             | 用途                             |
| ------------------ | ---------------- | -------------------------------- |
| **小时环比** | 与上一小时对比   | 发现突发异常（如服务器宕机）     |
| **日环比**   | 与昨天同期对比   | 日常波动判断                     |
| **周同比**   | 与上周同一天对比 | 排除周内波动影响（周末vs工作日） |

#### 示例

```
当前活跃数：2,410
小时环比：+14.43%  ← 比上一小时增长14.43%
日同比：+6.99%     ← 比昨天同一时间增长6.99%

解读：
  - 小时环比正常（白天活跃上升）
  - 日同比正常（符合预期）
  - 如果小时环比突然 -50%，可能有问题！
```

## 十、异常检测与归因

### 什么是异常？

```
异常 = 数据偏离正常范围

示例场景：
  - 平时DAU是10000，今天突然只有5000 → 异常！
  - 平时付费率3%，今天突然变成8% → 异常！（好的异常）
  - 平时崩溃率0.1%，今天突然5% → 异常！
```

### 归因分析

```
发现异常后，最重要的是找原因（归因）

场景：DAU突然下跌30%

归因过程：
  1. 按维度切片分析
     - 按渠道：渠道A正常，渠道B下跌80% → 定位到渠道B
     - 按设备：iOS正常，Android下跌50% → Android有问题
     - 按版本：旧版本正常，新版本DAU为0 → 新版本有bug！

  2. 找到根因
     → 新版本Android包上架后崩溃，用户无法登录

  3. 采取行动
     → 紧急回滚版本，修复bug

这就是AI Agent要做的事：自动完成这个分析过程
```

### 常见异常场景

```
用户量异常：
  - 某渠道被下架
  - 服务器宕机
  - 版本bug导致闪退
  - 竞品上线抢用户

付费异常：
  - 支付通道故障
  - 促销活动效果
  - 物价调整反应
  - 外挂导致经济系统崩溃

留存异常：
  - 新手引导改动
  - 难度曲线问题
  - 服务器卡顿
  - 内容消耗完毕
```

## 十一、数据埋点基础

### 什么是埋点？

```
埋点 = 在代码里插入数据上报逻辑

类比：
  console.log() 是给开发者看的日志
  埋点 是给运营/产品看的用户行为数据
```

### 常见埋点事件

```javascript
// 登录事件
trackEvent('login', {
  player_id: '12345',
  device_id: 'xxx-yyy-zzz',
  channel: 'taptap',
  os: 'android',
  version: '1.2.0'
});

// 付费事件
trackEvent('payment', {
  player_id: '12345',
  order_id: 'ORD_001',
  amount: 68.00,
  product_id: 'monthly_card',  // 月卡
  currency: 'CNY'
});

// 关卡完成事件
trackEvent('level_complete', {
  player_id: '12345',
  level_id: 15,
  duration: 120,  // 用时120秒
  retry_count: 2  // 重试2次
});

// 自定义事件（业务特有）
trackEvent('gacha_pull', {  // 抽卡
  player_id: '12345',
  gacha_type: 'limited',    // 限定池
  pull_count: 10,           // 10连抽
  result: ['SSR_001', 'SR_002', ...]  // 抽到的东西
});
```

### 埋点设计原则

```
1. 关键路径必须埋点
   - 登录、注册
   - 付费全流程
   - 核心玩法（战斗、抽卡、升级等）

2. 带足够的维度信息
   - 用户维度：player_id, device_id, channel
   - 时间维度：自动带时间戳
   - 业务维度：等级、VIP、服务器等

3. 数据不能丢
   - 弱网重试
   - 本地缓存
   - 断点续传
```

## 十四、术语速查表

### 基础指标

| 术语   | 英文全称                    | 含义             | 公式                     |
| ------ | --------------------------- | ---------------- | ------------------------ |
| DAU    | Daily Active Users          | 日活跃用户       | 当天登录用户数（去重）   |
| MAU    | Monthly Active Users        | 月活跃用户       | 30天内登录用户数（去重） |
| PCU    | Peak Concurrent Users       | 最高同时在线     | 单日在线人数峰值         |
| 留存率 | Retention Rate              | 用户回访比例     | 第N天回访用户 / 新用户   |
| PUR    | Pay User Rate               | 付费率           | 付费用户 / DAU           |
| ARPU   | Avg Revenue Per User        | 人均收入         | 收入 / DAU               |
| ARPPU  | Avg Revenue Per Paying User | 付费用户人均收入 | 收入 / 付费用户数        |
| LTV    | LifeTime Value              | 生命周期价值     | 用户全周期贡献收入       |
| CAC    | Customer Acquisition Cost   | 获客成本         | 广告花费 / 新增用户      |
| ROI    | Return On Investment        | 投资回报率       | 收入 / 成本              |

### 新增/转化相关

| 术语       | 含义                     |
| ---------- | ------------------------ |
| 激活       | 首次安装并打开游戏       |
| 创角       | 创建游戏角色             |
| 激活注册率 | 激活用户中完成注册的比例 |
| 注册创角率 | 注册用户中完成创角的比例 |
| 首充       | 用户的第一笔付费         |

### 用户行为相关

| 术语 | 含义                 |
| ---- | -------------------- |
| 回流 | 流失后重新回来的用户 |
| 滚服 | 在多个服务器创建角色 |
| 区服 | 游戏服务器           |

### 时间对比相关

| 术语 | 含义                                    |
| ---- | --------------------------------------- |
| 环比 | 与上一个周期对比（如小时环比、日环比）  |
| 同比 | 与去年/上周同期对比（如周同比、年同比） |

### 付费相关

| 术语     | 含义                                |
| -------- | ----------------------------------- |
| 直购     | 直接购买商品（非抽卡）              |
| 支付渠道 | 用户使用的支付方式（微信/支付宝等） |
| 退款率   | 退款订单数 / 支付成功订单数         |
